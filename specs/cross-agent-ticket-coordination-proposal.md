# 提案：Codex 與 Gemini 的票券協作流程

狀態：規劃提案，尚未實作。目標是沿用 to-tickets 與 handoff，建立兩種 Agent 都能使用的任務、訊息及成果契約。使用者已確認 Gemini CLI 與 Codex 共用同一台電腦。第一版採本機共用協作目錄，預留兩種 CLI 的執行器；自動派工前仍須完成執行環境與命令能力檢查。

## 1. 使用方式與目標

使用者將規格交給 to-tickets，協調者整理可執行的票券與依賴，分配給 Codex 或 Gemini。兩邊在各自的工作區完成工作，將問題與成果送回共用目錄。協調者檢查成果、整合與驗證後，才將票券標記為完成，並解鎖後續票券。

每一輪只能有一位協調者。Codex 和 Gemini 都可以擔任此角色，但不能同時改派同一組票券。工作者提出問題與建議，協調者負責共同規格與整合決策；需要使用者決定的產品取捨或授權仍交給使用者。

## 2. 建議架構

- 任務說明採 Markdown，機器處理的中繼資料採 JSON，第一版使用 Python 標準庫指令處理。
- 票券、相依關係、派工和整合狀態由協調者透過指令維護。工作者不直接編輯共用狀態檔。
- 工作者各自發布不可覆寫的訊息及成果檔。每一筆具有唯一 ID、任務 ID、嘗試 ID、發送者和時間，避免共用追加寫入檔案。
- 狀態指令取得執行期獨佔鎖後重新讀取狀態，檢查版本與合法轉移，再以同磁碟暫存檔及原子替換發布。並行呼叫不能依賴 Agent 自律或先讀後寫的普通檔案判斷。
- 票券固定指派一個擁有者，第一版不提供兩邊自由搶單。前置票券完成、寫入範圍不衝突時，協調者才分派下一張票券。
- 規格與協作格式可版控；執行狀態、瀏覽器設定、編譯快取與原始對話放在明確忽略的本機目錄。第一版不自動提交或推送這些產物。

## 3. 程式碼與執行環境隔離

優先讓不同 Agent 在不同 Git worktree 與分支工作。兩個 Agent 可以修改同一儲存庫的不同工作區，但不可同時在同一 checkout 中暫存或提交檔案。若暫時只能共用 checkout，所有程式碼寫入及 Git 操作須依序執行，不能宣稱可平行開發。

本工作區根目錄與五個子專案是獨立儲存庫。建立根目錄 worktree 不會自動為 Junction 指向的子專案建立獨立工作區。票券須記錄真正受影響的儲存庫與每個儲存庫的基準提交；跨專案任務優先依儲存庫拆分，再由協調者進行契約檢查。

編譯輸出、測試資料庫、附件測試頻道及服務連接埠也須隔離。需要共用本機服務時，由單一整合驗證程序管理使用權。正式打包、寫入 dist、版本調整及推送由協調者依既有授權統一處理，工作者交付原始碼提交及證據。

worktree 不會自動帶入未追蹤的 .env、node_modules 等檔案。任務啟動前檢查環境，依既有授權準備所需設定；不能盲目複製機密。LAH-API 的 MOCK=true、Oracle 與資料庫安全規則繼續適用。

## 4. 票券契約

每張票券在既有交付內容、Blocked by、驗收標準與建議驗證方式之外，加入以下資訊：

| 欄位 | 用途 |
|---|---|
| id、revision、spec | 穩定的任務編號、規格版本及來源 |
| repositories、base_commits | 受影響儲存庫及基準提交 |
| owner、attempt_id | 被指派的 Agent 及本次執行編號 |
| workspace、branches | 工作者實際可寫的路徑與分支 |
| allowed_paths、shared_resources | 允許修改範圍及需要獨佔的資源 |
| blocked_by | 前置任務；以整合完成為解鎖條件 |
| acceptance、verification | 可觀測驗收條件與驗證方法 |
| deliverables | 提交編號、修改摘要、證據及未驗證事項 |

範圍規則需要指令比對實際 Git diff。若超出指定檔案，不得自動標記完成。相依圖需拒絕循環、遺失任務及尚未整合完成的前置依賴。

## 5. 狀態與交付

主要流程為 draft → ready → assigned → running → review → done。受阻時進入 blocked，記錄原因與待決問題；修正問題後由協調者明確恢復到合法狀態。

工作者提交成果只代表待驗收，不能自行改成 done。成果至少包含：

- 每個儲存庫的基準提交與結果提交，且能證明結果建立於正確基準上。
- 實際修改檔案、目的、已知限制與剩餘工作。
- 執行的驗證、結果及證據檔案；未執行項目須明確列出。
- 介面或共享資源的影響，及是否需要後續整合驗證。

協調者驗證提交與修改範圍，在整合分支套用變更並執行必要驗證後，才標記 done。工作者測試通過不等於整合已通過。

重新指派會產生新的 attempt_id。舊嘗試回報保留作紀錄，但不能變更新嘗試的狀態。逾時只能標記為疑似中斷，不能直接認定前一個程序已停止並啟動第二位寫入者；必須先確認程序與工作區狀態，再復原或改派。

## 6. 訊息與決策

訊息以獨立檔案發布，類型至少包括 question、answer、progress、result、review。每筆記錄 task_id、attempt_id、from、to、message_id、reply_to 及內文。訊息必須可重複讀取與去重，讀取不能刪除唯一證據。

實例：Gemini 發現 API 規格與實作不符，發布 question。協調者查證後發布 answer，必要時更新票券 revision。若影響另一位工作者，發布新的任務簡報或決策通知；既有工作不會因他人訊息直接被改寫。

訊息不能授予發送者原本沒有的權限，亦不能覆寫 AGENTS.md。不得把密碼、權杖、.env 內容或整段可能含個資的日誌放進票券與訊息。

## 7. 從人工啟動到自動派工

第一階段先採人工開啟兩個 Agent，分別給出一段固定指令，要求讀取共用協作規則及其任務簡報。工作者在執行中於檢查點查閱待讀訊息，完成後發布成果。這個階段即可減少複製整段對話的負擔，但不會自動喚醒已停止的聊天回合。

第二階段提供概念上的指令介面，例如 list、assign、inbox、submit、review、integrate；每個指令有明確 JSON 輸入輸出及狀態檢查。指令名稱在實作時定案，這裡不代表已存在的可執行工具。

第三階段接入本機 CLI 執行器。協調腳本為各任務指定 cwd、實際可執行檔、獨立輸出目錄與明確的權限策略，以參數陣列啟動程序，不拼接包含票券文字的 shell 指令。

Codex 與 Gemini 的原始事件格式不同，執行器需分別解析，再轉為共同的 progress、question、result、failed 事件；不能把兩邊輸出的 JSONL 當作同一種格式。程序結束碼只代表 CLI 是否正常結束，不等於任務驗收通過。需要授權或互動輸入時，回報協調者處理，不自動放寬權限。

自動執行應啟動具明確任務邊界的新工作程序，不假設能控制兩個使用者已開啟的聊天終端。若要續接執行，記錄並使用明確的 session ID，不使用可能指向其他工作的 latest／last。Gemini 的實際可用參數必須依安裝版本檢查，不直接套用新版文件。

共用文件、派工、訊息傳遞與 Agent 喚醒是四個不同能力，必須各自驗證。

## 8. 實作切片與驗收

1. 定義協作規則與票券格式，提供 Codex、Gemini 通用的任務簡報與成果範本。以兩張互不依賴的小任務進行人工試跑。
2. 建立本機派工指令，驗證依賴、唯一擁有者、狀態轉移、修改範圍及訊息去重。模擬同時派工、重複回報及過期 attempt，確認不會產生雙重寫入者。
3. 接上 worktree 與交付流程，驗證相同檔案衝突、髒工作區、失敗測試、程序中斷後復原，以及合併後才解鎖依賴。
4. 最後評估兩端自動啟動與監看。確認環境與授權後，測試啟動失敗、等待輸入、取消、重啟與結果保存。

建議先完成前兩個切片再決定是否需要常駐服務、MCP 或網頁看板。驗收重點是兩個 Agent 能完成不同任務並可追溯地交付，且協調者能根據真實證據整合。

https://geminicli.com/docs/cli/headless/

建議落地順序為先完成票券契約、派工指令與兩張任務的手動試跑，再驗證 Gemini 登入及受限任務執行，最後開啟雙 CLI 自動派工。
