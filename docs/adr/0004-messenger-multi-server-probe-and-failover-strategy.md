# 0004: 即時通桌面端多候選伺服器陣列與自動探活容錯機制

**狀態**: 已採納 (Accepted)  
**日期**: 2026-11-02  

### 決策背景與脈絡
桃園即時通桌面端（`lah-messenger`）需在八個地政事務所與地政局內部環境運作。目前各所伺服器 IP（如桃園所新主機 `220.1.34.18`、舊主機 `220.1.34.75`，以及中壢 `220.1.35.84`、大溪 `220.1.36.14` 等共 9 組正式主機）已被定義於全域候選陣列 `tySvrIp` 中。然而，在客戶端探活（Health Probe）與連線失敗容錯（Failover）上，需要進一步確認連線探測的範圍應限於本所還是擴及全縣，以及如何加速探測與維持使用者體驗。

### 決策選項與權衡 (Decision Options)
1. **方案 A（所屬轄區優先 + 全域容錯備援）**：
   - 優先探測同仁所屬轄區之伺服器陣列（例如桃園所同仁優先探測 `220.1.34.18`，次選 `220.1.34.75`）。
   - 若本所伺服器均無法連線，自動依序輪詢全縣其餘 7 所與局本部共 8 台主機，直到找到可用服務為止。
2. **方案 B（嚴格轄區隔離探測）**：
   - 僅在同仁所屬轄區的伺服器陣列內進行探測（例如桃園所只在 `34.18` 與 `34.75` 間切換）。
   - 若全數斷線則進入警示並提示手動設定，防止跨所連線造成資料與頻道歸屬錯亂。
3. **方案 C（平行非同步快速探活）**：
   - 啟動時透過 HTTP `/ping` 或 WebSocket HEAD 快速平行探測所有候選 IP，取第一個回應者連線，大幅縮減依序 3.5 秒逾時的累積等待時間。

### 決策內容與原則 (Decisions)
1. **初次安裝自動探測填入 (First-Install Auto-Discovery)**：
   - 僅當同仁電腦初次安裝即時通、或本機儲存完全沒有伺服器設定時（`localForage` 中不存在 `wsHost` 紀錄），啟動全域多伺服器自動探測機制。
   - 優先探測同仁所屬轄區的候選伺服器陣列（例如桃園所同仁優先探測 `220.1.34.18`，次選 `220.1.34.75`）。
   - 若所屬轄區的主機全數連線失敗，客戶端自動將全縣其他事務所與局本部之正式伺服器依序加入候選佇列進行跨所輪巡容錯，直到找到第一台正常服務的伺服器。
   - 首次探活成功後，自動將該可用主機 IP 填入設定並保存至本機快取，完成初始化並解除探測狀態。
2. **嚴格既有設定鎖定 (Strict Saved Host Precedence)**：
   - 若本機已有儲存之伺服器 IP（或同仁手動於設定介面修改），即時通一律嚴格以該設定為主。
   - 程式重開機或冷啟動時，100% 採用既有設定，絕不覆蓋同仁設定。
   - 在已有指定主機的情況下，若該伺服器離線或暫時無法連線，客戶端完全不執行任何自動切換或漫遊輪轉，僅維持在該伺服器進行斷線重試，徹底防範跨所連線導致之頻道錯亂與資料混淆。
3. **階層式動態探測逾時 (Tiered Probe Timeout)**：
   - 僅於初次安裝自動探測階段生效：轄區內主機連線逾時維持 3.5 秒；跨所全局備援主機連線逾時縮短至 1.5 秒，大幅加速初次安裝時之自動尋訪速度。

### 取捨與後續影響 (Consequences / Trade-offs)
- **正面效益**：在單一所別伺服器維護或硬體故障時，同仁端毋須手動更改設定，程式能於數秒內自動切換至外部可用節點維持訊息收發。
- **跨所連線注意事項**：連線至跨所伺服器時，同仁之公告頻道（如 `announcement_<dept>`）仍能透過其帳號與部門接收，但跨所即時通伺服器之 SQLite 歷史頻道資料與本所不同，當本所主機恢復後可再透過手動或重啟切回。
