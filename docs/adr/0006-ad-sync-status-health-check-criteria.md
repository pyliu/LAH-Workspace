# 0006. AD 同步狀態健康度判定標準與錯誤過濾機制

- 日期：2026-11-02
- 狀態：Accepted
- 決策者：pyliu, Antigravity

---

## 1. 背景與問題脈絡 (Context)

前端智慧管控系統（`LAH-FE`）的戰情面板包含「AD 同步狀態」卡片（`lah-monitor-board-adsync.vue`），負責監控網域控制站排程執行的 Active Directory 目錄複寫作業（`repadmin /syncall`，由 `check-ad-204.bat` 與 `t1.vbs` 收集日誌後發送電子郵件通知至系統 SQLite 快取庫）。

原先前端的燈號判定邏輯僅檢查「是否存在信件」與「信件日期是否為今日」，未深入解析信件內文（`item.message`）。這導致即使同步過程中發生網路逾時、RPC 伺服器無法連線、伺服器未開機或使用者中途取消，系統仍將其判定為正常（綠燈 🟢），造成假性正常（False Positive），失去自動化監控與告警的實質效益。

---

## 2. 決策方案評估 (Options Considered)

1. **方案 A：雙向嚴格比對（白名單標記 + 黑名單排除）(Adopted)**
   - 驗證成功必要條件：日誌內文必須同時滿足包含 `SyncAll 完成`、`SyncAll 已終止，沒有錯誤`（或英文 `SyncAll terminated with no errors`）以及腳本執行完畢標記 `check end`。
   - 驗證排除異常條件：先將合法之「沒有錯誤 / no errors」過濾後，內文不得包含 `報告下列錯誤`、`發生錯誤`、`失敗`、`已取消`、`無法使用`、`錯誤` 或其他英文 error/fail 等異常關鍵字。
   - 燈號連動：最新一筆郵件若發生錯誤或非今日，戰情卡片最外層標題燈號一律轉為紅燈（`danger`）；單筆紀錄亦同步標示 🔴 與紅字。

2. **方案 B：僅比對單一成功字串**
   - 僅比對是否出現 `SyncAll 已終止，沒有錯誤`。若同步過程部分分割區失敗，但因指令結束輸出可能存在誤判風險，防護力不足。

3. **方案 C：純黑名單排除**
   - 僅檢查是否出現 `錯誤` 或 `失敗`。若日誌在執行途中中斷（無 `check end`），會被誤判為成功。

---

## 3. 決策結果 (Decision Outcome)

採納 **方案 A**。

1. **解析邏輯實作**：
   - 於 `components/lah-monitor-board-adsync.vue` 增設 `isSuccess(item)` 方法。
   - 嚴格比對白名單（完成與結束標記）與黑名單（排除合法關鍵字後的錯誤詞彙）。
2. **燈號連動準則**：
   - 戰情卡片燈號（Header Light）：
     - 無資料：黃燈（`warning`）。
     - 最新紀錄非今日或解析為失敗：紅燈（`danger`）。
     - 最新紀錄為今日且驗證通過無錯誤：綠燈（`success`）。
   - 歷史清單項目：
     - 通過者：顯示 🟢。
     - 異常者：顯示 🔴 並套用 `text-danger` 樣式。
3. **說明視窗更新**：
   - 同步修正 Help Modal 中的說明文字，明確定義綠燈為「同步完成且無錯誤」。

---

## 4. 影響與相容性說明 (Consequences)

- **介面相容性**：前端內部解析邏輯變更，不改動 `LAH-API` 之後端 API 契約與 `monitor_mail.db` Schema。
- **維運效益**：準確辨別伺服器異常與 AD 複寫中斷，避免管理人員被假性綠燈誤導。
