# 0002: Windows 高 DPI 與桌面縮放之視窗尺寸與渲染適配策略

**狀態**: 已採納 (Accepted)  
**日期**: 2026-11-02  

### 決策背景與脈絡
即時通桌面客戶端（`lah-messenger`）由 Electron 遷移至 Rust + Tauri v2 後，其原生視窗架構（基於 `tao`）具備 Windows 原生 Per-Monitor DPI-aware 特性。先前嘗試透過注入 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS="--force-device-scale-factor=1"` 鎖定內容渲染，但在 150% 桌面縮放下引發了新的連鎖破版問題：
1. **外框與內容渲染失調（右側白邊）**：Tauri 視窗外框依系統 150% DPI 放大為 735x1110 物理像素，但 WebView2 內部卻被強制以 100% 物理像素渲染，且前端 CSS 寫死 `width: 490px`，導致右側多出 245px（735 - 490）的巨大空白區域。
2. **視窗高度超出螢幕工作區**：在常見的 1080p 螢幕下，150% 桌面縮放所對應的螢幕邏輯可用高度僅為 680px（1080 / 1.5 - 工作列約 40px）。原本寫死之 740px 視窗高度直接超出螢幕範圍，底部訊息輸入框與操作按鈕遭 Windows 工作列遮蔽。

### 備選方案分析 (Options Evaluated)

| 評估維度 | 方案 A：移除強制參數 + 工作區動態高度自適應 (推薦) | 方案 B：雙重強制物理像素 (Window 與 WebView2 均硬鎖 490x740) | 方案 C：開放垂直自由拉伸 (Resizable) |
|---|---|---|---|
| **DPI 縮放支援** | 完整支援系統 100%、125%、150% 縮放，字體清晰無白邊 | 忽略系統縮放，永遠以 490x740 物理像素渲染 | 支援系統縮放，手動調整 |
| **高 DPI 易讀性** | 高（字體隨系統縮放適度放大，符合高解析度螢幕閱讀習慣） | 低（在 150%/200% 或 4K 螢幕上視窗與文字會變極小，難以點擊） | 中（同仁需自行拉伸視窗） |
| **底部輸入框可見性** | 100% 保證（啟動時自動偵測螢幕可用工作區高度，上限 740px，不足時自適應收斂） | 100%（高度僅 740 物理像素，能容納於 1080p） | 依同仁手動拉伸而定 |
| **版面穩定度** | 極高（寬度維持鎖定 490px 邏輯寬度，CSS 改為 100% 滿版，無白邊） | 高（無白邊，但高解析度下極小） | 偏低（可能因任意拉伸引發邊界排版異常） |

### 決策建議
採用**方案 A**：
1. 移除 `--force-device-scale-factor=1`，回歸原生一致的 Per-Monitor DPI-aware 渲染管線。
2. 前端全域樣式 `main.scss` 移除寫死之 `width: 490px`，改採 `width: 100%` 自適應容器寬度，徹底消除右側白邊。
3. 主視窗寬度維持鎖死 490px 邏輯寬度；視窗高度於 Rust 原生層偵測當前顯示器之工作區可用高度（Work Area Available Height），動態設為 `min(740, available_height - 30)`，確保輸入框永遠完整呈現。
