# 領域文件規範 (Domain Docs)

工程技能在探索本專案程式庫時，應如何讀取與遵循專案的領域知識文件。

## 在探索程式碼前，請先閱讀以下文件

- 專案根目錄的 **`GLOSSARY.md`**，或
- 專案根目錄的 **`GLOSSARY-MAP.md`**（若存在）：此檔案會指向各個 context 專屬的 `GLOSSARY.md`。請閱讀與當前任務主題相關的詞彙表。
- **`docs/adr/`**：閱讀與你即將進行變更之領域相關的 ADR（架構決策紀錄）。

若上述任一檔案不存在，**請靜默繼續進行**，無需刻意標記缺失，亦無需在事前主動提議建立。當詞彙或決策真正需要釐清時，`/domain-modeling` 技能（可透過 `/grill-with-docs` 與 `/improve-codebase-architecture` 調用）會延遲並按需建立。

## 檔案結構

單一領域脈絡儲存庫（Single-context repo，適用於本專案）：

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-dist-artifacts-auto-publish.md
│   └── ...
└── ...
```

## 使用詞彙表中的規範術語

當你的產出提及領域概念時（例如在 Issue 標題、重構提案、假說驗證、測試案例命名中），請務必遵循 `GLOSSARY.md` 中定義的術語，切勿自行偏離改用詞彙表明確避免的同義詞。

若你需要表達的概念尚未收錄於詞彙表中，這是一個訊號：表示你可能正在創造專案未曾使用的詞彙（請重新審視），或是專案存在領域知識缺口（請記錄下來以供 `/domain-modeling` 補充）。

## 標註 ADR 衝突

若你的產出或建議與現有的 ADR 決策有所衝突，請明確提出討論，切勿隱蔽或私自推翻原決策：

> *與 ADR-XXXX 相衝突，但值得重新討論，因為……*
