# Correct（根除重複錯誤）

操作者（使用者）在這個專案儲存庫中不斷為了相同的錯誤糾正代理（Agent）。請直接改造儲存庫，讓下一個代理根本無法再犯這些錯。

> **強制輸出語言規範**：所有錯誤分類分析、證據整理、防呆層級選擇與最終回覆，**一律強制使用台灣繁體中文輸出**。

假設每一位貢獻者都是一個「只能看到自己所開啟的檔案、直接複製最近範例、並採取能通過編譯的最短路徑」的代理。請將儲存庫設計成：從單一檔案看起來正確的修改，對整個專案儲存庫而言也是正確的。

## 1. 找出錯誤類別（Find the mistake classes）

首先，閱讀近期的 Commits、Reverts、審查意見（review comments）、代理規則檔（如 `AGENTS.md` 或 `.agents/rules/`），以及解釋權宜解法（workarounds）的註解。將這些錯誤歸納成不同類別（classes）。只要同一類錯誤發生過兩次，就構成一個錯誤類別。

## 2. 在能奏效的最高層級修復每一個類別（Fix each class at the highest level that works）

請依序嘗試以下層級（由高到低）：

1. **從架構上徹底消除（Eliminate it with architecture）**：讓每一份狀態都只有單一擁有者，讓每一項任務都只有一種受支援的做法。隱藏內部實作細節，讓錯誤的匯入直接失敗。將手動同步的清單替換為單一真相來源（single source of truth）。刪除代理可能會去複製的舊做法與死碼（dead code）。
2. **用型別強制約束，讓錯誤狀態根本寫不出來（Enforce it with types）**：如果錯誤的程式碼依然能通過編譯或語法檢查，請新增一條 Lint 或 CI 檢查，且其錯誤訊息必須直接點出應該改用哪個檔案、型別或函式。如果該舊模式在既有程式碼中已經很常見，請設定為「僅在變更中新增更多此類寫法時才報錯失敗」。
3. **測試行為（Test the behavior）**：如果某個測試在它所檢查的行為壞掉時依然通過，或者只在內部實作細節改變時就失敗，請修正或刪除該測試，改為針對實質行為進行測試。
4. **最後才寫文件或代理規則，且僅用於主觀判斷（Write docs or agent rules last）**：當代理跳過不讀文件時，文件不會觸發任何建置失敗。因此唯有需要取捨判斷（judgment calls）的事項才寫成文件或 `AGENTS.md` 規則。

## 3. 修復並證明有效（Fix and prove）

接著，立即修復最常發生的錯誤類別，每個類別獨立一個 Commit。**證明每一項新增的檢查都能在過去真實發生過的錯誤案例上觸發失敗**。在本機與 CI 執行相同的驗證指令。若確有例外需求，必須在觸發違規的那一行加上例外標記、明確理由、到期日，以及人工審核批准。

## 4. 維護規則對照表（Keep the rule table）

最後，在代理規則檔（如 `AGENTS.md`）中維護一張對照表，將每一條規則與「強制執行它的機制（型別／Lint／測試）」配對記錄。每當操作者糾正你時，先修復錯誤並將規則加入表中；如果該規則早就存在於表中，卻沒有任何強制機制把關，代表這是一次重複犯錯——請在同一次變更中，將它提升到能奏效的最高層級進行防呆。一旦某個錯誤在結構上已經不可能再發生，即可將該條文字規則從表中移除。

**最終回覆**：列出每一個錯誤類別及其歷史證據、你選擇的防呆層級，以及為什麼更高層級在此不適用。
