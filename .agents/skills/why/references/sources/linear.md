# Linear 議題與工單追蹤調查劇本（Linear Tickets）

## 此資料來源包含什麼

- 描述功能、臭蟲及其背後動機的議題工單（Issues）
- 附掛在工單上的專案文件（通常為產品需求文件 PRD 或技術規格書）
- 父子工單階層關係（從高層級專案計畫到具體實作子工單）
- 工單底下的留言討論（需求釐清、範圍變更、「為什麼我們要這樣做」的理由）
- 標籤（Labels，例如 `compliance`、`customer-request`、`perf`），能直接指出動機類型
- 解釋需求範圍變化的狀態更新紀錄
- 附件與關聯的 GitHub PR

Linear（或 Jira、GitHub Issues、Plane、Shortcut 等議題追蹤系統）通常是保存**產品與業務脈絡**的地方——也就是「因為客戶 X 提出要求」或「這是為了 Q3 合規計畫而做」這一層的原因。

## 如何搜尋與挖掘

使用環境中的 Linear（或對應工單系統）MCP 工具：

1. **從已關聯的工單 ID 開始（Start with linked tickets）**：若種子 Commit 或 PR 內文中提及了工單 ID（例如 `ENG-1234`、`[BUG-567]`、`#123`），請先用 `get_issue` 拉取這些工單，並完整閱讀內文與所有留言。
2. **以關鍵字搜尋相關工單（List related issues by keyword）**：使用 `list_issues` 搭配文字搜尋功能名稱、關鍵符號（Symbol）或業務術語，並嘗試多種不同的詞彙表達。
3. **順著工單樹向上追溯（Walk the issue tree）**：若你查到的是一張子工單（Sub-issue），請務必拉取它的父工單（Parent issue）。子工單通常只寫「怎麼做（戰術層面）」，而父工單才載明了「為什麼要做（戰略層面）」。
4. **閱讀專案級文件（Read project docs）**：若工單歸屬於某個專案（Project），請呼叫 `get_project` 並檢查附掛的文件——規格書與設計理由最常保存在專案層級的文件中。
5. **檢查標籤與里程碑（Check labels and milestones）**：標籤能暗示動機類別（如客戶要求、事故後續追蹤、合規審查）；里程碑則將工作與特定截止日期綁定，往往能揭示背後的業務驅動力。

## 什麼是優質的證據

- 明確陳述業務痛點的工單描述：「因為客戶 Acme 的 SOC2 稽核要求，需要新增 X 功能。」
- 記錄了架構取捨的留言：「我們決定採行方案 B，因為方案 A 需要修改計費服務。」
- 標題點出高層級目標的父工單：「Q3 企業級可用性提升計畫」或「降低付款失敗率」。
- 附掛在工單上的 PRD 或技術規格書。
- 如 `customer:acme`、`incident-followup`、`compliance`、`perf-regression` 等具體標籤。

## 常見陷阱（Common Pitfalls）

- **需求範圍偏移（Scope drift）**：PR 所引用的工單可能曾經關閉後又以不同範圍重開。請務必閱讀完整歷史紀錄。
- **流於形式的範本套話（Mechanical templates）**：有些團隊強制要求填寫「Why」欄位，但工程師只填了「改善使用者體驗」之類的罐頭套話——這種空泛文字不算真正的答案。
- **過時的舊工單（Stale tickets）**：早期工單可能反映的是後來被推翻的舊版計畫。請務必核對日期，並與程式碼實際上線日期交叉比對。
- **因重複而關閉的工單鏈（Closed-as-duplicate chains）**：若工單被標記為 Duplicate，請順著關聯追回真正的主工單（Canonical ticket）。
- **權限受限的私密內容**：若無權限存取某張工單，請明確將其記錄為「搜尋缺口（Gap）」，切勿憑空猜測。

## 回報內容規範（What to Return）

針對每一張相關工單，請回報：
- **工單 ID 與標題**
- **從描述或留言中逐字引述的問題／動機原文**（請勿自行改寫摘要，綜合分析員需要精確原文來引用）
- **標籤、父工單與所屬專案**
- **作者、建立日期與關閉日期**
- **工單連結**（若可取得）
