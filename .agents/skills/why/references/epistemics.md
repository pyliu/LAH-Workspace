# 知識論與證據可信度框架（Epistemics）

當歷史證據零碎、片面甚至彼此矛盾時，我們該如何評估可信度（Confidence），並在不把推論誇大為虛假確信的前提下誠實告知使用者？

**程式碼本身只展示了它「做了什麼」，但無法證明它「為什麼存在」。** 「為什麼（Why）」保存在 Commit 訊息、PR、工單、文件與對話紀錄裡——而這些紀錄往往是不完整、帶有偏見，甚至已經佚失的。假裝事實並非如此，只會製造出聽起來很有把握、實則誤導使用者的盲目猜測。

## 五大可信度層級（Confidence Tiers）

最終輸出報告中的每一項主張（Claim），都必須明確歸屬於以下五個層級之一。該層級決定了它應該放在哪個章節，以及必須使用什麼樣的繁體中文措辭。

### 1. 直接證據（Direct）

有明確的文字引述直接回答了問題：也就是作者當年**親筆寫下**說明「為什麼」的文字，而不是「因為程式碼做了 X，所以作者當年一定想要 X」。
- **範例**：PR 描述寫著「此修改修復了項目超過 1000 筆時無法分頁的臭蟲」；工單寫著「應客戶資安審查要求新增此檢查」；程式碼註解寫著 `// 上游 API 拒絕大於 100 的值，故限制上限為 100`；設計文件寫著「因為需要跨重啟持久化，我們選擇方案 A 而非方案 B」；或作者在討論串中留言「舊作法在測試中太不穩定，改用此作法」。
- **措辭規範**：篤定、現在式、緊鄰附上引用來源。例如：「此設計之所以存在，是因為 X（參見 PR #123）。」

### 2. 間接支撐（Supported）

多項間接證據同時收斂指向同一個結論。雖然沒有單一來源直接明寫，但跨來源的證據模式讓該結論極具說服力。
- **範例**：Commit 標題寫著「改善效能」、關聯工單標記了 `perf`，且周邊幾個 Commit 全都在修改同一條熱路徑（Hot path）；或者隨該變更一起新增的數個測試案例全都針對極大輸入值進行測試；又或者同一位作者在同一週內的其他 PR 都點名了同一起線上事件。
- **措辭規範**：有把握但清楚標示為推導結論，並逐一引用各項證據。例如：「多項證據強烈指向 X：[列出具體證據項目與來源]。」

### 3. 合理推論（Inferred）

對脈絡做出的合理解讀，但沒有直接文字佐證。這是**你的詮釋（Interpretation）**，而非紀錄中的既定事實。
- **範例**：Commit 沒寫為什麼，但對照事件頻道的時間點，當時正式環境正發生該錯誤，且該修復在當天就被緊急合併，因此很可能是一次緊急熱修復（Hotfix）；或者函式名稱暗示了重試邏輯，且重試次數 `3` 與團隊在程式碼庫其他地方慣用的 3 次重試慣例一致。
- **措辭規範**：使用保留語氣（Hedged），並將推理鏈完整攤開。例如：「考量到 A 與 B，由於 D 的緣故，C 似乎是最合理的解釋。」

### 4. 推測性假設（Speculative）

建立在薄弱證據上的合理假設，且其他替代解釋也同樣說得通。這類假設仍值得提出（因為使用者可能剛好知道哪一個才對），但必須明確標示為猜測。
- **範例**：「這可能是為了繞過某個早期瀏覽器臭蟲而寫的暫時性解法（Workaround），但我們沒有找到當年的直接紀錄」；或「這個閾值有可能是為了配合某項 SLA 承諾而設定，但現存文件中未見相關記載」。
- **措辭規範**：「其中一種可能性是 X，但我們沒有找到直接證據。」通常應放在「競爭假設（Competing Hypotheses）」章節中，與其他可能性並列呈現。

### 5. 未知（Unknown）

你已經徹底搜尋過，但確實找不到答案。**這是一個完全合法且極具價值的調查結果，請務必將其記錄下來。**
- **措辭規範**：「我們搜尋了 X、Y 與 Z，但未發現任何說明其原因的證據。」請具體寫出你**實際查了什麼**——只寫一句「我們查不到原因」毫無幫助；請寫出：「我們以關鍵字 A 與 B 搜尋了議題追蹤系統、檢視了 2023 年以來修改過此檔案的 6 個 Commit，並在整個儲存庫中 grep 了符合該閾值的字串字面量，但皆未發現任何設計理由記載。」

## 繁體中文措辭指南（Phrasing Guide）

- **篤定詞彙（Confidence words）**：代表背後有「直接證據（Direct）」或「間接支撐（Supported）」，後面**必須緊鄰附上引用來源**。絕不可將這些詞用於個人推論：
  - 「因為…（because）」、「原因在於（the reason is）」、「是為了…而設計（was designed to，宣稱作者意圖）」、「修復了／解決了（fixes / solves，宣稱變更達成了目標）」、「團隊決定（the team decided，宣稱曾發生團隊共識決策）」。
- **保留語氣詞彙（Hedges）**：明確向讀者發出「這是推論詮釋，而非文獻記載」的訊號。在「我們可以合理推論的事項」章節中請大量使用：
  - 「似乎（appears to / seems to）」、「很可能（likely）」、「暗示了／顯示出（suggests）」、「與…相符（is consistent with）」、「一種解讀是（one reading is）」、「合理推測（plausibly）」、「當時可能是（may have been）」、「現有跡象指向（the evidence points toward）」。
- **嚴禁使用的詞彙（Words to avoid）**：
  - **「顯然（obviously）」**：如果真的那麼顯然，使用者就不會來問了。
  - **「很明顯地（clearly）」**：後面接的往往是一點也不明顯的武斷宣稱。
  - **「理所當然（of course）」**：同上。
  - **「就只是（just）」**（例如「這就只是為了效能而寫的 X」）：輕率的語氣通常是用來掩飾背後的證據不足。
  - **「我認為／我相信（I think / I believe）」**：你的任務是綜合客觀證據，而非發表個人感想。請改用「證據顯示（the evidence suggests）」。

## 避免事後合理化（Avoid Rationalization）

一段在今天看來「好像挺合理」的程式碼，當年可能是為了完全不同（且如今已不復存在，甚至當年就是錯的）的原因而寫下的。
- 切勿將混亂的歷史演進強行美化成一套乾淨完美的事後理由。
- 切勿先假設原作者當年一定做了「正確的事」，再倒果為因去找理由替他辯護。
- 切勿把單純的複製貼上（Copy-paste）自動當成深思熟慮的一致性設計。
- **切勿把「找不到證據（Absence of evidence）」當成「不存在該問題的證據（Evidence of absence）」**（例如不可宣稱：「因為沒有人提到資安顧慮，所以當年肯定沒有資安問題」）。

## 避免迎合偏誤陷阱（The Sycophancy Trap）

使用者在發問時常會順帶塞入自己的猜測：「為什麼我們要這樣寫？我猜是為了效能吧？」
**切勿順著使用者的話直接附和確認！** 使用者的猜測只是調查的起點之一，而不是等你去背書的結論。請將使用者的猜測視為眾多候選假設之一，獨立查驗客觀證據：如果證據確實支持，就附上引用來源確認它；如果證據不支持（或指向其他原因），請誠實告知，並呈現證據真正支持的結論。

## 當證據彼此矛盾時（When Evidence Contradicts）

請在輸出報告中**同時列出雙方的證據與引用來源**，不要為了拼湊出一個乾淨圓滿的故事而擅自抹除其中一方。例如：工單上寫著「為了滿足客戶 X 的合規要求而新增」，但 PR 描述卻寫著「清理此區域的技術債」。這兩者可能同時為真（工單是業務起因，PR 是作者順手重構的切入點），也可能其中一方寫錯了——請將兩者並列，交由使用者做最終判斷。

## 當證據缺失時（When Evidence Is Missing）

一句誠實且交代清楚搜尋範圍的「**我們不知道（We don't know）**」，是這個技能最有價值的產出之一。它能讓使用者清楚知道：答案不在顯而易見的紀錄裡，接下來應該直接去問真人（原作者、PM 或技術負責人），或者決定這個問題不值得再花時間深究。反之，若不敢承認未知，反而用看似篤定的猜測去填補空白，會嚴重誤導使用者做出錯誤的修改決策。請具體點出每一個知識缺口：問題是什麼、查了哪些來源、在各來源搜了什麼關鍵字，以及找到了什麼（完全沒有，或只有無關的邊角資訊）。

## 定稿前的最終自我檢查（Before Finalizing）

在綜合分析員（Synthesizer）交付最終報告前，必須逐一檢查「我們找到的確切證據」與「我們可以合理推論的事項」中的每一句主張：
1. 每一項直接或間接主張是否都附有具體的引用來源？若無，必須移至「合理推論」或「競爭假設」。
2. 措辭語氣是否與其所屬的可信度層級完全吻合？
3. 是否不小心把「程式碼本身的行為」當成了「作者意圖的直接證據」？（若有，請移除或重新分類為推論。）
4. 報告中是否包含具體的「我們尚不知道的事（What We Don't Know）」章節？（如果整份報告完全沒提到任何知識缺口，通常非常可疑——除非歷史文獻異常完整，否則很可能是把不確定的部分藏了起來。）
