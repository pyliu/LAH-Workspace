# 解釋數據背後的成因（Explain the Number）

- **追問「為什麼不是兩倍好？」** 明確指出限制該結果的資源或程式碼路徑，例如 CPU 核心、鎖（Lock）、磁碟、網路，或是負載產生器本身。請從執行期間收集的效能剖析（Profile）或系統計數器中取得依據，並對應回原始碼。單靠閱讀程式碼所做的猜測不算數。如果你無法解釋為什麼這個數字沒有好上兩倍，代表你根本不知道自己量測到了什麼。
- **列出這個數字可能量測到的其他事物，並憑證據逐一排除。** 常見的干擾因素包括：錯誤提早返回、被跳過或命中快取的工作、根本沒執行到的程式碼、未調校的對照組（維持預設設定的一方）、環境雜訊，以及所佔比例太小以至於在端到端（End-to-End）流程中無關緊要的片段。
- **將證據與數據保存在一起。** 將執行次數、數據離散程度（Spread）以及瓶頸限制因素記錄在筆記或連結的產物（Artifact）中。

針對效能數據，請搭配 [benchmark-checklist](../benchmark-checklist/SKILL.md) 技能執行完整檢核程序。針對評測（Eval）結果，也請對實驗過程提出同樣的詰問：每次執行是否都確實完成了任務？差距在不同試驗與不同模型間是否依然成立？這個測試情境本身是否具實質意義？

如果數據背後的證據缺少執行次數、缺少離散程度、沒有指明限制瓶頸，或者宣稱節省的時間甚至大於被修改片段原本花費的時間，就代表你跳過了本原則。

本原則與 [證明它能運作](../principle-prove-it-works/SKILL.md) 不同：後者旨在確認產出結果是否真實有效。

> **輸出語言規定**：套用本原則時，所有分析、說明與回覆內容一律使用**台灣繁體中文**。
