# 測試行為，而非實作細節（Test Behavior, Not Implementation）

測試是一份關於「程式碼為其使用者做了什麼」的主張；這裡的使用者可以是呼叫端（Caller）、終端使用者或另一個外部服務。所謂**行為（Behavior）**，就是這些使用者透過他們所接觸的介面能夠觀測到的事物，包含：回傳值、錯誤、可讀回的狀態，以及對外部系統產生的副作用（例如發出的請求、寫入資料庫的資料列、或發送出的訊息）。所謂**實作（Implementation）**，則是使用者無法觀測到的內部細節：私有輔助函式（Private Helpers）、內部呼叫順序、中間過度資料，以及是由哪一個內部協作物件完成了工作。

請用兩個假想的修改來檢驗每一個測試：

- **破壞行為。** 讓程式碼回傳錯誤的值、跳過某個副作用，或將某個副作用重複執行兩次。如果測試依然通過，代表這個測試什麼都沒證明。常見原因包括：斷言（Assertion）比介面契約（Contract）還寬鬆、預期值是由受測程式碼自己算出來的、單純重複宣告常數或提示詞字串卻從未實際執行讀取它的程式碼，以及對測試自己拼湊出來的假資料進行斷言。
- **改變內部實作。** 保持所有外部可觀測結果完全不變，僅重構底層程式碼結構。如果測試因此失敗，代表它被綁死在實作細節上——這種測試每次重構都得重寫，卻抓不到任何真正的 Bug。

請保留能抓出第一種修改、且能挺過第二種修改的測試；其餘測試請重寫或刪除。若要寫出同時滿足這兩點的測試，請以具體的輸入透過使用者介面驅動程式碼，並根據「需求規格」而非「程式碼執行結果」推導出預期值，最後精確斷言契約所承諾的內容——不多也不少。

決定什麼是行為的關鍵在於「介面契約」，而非斷言長什麼樣子。當契約承諾「空購物車絕不扣款」時，斷言付款客戶端「未被呼叫」就是在測試行為（請搭配一個實際會扣款的測試案例，證明該測試確實觀測得到呼叫）。被模擬（Mocked）的外部服務所收到的 Payload 是行為，因為該外部服務會觀測到它；對內部私有輔助函式的呼叫則是實作，因為沒有任何外部使用者看得到它。當沒有任何資料列符合條件時，「空陣列」是精確的行為答案；但如果測試只是隨便檢查有回傳某個陣列，那就是空洞的檢查。死背完整錯誤訊息字串會綁死沒有任何呼叫端在乎的措辭；呼叫端真正用來做條件分支的「錯誤型別／錯誤碼」才是契約。

測試也可以用來釘住某個不變條件（Invariant），而非特定函式呼叫，例如某個鍵值必須同時存在於兩張資料表中，或是編譯期的型別檢查。此時，該不變條件本身就是受測行為。

> **輸出語言規定**：套用本原則時，所有分析、說明與回覆內容一律使用**台灣繁體中文**。
