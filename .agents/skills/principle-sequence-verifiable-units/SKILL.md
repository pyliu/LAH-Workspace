# 將工作排序為可驗證的單元（Sequence Work into Verifiable Units）

將工作安排為一連串小單元，每個單元結束時都必須處於可檢查的狀態，且在當前單元驗證通過（Green）之前，絕不推進到下一個單元。

**原因：** 在引發問題的那個單元當下抓到錯誤，定位成本極低；等到整批修改完才發現錯誤，問題早已深埋其中，而且你已經在壞掉的基礎上蓋了更多東西。將這些相同的單元按順序排列成審查者可以重播（Replay）的交付序列，就能把「請相信我」變成「你看它先變紅（Red），接著變綠（Green）」。

**執行階段（Execution）：** 在全面清查（Sweep）、遷移或一連串相似修改中，請在開始下一個修改前先驗證當前修改。每個單元都是一個「修改前／修改後」的夾擊區間：從已知良好的狀態出發、進行一項變更、執行檢查，通過後再繼續。請先 Rebase 到乾淨的主幹（Trunk）上，確保每次檢查都是相對於真實基準線進行量測。當使用槓桿工具（Lever）執行批次修改時，逐單元檢查的成本近乎為零——即便如此，也請務必執行檢查。

**交付階段（Delivery）：** 請按照能夠「證明工作成果」的順序來堆疊 Commits 與 PR。最經典的結構是：先提交會失敗的測試，再於其上提交修復程式碼。其他具說服力的敘事順序包含：先做減法再重塑結構、先擷取基準線（Baseline）再套用改善方案、先搭基礎鷹架（Scaffold）再實作功能。讓每個 Commit 都能獨立站得住腳，使整個提交序列讀起來就像一篇論證嚴密的推論。

本原則是 **prove-it-works**（[證明它能運作](../principle-prove-it-works/SKILL.md)，確保每項檢查真實有效）與 **build-the-lever**（[打造槓桿工具](../principle-build-the-lever/SKILL.md)，讓逐單元檢查成本極低）在執行順序上的互補原則。

> **輸出語言規定**：套用本原則時，所有分析、說明與回覆內容一律使用**台灣繁體中文**。
