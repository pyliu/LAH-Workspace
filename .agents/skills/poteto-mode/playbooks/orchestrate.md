### 專案統籌調度 (Orchestrate)

**你負責掌控整個專案計畫（Program），絕不親自撰寫程式碼。你的職責是撰寫任務簡報（Brief）、排空佇列（Drain the queue）、維持合併前緣（Frontier）綠燈、並做出決策。** 本劇本適用於交由單一常駐協調者（Coordinator）對話負責的完整大型計畫：跨越多日、眾多堆疊 PR（Stacked PRs）、數十至數百個子代理（Subagents），且人類每天僅檢視兩次而非每五分鐘盯場。若僅是推進單一任務直到達成條件，請路由至自主執行（Autonomous run）；若是需要客製化工作流程的單一高難度任務，請路由至 `figure-it-out`。唯有當工作規模超越任何單一代理的存活週期時，才路由至此處。單一代理能在當前工作階段（Session）預算內完成的工作，不構成一個大型專案計畫。

儀式感（Ceremony）必須隨計畫規模縮放。面對低成本且高度相似的工作單元（Units），請依各節指示精簡流程。

以下三條鐵律貫穿全局：

- 任務完成通知是佇列事件（Queue events），而非中斷信號（Interrupts）。
- 每次啟動（`invoke_subagent`）與每次喚醒續行（`send_message`），皆必須一字不漏地附帶常駐指令（Standing orders）。
- 任務簡報（Brief）就是你的核心產出。含糊不清的簡報會無聲地失敗，因為執行代理（Worker）無法向你反問問題。

#### 角色與配置 (Roles and placement)

- **協調者（Coordinator，即本對話）。** 本機執行。負責確立框架、撰寫任務簡報、排空收件匣（Inbox）、維護給人類的進度報告，並做出判斷與決策。協調者絕不親自撰寫或編輯業務程式碼。合併衝突、分支鏈變基（Chain rebases）與程式碼變更一律視為子代理任務。在本地 Git 操作成本低廉的儲存庫（注意：`LAH-Workspace` 下 `LAH-API`、`LAH-FE`、`lah-messenger-server`、`lah-messenger` 為四個各自獨立的 Git 儲存庫）中，機械式地落地已驗證的工作單元（對 Worker 的提交進行 Fast-forward 或乾淨的 Cherry-pick 後推送）屬於帳務整理，協調者可自行處理。若將已完成的工作排隊堵在閒置的堆疊代理（Stacker）後面，只會讓截止時間一無所獲。整個迴圈從頭到尾皆由代理驅動。一律透過 `invoke_subagent` 工具啟動子代理，並搭配 `send_message` 與 `manage_subagents` 進行通訊、續行與管理。請依據「Subagents」章節，為每個子代理的工作挑選合適的模型層級與推理預算。狀態讀寫一律在排空點（Drain points）透過 `scripts/orch/orch.ts` 執行，一行指令輸入、一行結果輸出。該 CLI 絕不負責啟動、等待或喚醒任何代理。
- **子協調者（Sub-coordinator）。** 一律於本機持久執行，每個軌道（Track）配置一個，且僅在計畫規模超出單一協調者排空能力時才啟用。協調者能自行排空的軌道不需要中間層。每一層巢狀結構都會重複支付完整的背景引導成本，且阻塞式的子協調者會在父代理閒置時掩蓋其子代理的進度。子協調者擁有該軌道的工作單元與看板、撰寫其 Worker 的簡報、透過 `invoke_subagent` 啟動自己的 Worker 與驗證者（Verifier，巢狀支援至第 3 層，並可配置 `Workspace` 隔離模式）。在每一波（Wave）邊界彙整總結，絕不直接轉發未經整理的原始子代理報告。將執行中的子代理數量上限控制在單次排空可處理的範圍（約 10 個），採滾動視窗（Rolling window）補充，絕不採阻塞式批次（Blocking batches，否則每批都得受限於最慢的子代理）。
- **執行者／驗證者（Worker / Verifier）。** 優先使用獨立分支或共享工作區（`Workspace: "branch"` 或 `"share"`），除非任務需要存取當前環境資源：例如透過 Chrome DevTools MCP 或終端工具進行執行期驗證、讀取 `<appDataDir>\brain\<conversation-id>\.system_generated\logs\transcript.jsonl` 下的本機對話紀錄、模擬器與本機 IDE 狀態，或僅存在於本機的憑證。隔離環境的代理若無法直接讀取本機協調狀態庫，其簡報必須內嵌所需資訊或指向儲存庫路徑。優先選擇數量較少、職責較廣的 Worker。每個工作樹（Worktree）或分支僅限單一寫入者（遵循 `principle-separate-before-serializing-shared-state` 技能）。同一個工作單元的驗證者（Verifier）應盡可能配置與執行者（Worker）不同的視角或模型層級。

結構深度維持在「協調者 → 軌道（Track）→ 執行者（Worker）」。請依專案特性劃分軌道（建置、落地整合與驗證是常見切法，但非硬性規定）。寫死的固定蜂群樹狀結構已被證實過於僵化而不採用。

#### 狀態庫結構 (Store layout)

在當前代理的狀態目錄（如 `<appDataDir>\brain\<conversation-id>/orchestrate/<project-slug>/`）下建立目錄。每個檔案都只有唯一一個寫入者。擁有者發布事實，讀取者於讀取時進行彙整。使用 `bun scripts/orch/orch.ts`（下文簡稱 `orch`）進行帳務管理，同時其標準的純文字 TSV 與 JSON 格式即使不透過 CLI 也能直接閱讀。

- `preferences.md` 是常駐指令暫存器（Standing-orders register）：帶編號的行，每行一條限制條件（模型策略、堆疊形狀與數量、驗證門檻、禁止修改路徑、升級回報政策、以及 `LAH-Workspace` 的強制規範如 `./LAH-API/www/.env` 保持 `MOCK=true`、保留無關既有註解等）。每次啟動（`invoke_subagent`）與每次續行（`send_message`）都必須一字不漏地貼入。指令會在多次續行間衰減，每遺漏一條就會耗費一次人類介入。當你發現自己正在重複陳述某條指示時，請在行動前先將該行追加至檔案中（遵循 `principle-encode-lessons-in-structure` 技能）。
- `overview.md` 是持久化的 PR 與 Issue 資料庫。僅可追加（Append），絕不因單一事件而整份重寫。
- `units.tsv` 每個工作單元佔一行：包含 `id`、`track`、`state`、`branch`、`PR`、`head SHA`、`brief path`。請就地更新資料列。
- `frontier.json` 是依「堆疊安全（Stack safety）」計算出的合併前緣。
- `ledger.tsv` 是依「驗證（Verification）」維護的驗證分類帳。
- `inbox/` 存放完成通知指標（Pointers）。`gates.md` 停放需要人類裁決的關卡（問題、選項、未回覆時的預設動作）。
- `decisions.tsv` 是透過 `show-me-your-work` 技能記錄的決策軌跡。
- `status.md` 是在每次排空時由 `units.tsv` 與 `ledger.tsv` 衍生產生，絕不手動維護。請從表格重新生成它，而非將事件寫成流水帳填入其中。

#### 任務簡報 (The brief)

你發給子代理的提示詞（Prompt）是你唯一的產品，一份草率的簡報會在整棵代理樹中放大為全面失控。每次呼叫 `invoke_subagent` 都必須完整包含以下所有欄位。填不出來的欄位代表你尚未將該工作單元界定清楚。

```
GOAL         一句話說明目標成果，必須讓無法存取當前對話的外部代理也能直接執行
SCOPE        此單元可寫入的路徑、禁止觸碰的路徑、其專屬的工作樹（Worktree）或分支（需標明屬於哪一個獨立 Git 子專案）
CONTEXT      指向相關檔案與 PR 的指標；若此單元依賴上游報告，必須完整貼入，因為 Worker 看不到同層級的兄弟代理
ACCEPTANCE   可檢驗的驗收標準，每行一項
VERIFY       精確的驗證指令或驗證技能路徑，以及已知的陷阱（Gotchas，例如 LAH-API 必須維持 MOCK=true）
TIMEBOX      執行時間的大致上限；逾時時請回傳部分發現並停止，而非無止境跑下去
FORBIDDEN    禁止重新指定 PR 基底或合併、禁止 rebase、禁止 force-push、禁止修改範圍外的程式碼、保留無關既有註解，外加單元專屬禁令
REPORT       status、branch、head SHA、PRs、verdict、實際執行的指令、偏差說明、建議後續事項
STANDING     <一字不漏貼入 preferences.md 內容>
```

請依工作單元規模調整簡報大小。僅需一行指令的單元，可將範本濃縮為一段文字，但仍須點出目標、範圍、驗證指令與回報格式。為兩行程式碼的修改包一層 4KB 的樣板，撰寫與遵守的成本比修改本身還高。本機子代理可透過路徑引用常駐指令檔；跨環境啟動或每次透過 `send_message` 喚醒續行時，則必須一字不漏地貼入。

子協調者（Sub-coordinator）的簡報需額外加上：其軌道邊界與工作單元清單、子代理啟動預算與環境配置清單、排空協定（Drain protocol），以及彙整回報格式（每個子代理一行：名稱、狀態、PR、head SHA、判定結果，外加軌道整體狀態與合併前緣變化量）。

相依性（Dependency）是上下文的接力傳遞，而不僅是執行順序。未宣告的上游背景會迫使 Worker 瞎猜。缺漏欄位屬於「拒絕啟動」條件。每一波（Wave）中，對每個子協調者抽樣稽核一份 Worker 簡報，與該波並行執行，絕不作為阻擋在前的關卡。若簡報稽核未通過，應暫停該軌道並修正子協調者的指示（而不僅是修正該 Worker），因為簡報品質往往在長程執行後期衰減。絕不透過連續喚醒（Resume-chain）拼湊簡報；請整合範圍後重新啟動（Respawn）乾淨的子代理。

#### 執行步驟 (Steps)

1. **確立框架（Frame）。** 將完成條件（Done predicate）陳述為可計數的指標（例如：「全部 126 個工作單元皆已合併，且每個單元於分類帳中皆達到 `unit-test-verified` 以上等級」）。量化範圍：單元數量、預估工作量、預期堆疊數與牆上時鐘（Wall-clock）時間預算。若單一代理能在該預算內完成，請立即停止本劇本並改用自主執行（Autonomous run）。降級精簡不應依賴其他文件存在，而是直接在本工作階段動手完成、必要時輔以一般 Worker、內聯驗證、邊做邊落地，完全略過下方的狀態庫、暫存器或前導測試機制。請根據預算排定落地時程：當預算消耗約 70% 時，停止啟動新工作並將已驗證的成果落地。依專案特性命名各軌道。若有具爭議的拆解或不可逆決策（One-way door），在前導測試前先執行 `arena` 技能。框架僅需向使用者展示一次，可逆的準備工作無須等待即可推進。
2. **安裝執行環境（Install the runtime）。** 執行 `orch init`。透過 `show-me-your-work` 技能開啟決策軌跡，在啟動任何子代理前寫好常駐指令（Standing orders），並透過 `orch frontier set --repo <repo-dir>` 從現有 PR 初始化 `frontier.json`（若程式碼託管平台為 Origin 則加上 `--forge origin`）。
3. **前導測試（Pilot）。** 將一個工作單元完整推過整條路徑：簡報、Worker、驗證、堆疊登錄、分類帳記錄、合併。前導測試的存在是為了在成本僅有一個代理（而非五十個）時，證偽簡報範本、驗證配方與單元粒度。在扇出（Fan-out）展開前，根據前導測試的證據修正契約。前導測試規模應配合單元調整：若計畫由高度相似的低成本單元組成，第一個單元就是前導測試，直接作為正常單元執行並內聯驗證指令，一旦落地即刻展開扇出。專屬的前導流水線（獨立驗證代理、稽核關卡）僅保留給高成本或新型態的工作單元，而非毫無證偽價值的複製型單元。
4. **規模化擴展（Scale）。** 以滾動視窗方式透過 `invoke_subagent` 啟動 Worker 直至並行上限，隨著子代理完成隨時補位。阻塞式批次會為每批最慢的子代理買單。僅在超過「角色與配置」所述的單次排空門檻時，才啟動軌道子協調者。每次排空後重新計算就緒的工作，將上游報告傳遞至下游簡報中。保持同層級代理僅向上彙報。抽樣簡報稽核與該波並行執行，若失敗則阻擋下一輪補位，而非中斷當前波次。
5. **排空佇列（Drain）。** 在每個排空點執行下方的佇列紀律。
6. **持續落地（Land）。** 落地整合是持續進行的，絕非留到最後的終端階段。整合從第一個通過驗證的單元就開始，並與剩餘波次並行推進。在大型複雜儲存庫上，堆疊代理（Stacker）從第一波起就是常駐角色，隨單元驗證完成即刻整合；在本地 Git 成本低廉的儲存庫上，協調者可依「角色與配置」自行落地已驗證單元。在推進上層堆疊工作前，務必保持合併前緣（Frontier）綠燈，並受「堆疊安全」規範約束。僅在合併完成或回報新 head SHA 時推進 `frontier.json`。
7. **結案收尾（Close）。** 排空最終收件匣，將每個曾啟動的子代理對帳至終態列（`done`、`abandoned`、`zombie-reconciled`），在真實產物上確認完成條件（Predicate），確認每個已落地 PR 的當前 head SHA 皆有驗證判定（Verdict），依 `show-me-your-work` 技能稽核決策軌跡（包含跨模型審查），並將重複發生的修正編碼寫入 `preferences.md` 或簡報範本中。完整保留狀態庫作為事後檢討（Postmortem）依據。

#### 佇列與排空紀律 (Queue and drain)

- 收到子代理完成通知時，執行 `orch inbox push <agent> <unit> <status> [--report PATH]` 並立即回到你原本正在做的事。絕不在當下直接進行深度審查。需要審查的完成項目應轉化為一個驗證者（Verifier）工作單元。絕不在排空過程中直接審查 Diff。
- 在以下四個時間點進行批次排空：關鍵區段（Critical section）結束時、軌道彙整（Track rollup）時、合併前緣監控器喚醒時（透過 `schedule` 工具或 `loop` 技能設定定時喚醒與長效的心跳保底機制）、以及向人類報告之前。每批排空皆以 `orch inbox drain` 開始。排空期間抵達的通知一律留待下一批處理。
- 必須先完成才能排空的關鍵區段包括：撰寫任務簡報、堆疊操作、衝突裁決、撰寫人類關卡（Gate）、更新分類帳或合併前緣。
- 每次排空需對每個指標進行分類（`landed`、`needs-verify`、`failed`、`zombie`、`noise`），透過 `orch unit add`、`orch unit set` 與 `orch ledger record` 寫入對應資料列，執行 `orch status`，接著在單一回合訊息中啟動下一波子代理。
- 在軌道彙整時，必須為每一個曾啟動的子代理交代下落：已抵達（Arrived）、已重啟（Respawned）、或其範圍已被明確吸收（Absorbed）。默默重做失蹤子代理的工作，會同時掩蓋白費的運算資源以及其結果原本要填補的覆蓋率缺口。
- 排空回合的結尾僅輸出 `orch status` 的三行摘要：各狀態計數、本次變更內容、開啟中的人類關卡。詳細資訊存放在 `status.md`。完整的回覆契約僅適用於檢查點（Checkpoints）與結案（Close）。

#### 堆疊安全 (Stack safety)

- 合併前緣（Frontier）是計算出來的物件，絕非文字敘述。每次合併與堆疊變更後，皆須重新計算 `frontier.json`：包含排序後的 PR 清單、分支名稱、head SHAs、世代編號（Generation number），以及最底層未合併的 PR。該指令會從當前檢出分支沿著 PR 基底鏈向上走訪，因此鏈路順序與 PR 狀態皆來自遠端平台（預設使用 `gh`，若為 Origin 則傳入 `--forge origin`）。Head SHAs 則取自本地分支參照，因此請從 Stacker 的 Clone 中解析。沒有對應 PR 的分支應直接報錯而非猜測。請注意 `LAH-Workspace` 中四個子專案各自為獨立 Git 儲存庫，執行前必須確認位於正確的子專案目錄。
- 每個堆疊僅允許唯一一個堆疊代理（Stacker）變更拓撲結構（分支鏈變基、強制推送、基底重指派、合併），且在該堆疊內序列執行。請將持有者記錄於常駐指令中。大規模分支鏈變基應交由隔離的工作樹或子代理執行，避免拖垮主環境。
- Worker 絕不執行 rebase，也絕不重指派基底或合併 PR。看護代理（Babysitters）遵循 `playbooks/babysit.md`，每個堆疊配置一個，範圍鎖定在單一不可變的合併前緣世代（Frontier generation）。遇到衝突時僅向 Stacker 回報，而不自行 rebase。
- PR 的關閉與基底重指派一律只能透過 Stacker 執行。關閉基底 PR 會使上方整條分支鏈成為孤兒。合併與堆疊手術皆視為一般工作單元，同樣需要撰寫任務簡報。
- 配置一個回溯監控代理（Retro watcher）追蹤已合併的 PR，監看是否有退版（Reverts）、合併後 CI 破損或孤立的後續追蹤事項。

#### 驗證規範 (Verification)

驗證規模應與工作單元匹配。當 `VERIFY` 僅是一行低成本指令（如 `php -l`、`node -c`、`yarn lint`）時，由 Worker 自行執行並回報輸出，協調者僅抽查收據（Receipts）。專屬的驗證者代理（Verifier，配置與 Worker 不同的模型或獨立視角）則保留給驗證成本高昂、需高度判斷力或爆炸半徑大的工作單元。若一個驗證代理的全部產出只是重跑一行簡單指令，那是形式主義，而非真正的驗證。在驗證 `LAH-API` 相關單元時，務必確認 `./LAH-API/www/.env` 維持 `MOCK=true`，嚴禁對 Oracle 9i 執行未授權寫入或破壞性操作。

使用 `orch ledger record` 寫入分類帳資料列，並以 `orch ledger check` 檢查當前 PR 與 head SHA。`ledger.tsv` 中每個判定結果（Verdict）佔一行，以「PR 編號 + head SHA」為主鍵：`live-ui-verified | unit-test-verified | type-check-only | verifier-blocked | verifier-failed`。CI 綠燈只是判定的輸入條件之一，本身並非判定結果。涉及行為變更的工作必須達到比 `type-check-only` 更高的等級。`verifier-blocked` 不算通過，應待環境修復後重新啟動驗證。`verifier-failed` 應派發修復單元（Fix unit），而非盲目重跑驗證。Worker 可進行自我回報，但 Verifier 在相同主鍵下會覆蓋該結果。新的 head SHA 會使舊資料列失效，因此重新堆疊（Restack）後必須重新驗證。回答「這是否已驗證」的唯一依據是分類帳（Ledger），而非記憶或對話紀錄。

工作單元的產出必須在落地的瞬間完成外部化（Externalized），才算真正完成，絕不留到整場執行結束才批次處理。Worker 必須推送其分支、Verifier 必須寫入其分類帳資料列、收據必須存入狀態庫。若某項工作僅存在於單一暫存環境中，一旦該環境終止就消失，那它從未真正完成。

#### 存活監控與故障處理 (Liveness and failure)

- 絕不為了檢查子代理狀態而呼叫恢復/續行，因為這會重新喚醒閒置中的代理。請以唯讀方式探測：透過 `manage_subagents`（`Action: "list"`）、檢查分類帳、`units.tsv`、`gh`、已推送的分支狀態。對話紀錄檔的修改時間（mtime）不代表代理仍存活。
- 無聲死去的子代理會在收件匣中產生一列合成的事後檢討紀錄（包含單元、失敗模式、最後證據、後續選項）。隨證據抵達即時重新規劃，絕不等待所有代理完全靜止（Full quiescence）。
- 依失敗模式重試：觸及上限或記憶體不足（OOM）時，縮小範圍後重新啟動（Respawn）；網路斷線時，原樣重試；工具錯誤時，改用不同模型或配置重試；未知原因則重試一次。重試兩次仍失敗後，放棄該單元並繞過它重新規劃。
- 遲到數小時才回報的殭屍代理（Zombie），在接受其任何產出前，必須先與當前的合併前緣及分類帳進行對帳。若有獨特發現，請透過全新的工作單元加以挽救，絕不盲目合併。
- 當繼續啟動子代理只會在整棵樹上產生垃圾產出時（例如上游產出錯誤、驗收標準破損、基礎設施停擺），請在常駐指令最上方寫入一行停止令（Stop line），讓執行中的工作跑完，修復根本原因後再將其清除。
- 限制你自身的基礎設施重試次數，標準與限制子代理相同。在連續數次工具異常中止後，請停止重試，將終端交接資訊寫入持久化狀態（已完成項目、存放位置、精確的恢復指令），然後結束本次執行。
- 當環境或工作階段重啟後：本機子代理已終止，但已推送的分支與遠端工作仍在。請重新讀取常駐指令與 `units.tsv`、重新計算合併前緣、透過 PR 與分支（而非代理 ID）重新掛載進度、根據儲存的簡報與當前狀態為每個軌道重新啟動一個子協調者、執行排空並恢復運作。已終止工作階段的狀態庫鎖定會在下一次寫入時自動清除（`orch` 會自動替換持有者 PID 已消失的鎖定）。

#### 升級回報機制 (Escalation)

應升級交由人類裁決（批次彙整於狀態頁面，而非逐項打擾）的事項：不可逆操作（對共用分支進行 force-push、部署、刪除資料、關閉他人的 PR、修改資料庫 Schema 或 `.env`）、無法透過實驗解決的真實產品或偏好決策、與觀測到的事實相矛盾的常駐指令、以及重新規劃後仍無法突破的計畫級死胡同。在透過 `ask_question` 詢問前，先將每項問題停放為 `gates.md` 的條目，並將其他工作繞過該關卡繼續推進。

絕不升級打擾人類的事項：合併前緣微調、變基（Rebase）操作細節、重試、CI 偶發失敗（Flake）分類、審查討論串分類、格式修正、簡報已明令禁止的範圍（直接拒絕並繼續），以及詢問「我該繼續嗎」。若有疑慮，先採取可逆行動並記錄下來。

執行中途的新發現，僅修復會阻擋合併前緣（Frontier）的問題；其餘一律停放至後續追蹤事項（Follow-ups）。在這種扇出規模下，微小的範圍蔓延（Scope leak）都會倍增成無人要求的額外 PR。

**回覆要求（Reply）：** 在檢查點（Checkpoints）與結案（Close）時，請回報：完成條件（Predicate）以及取自 `units.tsv` 與 `ledger.tsv` 的對應計數、各軌道及其已落地成果、合併前緣（PR 清單與 SHAs）、驗證判定摘要、放棄的項目與原因、等待人類裁決的關卡（唯一的提問項）、狀態庫路徑，以及決策軌跡路徑。所有數字必須來自表格而非文字敘述，並附上 PR 與檔案連結。**所有回覆、摘要與報告皆須以台灣繁體中文輸出。**
