### 堆疊自動駕駛（Autopilot-stack）

**你掌控整個 PR 堆疊（Stack），但絕不親自執行合併上線（Landing）。你的交付物是一條線性、依基底分支串聯（Base-chained）的 PR 堆疊，交由操作者（Operator）審查並合併。** 除了已驗證工作的最終交付方式之外，其餘規則皆遵循 **Autopilot-full**（`playbooks/autopilot-full.md`）。每次定時檢查（Tick）都會從主幹重新讀取這兩份劇本，當兩者有所差異時，以本劇本為準。

> **強制語言規範**：所有回覆、分析報告、待辦清單（Todo list）、決策紀錄（Decision trail）、PR 標題與描述，以及 Commit 訊息，**一律強制使用台灣繁體中文輸出**。同時必須嚴格遵守工作區 `AGENTS.md` 的四個獨立 Git 儲存庫邊界與安全護欄。

1. **執行 Autopilot-full 的負責人機制，但移除合併動作。** 各 PR 負責人（透過 `invoke_subagent` 孵化）以回報 `STACK-READY` 取代 `merge-ready`。負責人絕不自行 Rebase 到其他分支（包含主幹在內），也絕不自行變更目標基底分支（Retarget）、合併、關閉 PR 或啟動自動合併，因為根協調者（Root，即你）掌控整條堆疊鏈的拓撲結構，而操作者掌控最終合併。當某個項目依賴另一個項目時，其負責人應從該父項目的分支切出新分支，而非從主幹切出。
2. **確保堆疊拓撲只有單一寫入者。** 各負責人僅推送自己的分支，並向你回報每次的最新提交（Tip）及其預期的父分支。唯有你能對堆疊鏈中的環節進行 Rebase 或變更目標基底分支（Retarget），因為同一條鏈上若有兩個寫入者將會互相覆蓋彼此的工作。請依相依順序將每個通過驗證（Clean）的 PR 串接起來，並將其基底分支設為其父項目的分支（使用 `origin pr edit <pr> --base <parent-branch>` 或 `gh pr edit <pr> --base <parent-branch>`）。絕不強制依賴 `gt`。負責人會將你推送後的版本作為其新的基底與租約（Lease），若發生衝突則由負責人解決屬於它自己的那層切片後，再交由你推送。
3. **在根協調層吸收主幹漂移（Drift）。** 在操作者開始合併上線之前，對堆疊鏈中的每個環節套用 Autopilot-full 步驟 5 的檢測規則，並在需要時由下而上（Bottom-up）對整條堆疊鏈進行 Rebase。接著逐一環節套用 `patch-id` 規則（每個環節的比較基底即為其父分支）。
4. **交付堆疊鏈後即放手，切勿再寫入。** 每個環節的 PR 中都記載了其驗證裁決。一旦操作者開始執行合併上線，除了 `playbooks/shipping.md` 授權的「父分支合併後重新指向基底分支」之外，任何人都不准再寫入該堆疊鏈，因為第二個寫入者會破壞進行中的合併流程。合併途中若發現任何問題，皆須透過你回報給操作者，且任何修復都必須等待操作者明確下達動工指令。

**如何在兩種自動駕駛模式間選擇：** 當各個 PR 彼此獨立且已獲得合併授權時，選擇 **Autopilot-full**。當操作者希望在合併前親自審查、各項工作具有先後順序或緊密耦合，或者未授予合併權限時，選擇 **Autopilot-stack**。

**回覆（Reply，強制使用台灣繁體中文）：** 依據 **ketchup**（`../ketchup/SKILL.md`）技能向操作者進行進度總結，附上堆疊根部與頂端 PR 的連結、每個環節的單行驗證裁決摘要，以及任何被擱置或排除的項目與原因。
