### 自主持續執行（Autonomous run）

**你對退出條件（Exit condition）負有全責。先定義何謂「完成」，接著不間斷地一路推進直到達標。**

> **強制語言規範**：所有回覆、分析報告、待辦清單（Todo list）、決策紀錄、PR 描述與 Commit 訊息，**一律強制使用台灣繁體中文輸出**。

1. 在進入第一輪迭代之前，先將退出條件定義為一個可程式化檢驗的斷言（Checkable predicate，例如：測試全數綠燈、問題重現已修復、所有 N 個 PR 皆已合併、像素差異為零）。
2. 使用 Antigravity 的 `schedule` 工具（或建議 `/schedule`、`/goal` 指令，對應原 `/loop` 機制）選擇喚醒機制。若有特定事件需要監看（如 CI、合併狀態、分支前進），可指派一個監看子代理（透過 `invoke_subagent`）在事件發生時透過 `send_message` 喚醒你，並搭配長週期的時間心跳（Heartbeat）作為備援。若無特定事件，則設定與結果值得重新檢查之時間相匹配的固定間隔計時器。請依據 `SKILL.md` 的「子代理調度（Subagents）」章節，為每個子代理選擇合適的模型層級（預設 `Model: "inherit"`）。
3. 每一輪迭代僅做出當前證據所支持的最小幅度變更，對照退出條件斷言進行驗證，若指標有所推進則提交 Commit，若無幫助則直接捨棄變更。凡是抱持「說不定有幫助」心態的多餘防禦性修改（Belt-and-suspenders）一律還原，不得留在分支上搭便車。
   請透過 **sequence-verifiable-units**（`../principle-sequence-verifiable-units/SKILL.md`）原則技能來安排工作序列，每完成一個單元即立刻驗證，而非把所有檢查堆積到最後才批次執行。
4. 執行途中發現的問題皆屬你的職責。遇到損壞的技能、相關聯的 Bug、不穩定的驗證器、審查雜訊、工具鏈失敗、孤立的後續追蹤項目，以及可修復的架構漂移，請直接透過 `poteto-mode` 自行解決。將主線以外的附帶修復（Out-of-band fixes）放入獨立的 PR 中。切勿將可逆的工作擱置給人類處理，也不要為此呼叫 `ask_question`。唯有遇到不可逆操作（以及違反 `AGENTS.md` 安全紅線的操作：如關閉 `LAH-API` 的 `MOCK=true`、對 Oracle 執行破壞性 SQL、安裝/移除套件、修改 `.env`、執行正式打包 `nuxtron build`）、實驗無法解決的真正產品／偏好決策，或陷入真正的死胡同時，才浮上水面詢問使用者。請始終將退出條件斷言作為核心驅動目標，並在完成每個支線修復後立即回到主線。
5. 透過 **show-me-your-work**（`../show-me-your-work/SKILL.md`）技能為每一輪迭代建立檢查點紀錄，每一列以繁體中文記錄本輪修改了什麼，以及退出條件斷言是否有所推進。
6. 當退出條件斷言完全滿足時才停止。遇到停滯期（Plateau）絕不等於停止；請持續推進並轉換做法以突破瓶頸。若確實陷入死胡同請誠實回報，切勿在原地空轉，更嚴禁為了宣告勝利而擅自放寬退出條件。

**回覆（Reply，強制使用台灣繁體中文）：** 退出條件、執行的迭代次數、已交付的變更、已捨棄的嘗試、最終的退出條件斷言狀態。
