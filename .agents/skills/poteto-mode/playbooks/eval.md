### 盲測評估（Eval）

**你對實驗設計負有全責。負責規劃、盲化處理（Blind）、執行與綜合分析。**

> **強制語言規範**：所有回覆、分析報告、待辦清單（Todo list）、評分標準（Rubric）、決策紀錄與綜合評估結論，**一律強制使用台灣繁體中文輸出**。

**盲化處理不可妥協的鐵則（Non-negotiables for blinding）：**

- 在候選子代理（Candidate）可見的任何目錄名稱、檔案名稱或 Prompt 中，**嚴禁出現** `eval`、`test`、`judge`、`experiment`、`rubric`、`score`、`compare`、`benchmark`、`candidate` 或 `arena` 等字眼（及其對應的中文「評估」、「盲測」、「評審」、「實驗」、「評分標準」、「候選」等暗示字眼）。
- 給候選子代理的 Prompt 必須看起來完全像是一般使用者的自然開發請求。只陳述任務目標，絕不透露後設評估意圖。
- 禁止出現誘導回報技能鏈的提示。不要要求候選子代理列出自己套用了哪些技能、原則或讀取了哪些檔案。僅一般性地要求提供設計說明，並從最終程式碼的結構與實際對話紀錄來評斷其是否遵循技能鏈，而非聽信其自我宣稱（Self-report）。
- 淨化目錄與識別代號（Slug）名稱。使用一般使用者在真實專案中可能會取的名稱。
- 絕不讓候選子代理知道還有其他競爭候選者的存在。
- 評審子代理（Judge）可以知道自己正在擔任評審，但只能看到經過淨化匿名的標籤（如方案 A、方案 B）及其產出，絕不能看到背後的模型名稱。
- 當比較兩個變體（Variants）時：由同一個評審子代理在單一回合內、使用同一套量表同時為兩組產出打分，且評審完全不知道哪一個產出來自哪個變體。

**執行步驟：**

1. **界定框架（Frame）。** 明確定義本次受測的變體是什麼，以及什麼樣的行為表現算作成功。撰寫僅供評審子代理查閱的評分標準（Rubric，包含 3 到 6 項具體標準），並對所有候選子代理嚴格保密。
2. **建立淨化的隔離環境。** 為每個候選子代理準備各自獨立的工作目錄（例如位於 `<appDataDir>\brain\<conversation-id>\scratch\` 下以自然專案命名的目錄，或透過 `invoke_subagent` 的 `Workspace: "branch"` / `"share"` 隔離），並放入受測變體。預先植入自然任務應有的上下文：專案骨架，以及候選子代理在正常情況下會自然讀取到的 `.agents/skills/` 技能檔案。
3. **撰寫單一自然的任務 Prompt。** 完全模擬真實使用者會輸入的文字，不洩漏任何正在被量測的線索。
4. **平行孵化 N 個候選子代理。** 依據 **arena**（`../arena/SKILL.md`）技能的 Phase B，透過 `invoke_subagent` 平行啟動 N 個候選子代理。每個子代理在各自淨化後的獨立目錄中工作，且接收完全相同的 Prompt。請依據 `SKILL.md` 的「子代理調度（Subagents）」章節設定模型參數（預設 `Model: "inherit"`，或依 `.agents/rules/pstack-models.md` 配置）。
5. **孵化一位盲測評審子代理。** 依據 **arena** 技能的 Phase C，透過 `invoke_subagent` 啟動一位評審子代理。評審只能看到匿名標籤標示的產出與評分標準（Rubric），絕不會看到模型名稱。
6. **從對話紀錄（Transcripts）查驗技能鏈執行狀況，而非聽信自我宣稱。** 讀取每個候選子代理的對話紀錄檔（透過 `manage_subagents` 的 `list` 動作取得 `transcript` URI，或讀取 `<appDataDir>\brain\<subagent-conversation-id>\.system_generated\logs\transcript.jsonl`）。切勿跨工作區亂抓無關專案的私人對話紀錄。檢查每個候選子代理實際呼叫 `view_file` 開啟了哪些檔案，結合其實際讀取的檔案清單與最終程式碼結構來評定技能遵循度，絕不採信候選子代理在回覆中的片面之詞。
7. **親自從頭到尾閱讀每一個候選子代理的產出。** 將你的判斷與評審子代理的裁決進行比對。若兩者出現分歧，代表模型存在偏見或評分標準不夠明確。進行最終綜合分析。

**回覆（Reply，強制使用台灣繁體中文）：** 受測變體、評分標準（Rubric）、各候選方案觀察筆記、評審裁決、你的綜合分析，以及是否建議正式採用（Promote）該變體的具體建議。
