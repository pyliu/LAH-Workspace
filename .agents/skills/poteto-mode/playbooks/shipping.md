### 交付與合併落地 (Shipping)

**你負責最終落地（Land）的成果。獨立驗證每一個 PR，僅從根部開始落地連續通過驗證的 PR 序列，並在落地期間避免干擾堆疊。**

1. **解析程式碼託管平台（Forge），並在每個 PR 落地前獨立完成驗證。** 預設使用 GitHub CLI（`gh`）。若 `command -v origin` 成功且 Origin 能解析該儲存庫，則所有 PR 操作皆使用 `origin pr`；否則維持使用 `gh` 並記錄此降級選擇。絕不強制要求使用 Graphite（`gt`）。請注意 `LAH-Workspace` 的四個子專案（`LAH-API`、`LAH-FE`、`lah-messenger-server`、`lah-messenger`）各自為獨立 Git 儲存庫，執行前須確認位於正確儲存庫目錄，且 `LAH-API` 維持 `MOCK=true`。每個 PR 配置一個獨立的驗證者子代理（透過 `invoke_subagent` 啟動），使用對應的控制技能或驗證工具（如 `chrome-devtools`、語法檢查 `php -l` / `node -c`、Lint 與測試），比對父分支與當前 Head，以真實使用者的操作方式執行變更，並在該 PR 上發布 `PASS`、`PASS+NOTES` 或 `FAIL`。唯有「非撰寫該段程式碼的代理」所給出的判定（Verdict）才算數，因為作者往往只會檢查自己原本打算做出什麼。CI 綠燈與機器人審查批准（Bot review）皆不算數，因為兩者都沒有像真實使用者一樣實際運作該變更。
2. **僅落地從最底層根部算起、連續通過驗證的 PR 區間（Contiguous verified run）。** 從最底層尚未合併的 PR 向上走訪，遇到第一個沒有 `PASS` 或 `PASS+NOTES` 的 PR 即停下。位於它下方的所有 PR 就是本次可落地的連續區間（Run），而最頂端的那個通過驗證的 PR 就是本次的天花板（Ceiling）。位於未驗證 PR 上方的已驗證 PR 必須等待，因為它無法在缺少下方程式碼的情況下單獨落地。若某個上層 PR 的分支既不包含也不依賴下方未驗證的程式碼，則可將其移至主幹（Trunk）並獨立落地——但必須先取得全新的驗證判定，因為舊判定是在有下方程式碼墊底的環境下跑出來的，而主幹上並沒有那段程式碼。
3. **再次確認驗證判定是否仍準確描述當前程式碼。** 一份驗證判定涵蓋的是一份修補程式（Patch），而分支鏈變基（Chain rebase）會將其上方的每個 PR 推向新的 SHA，且不會觸發任何檢查失敗。在信任舊判定之前，請比對判定當時 SHA 與當前 Head 的 `git patch-id`。當兩份 Patch 僅在測試、文件或 Lint 設定上有所差異時，若該驗證通道（Lane）在兩個 SHA 上建置出的執行產物除雜訊（Noise）外完全一致，則原判定依然有效。所謂「雜訊」，是指對同一個判定 SHA 連續建置兩次也會出現的差異，或是內嵌的 Commit SHA 字串。請列出每一種雜訊及其對應檔案，以便閱讀者查核你的判斷。至於變更本身仍須通過最新的檢查與審查，因為舊判定並未見過這些修改。沒有建置產物的驗證通道（例如開發伺服器）無法以此方式證明等價性，因此必須重新執行驗證；任何發生偏移（Drifted）的項目也一律重新驗證。
4. **由下而上（Bottom-up），一次落地一個 PR。** 永遠先合併連續區間中最底層未合併的 PR，使用 `origin pr merge <pr>` 或 `gh pr merge <pr> --squash`（若在需要提交與推送的場景，請遵循 `AGENTS.md` 第 4.3 節規範，使用台灣繁體中文撰寫符合 Conventional Commits 的詳細標題與內文）。在 Origin 上，基本指令會連帶合併你所指定 PR 下方的所有 PR；而在 GitHub 上，若某個 PR 的基底（Base）仍是其父分支，直接合併會合入該父分支而非主幹（Trunk）。因此合併後務必讀回 PR 狀態確認結果（`origin pr view <pr>` 或 `gh pr view <pr> --json state,mergedAt,baseRefName`），因為當合併佇列（Merge queue）僅將 PR 排入佇列時，合併指令也會回報成功，且「已請求自動合併（Auto-merge）」不等於「已合併」。真正落地的 PR 狀態必須為已合併（Merged），且其基底必須是主幹而非父分支。僅在某個 PR 的驗證判定已涵蓋其當前 Head 時，才可啟用 `--auto`（Origin 的 merge-when-ready 或 GitHub 的 auto-merge），因為它會在就緒時直接將當下的 Head 落地。當底層 PR 合併落地後，將原本以該分支為基底的下一個 PR 重新指派基底至主幹（`origin pr edit <pr> --base <trunk>` 或 `gh pr edit <pr> --base <trunk>`），將其 Patch 移至合併後的結果上，並使用 `--force-with-lease` 推送。由於驗證判定涵蓋的是 Patch 而非 Commit 本身，請依步驟 3 的 `patch-id` 規則決定原判定是否繼續有效；待其檢查通過且判定有效後即可合併。
5. **在堆疊落地期間，保持雙手離開，切勿隨意干預。** 步驟 4 中移動下一個 PR 的操作，是對分支或基底唯一允許的變更，因為合併指令會將該瞬間分支與基底上的任何內容直接落地（無論有無驗證判定）。在 GitHub 上，請搭配 `schedule` 工具或 `/loop` 使用 `playbooks/babysit.md` 中的佇列監控腳本（`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`）持續監看，直到它在天花板（Ceiling）PR 回報 `COMPLETE`。在 Origin 上，每次 `origin pr checks <pr> --watch` 返回時，使用 `origin pr view <pr> --checks` 重新讀取當前 PR，直到天花板 PR 顯示為已合併。當父分支合併時，子 PR 的基底自動移往主幹屬於正常預期行為，並非需要修復的損壞。若合併卡住，在動手改變任何設定前，請先查明原因。
6. **抵達天花板即停止。** 若要將落地範圍向上延伸，需要取得新的驗證判定，因此必須重新從步驟 1 走過一輪。

**回覆要求（Reply）：** 本次驗證通過的連續 PR 區間及其天花板、每個 PR 的驗證判定結果與產出該判定的驗證代理、實際落地了哪些 PR 以及你如何確認其已合入主幹、還有下一個缺口需要什麼條件才能推進。**所有回覆、摘要與報告皆須以台灣繁體中文輸出。**
