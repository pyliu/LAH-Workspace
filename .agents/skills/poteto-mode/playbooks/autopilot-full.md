### 全自動駕駛（Autopilot-full）

**你掌控最終裁決權（Verdicts），而非親自撰寫個別 PR。每一個 PR 由專屬的負責人子代理（Owner）從建構一路帶到合併，且在你的驗證集群（Swarm——從未參與撰寫該段程式碼的獨立代理群）實證通過即將合併的程式碼之前，任何 PR 都不准合併。**

> **強制語言規範**：所有回覆、分析報告、待辦清單（Todo list）、決策紀錄（Decision trail）、PR 標題與描述，以及 Commit 訊息，**一律強制使用台灣繁體中文輸出**。同時必須嚴格遵守工作區 `AGENTS.md` 的四個獨立 Git 儲存庫邊界與安全護欄。

一份裁決僅涵蓋單一修補程式（Patch），而一次綠燈 CI 僅涵蓋單一分支頂端提交（Head）。步驟 4 會在程式碼就緒時執行一次完整的驗證集群（Full swarm），後續唯有發生重大變更時才會再次執行完整集群。`playbooks/shipping.md` 中的 `patch-id` 規則可用於沿用分道（Lane）的驗證結果，但每一個新的 Head 提交都必須取得屬於它自己的綠燈 CI。

1. **操作者（Operator）的關卡優先。** 自治授權僅涵蓋佇列中的項目，因此操作者指名為自己負責的項目以及佇列以外的 PR，一律在達到「可合併（merge-ready）」狀態時停下等待。當操作者要求你「先說明計畫」時，代表尚未授權動工。此外，`AGENTS.md` 規定的人工授權紅線（關閉 `LAH-API` 的 `MOCK=true`、對 Oracle 執行破壞性 SQL、安裝/移除套件、修改 `.env`、執行 `nuxtron build`）一律視為最高優先級的操作者關卡。
2. **為每個 PR 透過 `invoke_subagent` 孵化一位專屬負責人（Owner），並將其工作狀態保存在接替者能隨時找到的位置。** 為整個計畫解析一次程式碼託管平台工具（Forge）：預設使用 GitHub CLI（`gh`）；若 `command -v origin` 成功且 Origin 能解析該儲存庫，則所有 PR 操作皆使用 `origin pr`；否則維持使用 `gh` 並記錄降級原因。絕不強制依賴 Graphite（`gt`）。在 LAH-Workspace 中，務必先確認目標變更屬於哪一個獨立 Git 儲存庫（根目錄、`LAH-API`、`LAH-FE`、`lah-messenger-server` 或 `lah-messenger`）。每位負責人是一個透過 `invoke_subagent` 啟動的子代理，負責建構功能、依據 `playbooks/opening-a-pr.md` 開立 PR、在真實交付物上驗證變更、依據 `playbooks/babysit.md` 照看 PR 直到綠燈，並在步驟 4 與步驟 5 放行後執行合併。

   請盡早開立 PR，讓 CI 與審查機器人能與開發工作同步執行。程式碼唯有在完成去贅字與清理檢查（移除多餘調試與垃圾代碼，對應 `/deslop` 概念）以及 `/no-comments`（保留既有無關註解、僅清理新增區塊之無意義敘事註解）之後，才算真正就緒（code-ready），以確保完整驗證集群是在完稿的程式碼上執行。接著在自我實證前，先 Rebase 到最新的主幹（Trunk）並回報 code-ready Head SHA，讓驗證能在修補程式最終降落的基底上進行。此後每產生一個新的 Head 都要回報，並在自我實證、CI 與 Babysit 皆完成後回報 merge-ready。除非主幹發生衝突或導致 CI 損壞，否則修復回合應維持在同一個基底上，因為每次 Rebase 都會重新觸發 CI。在推送 code-ready 版本以及後續需要驗證器介入的推送之前，請先在已提交的 Head 上針對受影響的路徑執行該子專案的語法與 Lint 檢查（如 `php -l`、`node -c`、`yarn lint`）。

   請始終假設執行環境或子代理隨時可能中斷。動工後請盡快推送分支，並依據 **show-me-your-work**（`../show-me-your-work/SKILL.md`）技能在根代理的儲存區（如 `<appDataDir>\brain\<conversation-id>`）啟動決策軌跡紀錄，此後每完成一個值得保留的工作單元就推送一次。凡是透過 `invoke_subagent` 孵化子代理的代理，都必須在該儲存區記錄子代理的 Conversation ID、當前狀態，以及根據過往同類任務估算的「逾時卡死門檻（stuck-after runtime）」，以便在父代理中斷時由根協調者進行探測。僅允許對你自己的分支進行強制推送，且必須使用 `--force-with-lease` 鎖定你最後一次推送或接手的 SHA；若發現分支上有任何非你本人推送的提交，請立即停止並向根協調者回報。
3. **讓各個負責人從主幹平行分出分支運作，絕不互相堆疊（Stacked），** 確保每個 PR 都能獨立合併上線。
4. **執行一次驗證集群（Swarm-verify once）。** 在 code-ready Head 上執行一次完整的驗證集群。唯有新增行為、重新設計或出現大規模的新 Diff 時，才再次啟動完整集群。單純的 Rebase、解決合併衝突或小幅修復，僅需在新的 Head 上指派單一驗證子代理。請依據 **swarm**（`../swarm/SKILL.md`）技能，針對 code-ready SHA 平行扇出多個獨立驗證子代理（`invoke_subagent`）。它們會重新執行各項檢查關卡、透過對應的控制技能（如 `chrome-devtools` 或終端控制）在真實介面上實證核心行為，並稽核 Diff。若缺少真實環境實測分道（Live lane），或在你親自稽核 merge-ready 報告所附的憑證（Receipts）之前，裁決都不得算作通過（CLEAN），因為任何分道都不會盲信未經親自查驗的宣稱。

   不論驗證分道將問題標記為何種等級，請將每一項經證實的發現整合為單一批次的向前修復指令（Fix-forward）交還給該 PR 負責人，並要求針對所有具備相同缺陷的位置補上「先紅後綠」的測試。若某個缺陷在不包含該 PR 的主幹上就已經存在，則將其記錄為主幹既有問題，不作為該 PR 的卡關條件；但若該缺陷是被此 PR 複製擴散或因新路徑而觸發的，則屬於該 PR 必須解決的責任。切勿親自推送修復到負責人的分支上，因為每個分支只能有一位寫入者。若負責人卡死，請直接孵化新的子代理接替它。
5. **負責人僅能合併經過你驗證、且在即將降落之主幹上測試通過的程式碼。** 單憑 CI 綠燈絕不構成合併授權。一旦驗證集群的分道開始執行，合併準備階段（Merge prep）就會先 Rebase 到最新主幹、回報新的 Head，並等待 CI 綠燈。

   在即將執行合併的正前方，先 Fetch 最新主幹並評估主幹上的新變更是否可能影響此修補程式（因為若主幹每動一次就無腦 Rebase，將會陷入永無止境的重跑循環）。當即將合併的最終程式碼組合從未被測試過時（例如發生衝突、雙方修改了同一個檔案，或變更了該 PR 觸發的檢查項目），必須執行 Rebase 並等待 CI。若雙方僅同時修改了 Lockfile，當在合併結果上執行鎖定版本的安裝（Frozen install）能夠通過、且該 PR 修改的套件在合併結果中的解析版本與 Head 完全一致時，則無須 Rebase（因為該次安裝已實測了即將降落的 Lockfile；若安裝失敗，則代表必須透過 Rebase 修復）。當主幹修改了此修補程式的呼叫端，或修改了此修補程式所依賴的項目（例如它呼叫的函式、跨專案 API 契約或相依套件版本）時，請在合併結果上執行此修補程式的檢查測試，通過後即可合併。其餘情況直接合併。若主幹的變動迫使在合併準備階段之後還得進行第三次 Rebase，請暫停並向根協調者回報，由根協調者重新排程發生碰撞的工作。
6. **運作根協調層（Run the root layer）。** 任何放寬檢查關卡的做法（例如調高資源預算或加入白名單）都必須先有驗證子代理的實證，再由你親自重新副署（Countersign），因為 PR 負責人本身有追求綠燈的利益衝突。在涵蓋核准權限的自治授權下，你的副署即代表核准，而負責人的紀錄必須指向你的副署以供驗證分道查核。任何被停用或改為軟性失敗（Soft-failed）的檢查都必須被揪出來恢復，因為它停止了對所有案例的守門作用。絕不擅自給予或繞過程式碼託管平台強制要求的審查核准，因為沒有任何副署能取代平台強制規範。

   在收到操作者的動工指令後，透過 `schedule` 工具設定每小時一次的定時稽核（對應 `/loop 1h`），持續稽核直到所有委派工作皆完成為止，因為長時間執行的任務容易發生漂移，且子代理可能會靜默卡死。每次定時觸發（Tick）時，都會從主幹重新讀取本劇本並修正漂移（例如未回報的 Head 或未登記的子代理，要求其負責人補齊紀錄，因為漂移代表紀錄缺口而非單純停滯）。它會一路向下探測每一個子代理（透過 `manage_subagents` 的 `list` 動作與檢查決策軌跡）直到最底層的分道，並純粹根據「實際副作用（Side effects）」來評判進度，因為狀態文字與摘要報告可能會掩蓋已經卡死的子代理。當子代理發生錯誤、無法啟動回合，或超過其「逾時卡死門檻」仍無任何新產出時，即判定為卡死；在第一次定時檢查時既未推送分支也未寫入任何決策軌跡列的負責人，同樣視為卡死。正在等待你或操作者回覆的子代理不算卡死，請直接回應它。一旦發現卡死的子代理，請立即透過 `manage_subagents`（`Action: "kill"`）終止並孵化新代理接替，無須乾等舊代理自行收尾。若該次定時檢查發現了任何對操作者有意義的狀態變化，請在回合結束時依據 **ketchup**（`../ketchup/SKILL.md`）技能向操作者匯報最新進度；若無任何變化則保持安靜。
7. **收到操作者的停止指令時立即全數待命（Stand down）。** 暫停指令會以「零寫入命令（Zero-writes order）」傳達給每一位負責人。每位負責人必須立即回報當前位置並妥善保存其任務簡報，直到操作者解除暫停為止。

**回覆（Reply，強制使用台灣繁體中文）：** 依據 **ketchup** 技能向操作者進行進度總結，涵蓋每個 PR 的狀態與驗證裁決、已合併項目、副署放行項目及其原因、待操作者裁決的關卡，並附上每個 PR 與決策軌跡的連結。
