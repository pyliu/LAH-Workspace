# 基礎優先思維（Foundational Thinking）

**結構性決策**旨在保護未來的選擇權（Option Value）；**程式碼層級的決策**則旨在保護簡潔性。

**資料結構優先。** 在動手寫邏輯之前，先把資料的結構（Data Shape）定好。及早定義核心型別、梳理每一種資料存取模式，並選擇最契合主要執行路徑的資料結構。

在程式碼層級，請對「結構」保持 DRY（不重複），而非強求每一行程式碼都不重複。型別與資料模型應該收斂統一；但三行相似的敘述仍然勝過一個過早抽出的抽象層。寧可直白明確，也不要賣弄奇技淫巧。測試應針對行為與邊界條件，而非追求行數指標。

**並行處理推論（Concurrency Corollary）：** 在不同的執行單元（Actors）之間共享狀態前，先問自己：「如果另一個執行單元同時修改這份狀態，會發生什麼事？」如果答案不是「完全沒影響」，就必須進行隔離。

**基礎鷹架優先（Scaffold First）。** 如果某項工作能讓後續每一個階段都受益，請最先執行它。問自己：「接下來的每個階段是否都會因為這個機制的建立而受惠？」CI、Lint 檢查、測試基礎設施以及共用型別都屬於基礎鷹架。請為了最大化選擇權來安排順序：環境建置先於功能開發、測試先於修復。每次提交（Commit）應保持小巧且目的單一。

每一次增量修改都應該落地一個內聚的抽象概念，或是深化既有的抽象，而不是把新功能當作特例協調邏輯散佈到各個呼叫端。

減法先於打地基：先移除無用的死碼（Dead Code），再鋪設基礎建設。
