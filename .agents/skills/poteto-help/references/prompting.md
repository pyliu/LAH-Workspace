# 如何撰寫優質提示詞（Prompt）

一個好的提示詞只需清楚陳述「意圖」與「完成檢查條件（Done Check）」。劇本（Playbook）會自動提供執行步驟，因此幾句直白清楚的繁體中文句子，遠勝過冗長的規格書。

## 應該包含的要素

- **目標（Goal）**：說明哪裡出了問題，或使用者想要達成什麼結果。
- **完成檢查條件（Done Check）**：必須是可以明確判定「通過」或「失敗」的條件。「把它改好一點」或指定執行時間長度都不是有效的檢查條件。
- **需要展示的證據（Proof）**：要求提供真實的終端機指令輸出、操作流程錄影、實際寫入資料庫或快取的值，或是修改前後的量化數據對比。
- **已知資訊**：提供症狀、重現步驟、錯誤日誌或相關檔案連結，能替 Agent 省去盲目搜尋的時間。
- **明確的限制條件**：例如「先重現問題（repro first）」、「先不要修改任何程式碼」、「零行為變更（zero behavior change）」、「在繼續實作前先讓我審查」等，每一項都會直接改變 Agent 的執行策略。

## 應該省略的內容

- **實作細節（How）**：告訴 Agent 要達成什麼結果，並保留空間讓它找出更好的實作方式。
- **手動列出技能或步驟清單**：手寫的執行順序往往會遺漏或打亂劇本原本保留的嚴謹步驟。只有在需要強制覆寫某個特定選擇時，才直接點名技能。
- **使用者自己猜測的原因**：在 Agent 用自己的話重新陳述問題之前，先不要給出你的猜測。過早提出的假設會窄化 Agent 的搜尋範圍。

## 先載入脈絡

- **面對雜亂的回報時**：要求 Agent 在做任何事之前，先用自己的話與白話文重新陳述底層核心問題（或使用 `/in-your-own-words`）。這樣在寫下任何一行程式碼前就能發現理解偏差。
- **開啟新對話時**：先使用 `/recall` 回顧先前在該主題上的工作脈絡。舊對話中往往保存了新 Agent 所缺乏的關鍵背景。
- **修改不熟悉的程式碼前**：先用 `/how` 了解運作機制，再用 `/why` 了解設計原因。沒有建立完整心理模型的 Agent，很容易在第一個看似合理的地方只治標不治本。
- **要求論證**：使用 `/teach` 要求 Agent 為某個設計選擇提出論證，例如「說服我這個改法修復的是根本原因而非表面症狀」。檢驗論證永遠比檢驗摘要更容易。

## 先設計原型，再擬定計畫

- **絕不直接採納第一個設計**：要求針對幾個候選方案建立原型（若是 UI 變更則附上截圖或錄影），根據實際證據來挑選。
- **讓原型回答未知問題**：不要對著抽象的書面計畫進行紙上談兵的挑刺，因為審查者往往會憑空想像出實務上根本不會發生的風險。
- **開發共用套件或 API 時**：要求先寫好 README 或使用教學，再反推回程式碼實作。這份文件會成為 Agent 自我檢驗的明確標靶。
- **設計定案後才要求擬定計畫**：計畫中的每一個步驟都必須以一個可驗證的檢查條件作為結尾。

## 簡短的後續追問

- 一旦對話已經載入任務脈絡，「開始執行（do it）」、「繼續（continue）」、「一路做到完成為止（keep going until done）」本身就是完整有效的提示詞。
- 當主題轉換時，請以「新任務（new task）」開頭；否則模式會把新訊息當成上一個任務的下一步。

## 離開座位前（長時自動化任務）

- 明確告知「我要去睡了」或「我要離開座位一下」，讓 Agent 停止中途詢問。
- 將「完成條件」寫成每一輪迭代都能自動執行的檢查指令，並可搭配 `/goal` 或 `schedule` 工具持續推進。
- 若有平行修改需求，要求在獨立分支工作樹（Workspace branch/share）中進行。
- 預先回答 Agent 可能會停下來詢問的事項（例如「在滿足檢查條件前請持續推進，不需每步詢問」；但注意 LAH 系統紅線操作仍須遵守 `AGENTS.md` 授權規範）。
- 要求保留決策紀錄（Decision Log，參見 `/show-me-your-work`）以便事後稽核。
- 設定退場機制：「如果嘗試幾小時後真的卡住無法突破，請停下來並寫清楚卡住的原因。」

## 用一句話精準引導（One-Line Steer）

- **重申目標**：「我說過目前的目標是先重現問題，我還沒要求你修復。」
- **點名原則**：「套用 prove it works 原則。給我看真實的執行輸出，而不是只有建置日誌。」
- 直接點名原則之所以有效，是因為 Agent 已經讀過該規則，它的回覆會明確指出該原則改變了哪個決策。
