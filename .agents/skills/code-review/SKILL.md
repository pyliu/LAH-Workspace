# 雙軸程式碼審查 (Code Review)

對 Git Diff 進行嚴格的雙軸並行審查。

---

## 為什麼要雙軸審查？

一項程式碼修改可能在其中一個維度表現完美，卻在另一個維度完全失敗：
- 程式碼完全符合規範、乾淨優雅，但做出的行為根本不是需求要的 ➔ **規範通過、規格失敗**。
- 程式碼完美滿足需求，但到處充滿複製貼上、缺乏防護與壞味道 ➔ **規格通過、規範失敗**。

將兩者分開審查，能防止任一軸向的優點掩蓋另一軸向的重大缺失。

---

## 審查流程

### 1. 取得變更與比對基準
- 取得待審查之 Diff 與 Commit 清單（如 `git diff main...HEAD` 或工作區既有修改）。
- 尋找對應之規格文件（Spec / PRD / 票券說明）。

### 2. 軸一：規範與壞味道審查 (Standards Axis)
檢查是否違反專案文件（`AGENTS.md`、`CODING_STANDARDS.md`、Lint 規範）以及常見壞味道：
- **命名模糊 (Mysterious Name)**：變數或函式名稱無法揭示真實意圖。
- **重複程式碼 (Duplicated Code)**：相同或高度相似邏輯重複出現。
- **依戀情節 (Feature Envy)**：方法過度存取其他物件的內部資料。
- **過長參數列 / 資料泥塊 (Data Clumps)**：多個參數總是綁定在一起傳遞。
- **基本型別偏執 (Primitive Obsession)**：應用領域概念卻使用未經驗證的裸字串或數值。
- **散彈式修改 (Shotgun Surgery)**：單一改動被迫在多處散落修改。
- **過度發想 (Speculative Generality)**：加入當前需求不需要的抽象或介面。

### 3. 軸二：規格符合度審查 (Spec Axis)
比對變更與規格書（Spec）：
- **遺漏需求**：規格有要求但 Diff 沒實作。
- **範圍蔓延 (Scope Creep)**：Diff 包含了規格以外的未授權變更。
- **邏輯錯誤**：看似實作但實際運作與規格相反或有誤。

### 4. 輸出報告結構

```markdown
# 程式碼審查報告

## 1. 工程規範與壞味道 (Standards)
- [檔案與行號]: 發現項目說明（標註為硬性違規或架構建議）。

## 2. 規格相符度 (Spec)
- [規格條款]: 遺漏、偏差或範圍蔓延之具體說明。

## 3. 審查摘要結論
- 規範軸：通過 / 需修正 (X 項缺失)
- 規格軸：通過 / 需修正 (Y 項缺失)
- 最需優先改善的核心問題建議。
```
