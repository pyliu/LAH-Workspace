# Recall（工作脈絡回顧與重建）

> **輸出語言規範**：所有回顧簡報、狀態摘要、問題分析與下一步建議，**一律強制使用台灣繁體中文輸出**。

**在開始或接續工作之前，重建使用者近期的工作脈絡，並交還一份精煉的現況膠囊簡報（Capsule），說明目前進度停在哪裡以及接下來該做什麼。**

保持簡潔並聚焦主題。僅讀取範圍內討論串所需的資訊，完成後立即停止。

你的工作脈絡保存在兩份紀錄中：
1. **你自身的對話歷史紀錄（Chat Transcripts）**：保存了你做過什麼以及做過哪些決策。
2. **共用紀錄（Shared Record）**：保存了圍繞同一段程式碼、但以其他名稱發生的所有事件——使用者持續回報的症狀、曾部署上線卻又被還原（Revert）的修復、正式環境仍在觸發的錯誤等。這第二份紀錄正是 **why** 技能跨越版本控制（Git）、議題追蹤系統、討論頻道、長篇文件與錯誤追蹤系統所搜尋的目標。一個帶有長尾臭蟲的功能，其大半故事都留在共用紀錄裡，因此切勿僅憑對話紀錄就試圖重建全貌。

在 Antigravity 環境中，對話紀錄位於 `<appDataDir>\brain\<conversation-id>\.system_generated\logs\transcript.jsonl`（以及完整版 `transcript_full.jsonl`），其中 `<appDataDir>` 為 `C:\Users\<user>\.gemini\antigravity`。每一行代表對話中的一個步驟（Step）JSON 物件。請先讀取精簡版 `transcript.jsonl`，當發現 `truncated_fields` 欄位時，才讀取 `transcript_full.jsonl` 中對應的行號。

## 執行步驟

1. **先分類，再分流（Classify, then route）**：
   - 若是要接手「某一個特定的先前對話或分支」，應使用 `session-pickup` 劇本，而非本技能。
   - 若是要將工作習慣轉化為長期技能，應使用 `automate-me`。
   - 若只是要產出供他人閱讀的工作成果摘要，則是另一項任務。
   - **Recall** 的職責是在你採取行動前，跨近期多個對話載入工作脈絡。如果使用者已經給了你完整的狀態膠囊（檔案路徑、分支、變更內容），請直接使用並略過挖掘步驟。

2. **搜尋前先鎖定範圍（Lock the scope）**：
   - 明確界定時間範圍（「近期」必須是具體範圍，預設為最近 7 天）、指定的主題（若有提及），以及工作區（預設為當前工作區；未經要求，絕不讀取其他專案的對話紀錄）。
   - 向使用者回報確認你鎖定的範圍。絕不暗中將「全部（all）」縮減為「最近 N 筆」。

3. **平行展開對話歷史挖掘（Fan out across chat history）**：
   - 透過 `invoke_subagent`（設定 `TypeName: "research"`、`Model: "inherit"`）啟動平行子代理，每個子代理負責一部分對話紀錄。
   - 指示每個子代理：務必依檔案真實修改時間排序候選對話，切勿依 UUID 名稱排序；先搜尋主題關鍵字，再僅讀取匹配的對話及其相關區段；略過當前對話以及明顯的雜訊（子代理對話、評估與測試對話）。
   - 每個子代理針對每個匹配的對話回傳相同的結構區塊：主題、使用者目標、已做決策、未完討論串（Open threads）、遇到的卡關與修正，以及產出物（PR、工單、分支、修改檔案），並標註對話 UUID（`<conversation-id>`）。
   - 若僅有一兩個對話，請略過平行展開，直接搜尋即可。原始對話紀錄留在子代理中，主對話僅接收整理後的發現。

4. **當主題指明特定功能、檔案、子系統、領域或臭蟲時，同步掃描共用紀錄（Sweep the shared record）**：
   - 這是預設行為，而非自由裁量；即使使用者說「我在 X 的工作（my work on X）」也不例外。
   - 將此任務交給 **why** 技能的來源調查員（透過 `invoke_subagent` 的 `TypeName: "research"`），但將調查問題從「為什麼當初這樣設計」轉向「目前的現況為何、曾經嘗試過哪些失敗或被還原的作法、以及使用者仍在回報什麼問題」。
   - 重用 **why** 的各來源調查劇本，讓調查員與對話歷史挖掘平行執行，並繼承其原則：每個資料來源配置一個調查子代理、查無結果（Null results）本身也是重要發現、若某個 MCP 未啟用則略過並明確說明。將回傳結果整合進簡報中。
   - 唯有在沒有指名目標的純活動回顧（例如「我這週做了什麼」），才略過此步驟（此時你自身的歷史與即時狀態就是全部答案）。

5. **對照即時系統狀態進行驗證（Verify against live state）**：
   - 取出挖掘與掃描所浮現的 PR、分支、Commit 與工單，使用 `git`（注意 LAH-Workspace 各子專案為獨立 Git 儲存庫，需確認對應目錄）進行實地檢查。
   - 當答案取決於某個 Agent 實際執行過的操作（呼叫過的工具、讀取過的檔案、遇到的錯誤）時，請讀取完整的對話紀錄（包含 `transcript_full.jsonl` 中的對應步驟），而不僅是截斷後的摘要。

6. **依下方輸出契約撰寫簡報（Write the brief）**：
   - 依討論串（Thread）分組，並嚴格聚焦於指定主題。

## 輸出契約（Output Contract）

請依序呈現：**現況膠囊（Capsule）** → **工作討論串狀態（Threads）** → **待解問題（Problems）** → **下一步行動（Next move）**。更深入的細節請放在下方或直接刪減。

- **現況膠囊（Capsule）**：至多 5 點條列。說明這項工作是什麼，以及目前的整體進度。
- **工作討論串（Threads）**：每項一行，開頭必須加上以下唯一一個狀態標籤：`[已合併 #N]`、`[開啟中 PR #N]`、`[進行中 <branch>]`、`[已驗證，未提交]`、`[已還原 #N]` 或 `[已規劃，未開始]`。沒有標籤的項目代表尚未完成，請務必為其標上正確狀態。
- **待解問題（Problems）**：至多 5 項反覆出現的核心問題。包含使用者持續回報的症狀，以及任何曾部署卻被還原的修復嘗試，讓下一次嘗試能從上次失敗的地方精準接續。
- **下一步行動（Next move）**：單一且最具體、最有價值的下一個動作。

除非相鄰的功能或工單直接阻擋了本項目，否則請將其排除在外。當膠囊簡報與討論串列表超過一個畫面的長度時，請優先刪減細節而非刪減討論串。請透過 **unslop** 技能精煉文字，引用對話發現時標註對話 ID（`[label](conversation://<conversation-id>)`），引用共用紀錄時標註來源（PR 編號、Commit Hash、工單 ID 等），並在產生任何公開輸出前清理敏感私密資訊。

**回覆格式**：嚴格遵循上述輸出契約的繁體中文簡報。
