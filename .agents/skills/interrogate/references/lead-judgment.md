# 主審官裁決框架（Lead Judgment Framework）

## 過濾原則（Filtering Principles）

### 吹毛求疵引力（Nitpick Gravity）

審查者——尤其是被賦予對抗性任務的審查者——往往會傾向把版面填滿。如果他們找不到真正致命的問題，就會把細枝末節的小瑕疵（nits）放大來充數。如果某位審查者提出的發現全都是微小的排版或個人風格偏好，代表這段程式碼本身大概沒什麼問題——請直接在裁決中點出這一點。

### 假設性問題 vs 真實問題（Hypothetical vs. Actual）

「如果有人在這裡傳入 `null` 會怎樣？」唯有在呼叫端**真的有可能**傳入 `null` 時，才算是一個有效的發現。請親自追蹤呼叫點（call site）：如果輸入在上游就已經完成驗證，或者型別系統根本不允許傳入 `null`，請直接駁回（Dismiss）該發現。只看 Diff 的審查者不一定看得到完整的呼叫鏈，但你可以。

### 警惕過早抽象化（Premature Abstraction Warnings）

審查者經常建議抽離函式、新增介面（interfaces）或建立抽象層。請先自問：這段程式碼現在真的有第二種變化方向的需求嗎？如果沒有，這個抽象化就是過早的。能正常運作的簡單內嵌（inline）程式碼，遠勝過對當前範圍而言小題大作的「完美抽象層」。

### 「換作是我會用別種寫法」（"I Would Have Done It Differently"）

這是程式碼審查中最常見的偽陽性（false positive）。一個本質上只是在說「我個人比較喜歡另一種做法」的審查意見，既不是 Bug、也不是設計缺陷，除非審查者能證明目前的做法存在具體問題，否則根本不具備行動價值。請直接駁回這類意見，並說明原因。

### 缺乏上下文的訊號（Missing Context Signals）

留意那些暴露出審查者不了解專案脈絡的發現：
- 建議修改作者根本沒有撰寫或觸碰到的既有無關程式碼。
- 把與整個程式碼庫慣例完全一致的模式標記為問題（只是因為審查者不知道那是專案慣例）。
- 建議的做法與你已知的系統約束條件（如專案架構邊界或舊版相容性限制）相衝突。

這些都是審查者在資訊有限的情況下犯的無心之過。請優雅地予以駁回並簡述脈絡。

## 當審查者說對了的時候（When Reviewers Are Right）

切勿僅因為某個審查意見讓人不舒服或改起來很麻煩就將其駁回。對抗性審查的全部意義，就在於抓出你自己會漏掉的盲點。當出現以下徵兆時，代表該發現值得高度重視：

- **多個審查者各自獨立標記了同一個問題**（共識訊號 consensus signal）。
- 該發現指出了**具體的執行路徑**，而非空泛的假設。
- 該發現揭露了你對這段程式碼心智模型中的缺口。
- 你讀完該發現後，心想：「……對耶，還真的是這樣。」

對於**資安漏洞（security findings）**與**正確性錯誤（correctness bugs）**，在考慮駁回時請務必加倍謹慎。即使這類問題只由單一審查者提出，也值得你花更多心力深入查證。
