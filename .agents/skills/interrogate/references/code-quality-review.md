# 程式碼品質審查透鏡（Code Quality Review）

每位審查者除了套用審查標準（Rubric）之外，還必須套用本程式碼品質透鏡。這是一套嚴格的標準，專注於實作品質、可維護性、抽象層品質與程式碼庫的整體健康度。

最重要的是：**對程式碼結構抱持高度企圖心**。不要只停留在挑出局部的整潔問題，請積極尋找「程式碼柔道（code judo）」招式——也就是那些在不改變行為的前提下，能讓實作變得大幅簡化、更短小、更直接且更優雅的結構重組方式。

## 核心提示詞（Core Prompt）

請從這個基準態度出發：

> 對當前分支的變更進行深度的程式碼品質稽核。
> 重新思考如何組織與實作這些變更，在不影響既有行為的前提下，實質提升程式碼品質。
> 致力於改善抽象層、模組化、減少義大利麵條式程式碼（Spaghetti code），並提升精煉度與可讀性。
> 抱持高度企圖心：如果有一條清晰的路徑能透過重組部分程式碼來改善實作，請大膽提出。
> 保持極度徹底與嚴謹。三思而後行（Measure twice, cut once）。

## 審查維度（Dimensions）

每個維度各陳述一次，請套用與當前變更相關的維度：

0. **對結構簡化抱持高度企圖心**：不要只停留在「這裡可以再乾淨一點」。尋找能夠讓整條分支、輔助函式、模式、條件判斷或分層直接消失的重新定框（reframing）方式。假設通常都存在某個「程式碼柔道」招式，能更有效地運用既有架構，讓變更大幅簡化。如果你能直接刪除複雜度，而不是把複雜度搬來搬去，請強力主張刪除它。

1. **除非有極為強烈的理由，否則絕不允許一個 PR 將檔案從 1,000 行以下推升至超過 1,000 行**：請將此視為強烈的壞味道（code smell）。優先選擇抽離輔助函式、子元件或獨立模組。如果 Diff 跨越了這個門檻，請質問是否應該先拆解程式碼。唯有在具備極具說服力的結構理由、且產出的檔案依然條理分明時，才可破例。

2. **絕不允許既有程式碼長出義大利麵條式的糾纏（spaghetti growth）**：對新加入的臨時條件判斷（ad-hoc conditionals）、散落各處的特例處理，或硬塞進無關流程中的一次性分支保持高度警覺。將「在隨機地方出現的詭異 if 判斷」視為設計問題，而非單純的排版瑕疵。優先將邏輯推入專責的輔助函式、狀態機或獨立模組中，而不是讓既有路徑變得更加糾結。

3. **傾向於清理設計本身，而不只是接受「能動就好」的程式碼**：如果行為維持不變，但結構可以變得乾淨許多，請主張採用更乾淨的版本。優先選擇能減少活動零件（moving pieces）的簡化方案，而非只是把相同的複雜度分散到不同地方的重構。

4. **偏好直接、無聊、好維護的程式碼，拒絕取巧（hacky）或黑魔法（magical）般的程式碼**：將脆弱、臨時拼湊或依賴「黑魔法」的行為視為問題。對那些隱藏了簡單資料結構假設的過度通用機制保持懷疑。標記那些只增加了間接層、卻沒有換取任何清晰度的淺薄抽象層、純轉發包裝器（identity wrappers）或穿透輔助函式（pass-through helpers）。

5. **當型別與邊界整潔度影響可維護性時，嚴格把關**：當可以建立更清晰的型別邊界時，請質疑不必要的選填屬性（optionality）、`unknown`、`any` 或充斥強制轉型（cast-heavy）的程式碼。偏好明確定義型別的模型，而非結構鬆散的臨時物件。如果某個分支依賴靜默的預設退回值（silent fallback）來粉飾不清楚的不變量，請質問是否應該將邊界明確化。

6. **將邏輯留在正統（canonical）的分層中，並重用既有的輔助工具**：指出洩漏到共用路徑中的功能專屬邏輯，或透過 API 洩漏出去的實作細節。優先重用既有的正統工具函式，而非自己重造一次性的輪子。將程式碼推向正確的套件、服務或模組，切勿將架構漂移（drift）常態化。

7. **當更乾淨的結構顯而易見時，將不必要的循序編排（sequential orchestration）與非原子更新視為設計壞味道**：如果彼此獨立的工作毫無理由地被序列化執行，請質問是否應該平行執行；如果相關聯的更新可能讓狀態停留在只套用一半的階段，請主張採用更具原子性（atomic）的結構。不需要對微觀最佳化吹毛求疵，但務必標記那些可以避免、且會讓程式碼變得更脆弱的編排複雜度。

## 輸出期望（Output Expectations）

請依序優先排列：第一優先是結構性的程式碼品質退化與錯失的簡化機會；其次是義大利麵條式糾纏與分支複雜度；接著是邊界、型別與檔案大小問題；最後才是較小的模組化與可讀性問題。

## 核准門檻（Approval Bar）

切勿僅因為行為看起來正確就給予核准。除非作者能提出充分理由，否則請將以下情況視為預設的阻擋合併問題（presumptive blockers）：當一個「程式碼柔道」招式就能消除大量附帶複雜度時，PR 卻保留了這些複雜度；將檔案從低於 1,000 行推升至超過 1,000 行；新增糾纏既有流程的臨時分支；在共用程式碼中到處散落功能檢查；新增不必要的抽象層、包裝器或充斥轉型的契約；或者在明明有正統歸屬分層與既有工具時，卻重複造輪子或把邏輯放錯分層。若踩中上述條件，請給出明確、可操作的回饋，並要求更乾淨的結構拆解。

## 審查語氣（Review Tone）

對品質保持直接、嚴肅且高標準的要求。不要無禮，但絕不要把重大的可維護性問題軟化成溫和的建議。如果這段程式碼正在讓程式碼庫變得更混亂，請直接明講；如果實作錯過了一個顯而易見的大幅簡化機會，也請直接指出來。當真正的問題出在結構上時，不要只滿足於提出「也許可以把這個變數改個名字」這類表面建議。
