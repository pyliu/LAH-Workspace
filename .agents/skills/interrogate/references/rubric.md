# 審查標準（Review Rubric）

請透過以下任何與當前變更相關的透鏡角度進行審查。並非每個角度都適用於每一次變更。

## 1. 正確性（Correctness）

這段程式碼實際執行的結果，真的符合變更意圖所宣稱的行為嗎？

- **邊界情況（Edge cases）**：空輸入、`null` / `undefined`、邊界值、並行存取（concurrent access）。
- **錯誤處理（Error handling）**：錯誤是否有被妥善捕捉、向上傳遞，還是被靜默吞掉了（silently swallowed）？
- **數值與編碼細節**：差一錯誤（off-by-one）、隱式型別強制轉換（type coercion）、整數溢位、字串編碼問題。
- **狀態管理（State management）**：競爭條件（race conditions）、過期的閉包（stale closures）、懸空參照（dangling references）。
- **快樂路徑與錯誤路徑**：正常路徑（happy path）與異常路徑（sad path）是否都能正確運作？
- **冪等性（Idempotency）**：如果這個操作被執行兩次，或者上一次執行到一半崩潰了，會發生什麼事？如果答案是「取決於上次留下了什麼殘留狀態」，代表缺少了狀態調和（reconciliation）步驟。
- **並行控制（Concurrency）**：如果多個行為者可能同時觸碰同一份可變狀態（檔案、分支、共用資料表），存取是否有在結構上被序列化（鎖、循序階段、獨佔所有權），還是僅靠根本維持不住的口頭約定？

當你發現潛在的 Bug 時，請實際追蹤執行路徑。不要只標記「這裡可能是 null」，請展示會讓它變成 `null` 的完整呼叫鏈。

## 2. 根本原因 vs 表面症狀（Root Causes vs. Symptoms）

這段程式碼是在解決真正的問題，還是只是在粉飾表面症狀？

回答這個問題通常需要看穿修改檔案之外的脈絡。請閱讀周邊程式碼（呼叫端、被呼叫端、型別定義、同層模組），理解這項變更所處的整體架構。善用你手邊的唯讀工具（檔案檢視、搜尋）追蹤呼叫鏈、閱讀型別，並在判斷變更是否改對分層之前，先理解既有程式碼為何存在：

- 掩蓋了更深層不變量違規（invariant violation）的防衛性判斷（guard clauses）。
- 掩蓋了損壞契約的重試邏輯（retry logic）。
- 讓資料建模錯誤消音的強制轉型（type casts）。
- 權宜解法（workaround）：為什麼需要它？真正的正統修復應該長什麼樣子？
- 寫在模組 A 裡面的修復，其實應該是模組 B 介面契約的修復。
- 用文字指示取代結構約束：如果修復方式是寫一行註解說「切勿做 X」或是要讓人記住某個慣例，請質問是否能改用型別約束、Lint 規則或執行期檢查，讓錯誤的做法在結構上根本不可能發生。

## 3. 結構完整性（Structural Integrity）

這段程式碼是否能良好地融入它所屬的系統中？

- **邊界紀律（Boundary discipline）**：資料驗證是否集中在系統邊界，還是散落在商業邏輯各處？資料應在進入系統的邊界驗證一次，進入內部後即信任其型別。
- **抽象層級（Abstraction level）**：程式碼是否把高階流程編排（orchestration）與低階實作細節混雜在一起？
- **耦合度（Coupling）**：這項變更是否引入了會讓未來修改變得更加困難的依賴關係？
- **資料模型契合度（Data model fit）**：資料結構是否符合實際的存取模式（access patterns）？
- **外掛硬釘 vs 原生整合（Bolted-on vs. integrated）**：如果這個新需求從第一天就已知，程式碼會長這樣嗎？還是這項變更看起來像硬貼在既有設計上的補丁？
- **遺留雙重路徑（Legacy dual-paths）**：變更是否引入了新 API 卻同時保留舊 API？如果沒有外部消費者，請在同一次變更中遷移所有呼叫端並刪除舊路徑，不要留下最終會變成永久包袱的相容層。

切勿因為簡單的程式碼沒有抽象層就扣分——過早抽象化比重複程式碼更糟。

## 4. 可驗證性（Verification）

光靠閱讀這段程式碼與測試，你能確定它真的能正常運作嗎？

- 是否有測試？測試的是外顯行為（behavior）還是內部實作細節？
- 是否有能捕捉退化（regressions）的斷言或不變量檢查？
- 如果是 Bug 修復：是否有針對該 Bug 的重現測試？
- 如果觸及整合邊界：完整路徑是否有被測試涵蓋？
- **檢查真實標的，而非替代指標（proxy）**：如果程式碼只透過檔案修改時間（mtime）或快取狀態來檢查存活，而不是讀取實際數值，這就是一個驗證缺口。
- **針對委派或非同步工作**：程式碼是否驗證了實際產出的產物（artifacts），還是盲目信任子代理的自我回報與摘要？

## 5. 複雜度預算（Complexity Budget）

這段程式碼所達成的效果，值得它所引入的複雜度嗎？

- 可以在不犧牲正確性與清晰度的前提下寫得更簡單的程式碼。
- 只服務單一呼叫點的抽象層。
- 為了目前根本還不存在的情境所設計的設定項或參數化。
- 死碼（dead code）、未使用的匯入（unused imports）、殘留無用的參數。
- 過度工程（Over-engineering）：目前沒有任何呼叫端的「以防萬一（just in case）」程式碼路徑。
- 為了過渡期穩定性而保留、如今已不再需要的過時相容路徑——如果遷移已完成，請拆除鷹架。
- 使用者體驗是否值得這樣的複雜度？每一個功能、控制項與選項都必須證明自己的存在價值；半成品功能比沒有功能更糟。

**越簡單越好，除非簡單會導致錯誤。**

## 6. 資安（Security）

針對每一項資安發現，請追蹤輸入資料流經程式碼的完整路徑並展示出來：

- 未經清理（sanitization）就直接流入危險接收端（SQL、Shell 指令、`eval`、`innerHTML` / `v-html`）的使用者輸入。
- 新增端點中的身分驗證（authentication）或授權（authorization）缺口。
- 寫死在程式碼、日誌（logs）或錯誤訊息中的機密資訊（secrets）。
- 資安關鍵路徑中的檢查與使用時間差漏洞（TOCTOU, time-of-check-time-of-use）。
