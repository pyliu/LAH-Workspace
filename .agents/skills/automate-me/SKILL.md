# Automate me（個人工作模式自動化）

這是一套引導式流程，用於將使用者的工作慣例轉化為代理（Agent）會遵循的技能。產出為一個量身打造的 `-mode` 技能（例如 `jay-mode`、`priya-mode`）。

本技能負責協調三個部分：內建的對話歷史探勘流程（見步驟 1）、技能撰寫規範（參考 `agy-customizations` 技能），以及 **unslop** 技能（文字精煉紀律）。本技能負責串聯它們，而非取代它們。

> **強制輸出語言規範**：與使用者的所有互動提問、探勘報告、草稿呈現與最終回覆，**一律強制使用台灣繁體中文輸出**。

## 流程（Flow）

### 0. 檢查是否已有既有技能

遞迴搜尋工作區 `.agents/skills/**/*-mode/SKILL.md` 與全域技能目錄中符合使用者代稱（handle）的檔案。模式技能可能放在個人分類目錄下（`.agents/skills/<handle>/`），不一定只在頂層。若已存在，請使用 `ask_question` 工具向使用者確認意圖（除非使用者已經明確表示「更新我的技能」或類似語意）：

- 更新既有技能（重複執行時的預設選項）
- 重新開始（罕見，執行前請先詢問原因）

選擇「更新模式」會改變後續流程：
- 步驟 1 僅探勘該技能上次編輯之後的對話紀錄（可透過 `git log -1 --format=%cI <path>` 查詢時間點）。
- 步驟 2 詢問有哪些改變或遺漏，而非從零開始收集。
- 步驟 4 原地編輯既有檔案：保留使用者未推翻的章節、根據新證據修訂章節，僅在出現真正的新規則時才新增章節。

### 1. 探勘對話歷史（Mine their history）

在扇出（fan out）之前，先定位當前工作區的對話紀錄（transcripts）。在 Antigravity 環境中，對話紀錄位於 `<appDataDir>\brain\<conversation-id>\.system_generated\logs\transcript.jsonl`（以及同層級的歷史對話目錄）。請僅探勘與當前工作區相關的對話紀錄，避免跨工作區讀取無關專案的私密對話。

檢視近期對話中反覆出現的模式。可透過 `invoke_subagent`（`TypeName: "research"`，`Model: "inherit"`）平行啟動多個唯讀子代理（Subagent），分別處理不同時間切片的歷史紀錄（例如切成 3 個切片，確保每個子代理有充足樣本）。請依據 **poteto-mode** 技能的 Subagents 章節配置推理層級。每個切片探勘子代理負責讀取指定範圍的對話紀錄、尋找下列訊號，並回傳結構化的模式清單與證據指標。預設值得尋找的訊號包括：

- **回應偏好**：篇幅長短、語氣、格式、「講白話一點」的糾正。
- **委派習慣**：子代理使用方式、模型偏好、專用工作流程、平行化程度。
- **驗證態度**：「完成」的定義、單元測試 vs 實際環境重現、審查機制。
- **程式碼與文字紀律**：風格、引用的原則、Lint／格式化工具。
- **流程慣例**：Git 分支／worktree、Commit 規範、PR 流程、審查與合併工具。
- **後設偏好（Meta preferences）**：在任務中途修正技能、提議新技能的習慣。

在將某個訊號提升為規則前，請先跨切片交叉比對。在 2 個以上切片中出現的模式具有高信賴度；僅出現一次的孤立訊號通常屬於雜訊，應予捨棄。

### 2. 直接詢問使用者（Ask the user directly）

歷史探勘可能會遺漏尚未在對話中出現過的意圖。請使用 `ask_question` 工具（結構化多選題），不要讓使用者從頭打字輸入。

題型設計：每次一到兩個問題，每題 4 到 6 個選項，分類型問題設定 `is_multi_select: true`。先從廣泛的問題開始（「哪些領域最重要？」），再針對勾選的領域追問具體選項。在結構化問答結束後，最後用一個開放式聊天問題捕捉選項遺漏的細節。

切勿一次丟出 20 個問題。

### 3. 聚類分析結果（Cluster findings）

將探勘與問答結合後的訊號歸納為各個章節。常見章節如下（僅使用適用的項目）：

- **回應風格（Response style）**：篇幅、語氣、格式。
- **自主程度（Autonomy）**：多少事情可以直接執行不必先問、MCP 工具使用習慣。
- **先理解再動手（Understand first）**：在界定範圍或調查變更時，優先調用哪些技能。
- **子代理（Subagents）**：預設行為、平行化、模型與任務對應、專用工作流程。
- **文字／程式碼紀律（Prose / code discipline）**：原則技能、Lint 工具、風格指南。
- **審查與驗證（Review and verify）**：重現態度、驗證技能、實機測試工具。
- **開發流程（Process）**：Git worktrees、Commit 訊息、PR、審查／合併工具。
- **技能管理（Skills）**：撰寫技能的習慣、先修技能再修產出、主動提議新技能。

可參考 **poteto-mode** 技能（`../poteto-mode/SKILL.md`）的結構與顆粒度，但切勿照抄其內容——使用者的規則不等於 poteto-mode 的規則。

### 4. 草擬技能（Draft the skill）

參考 `agy-customizations` 技能的規範來撰寫技能檔案。放置位置與格式：

- **路徑**：保留既有模式技能的分類目錄。若是全新模式，當儲存庫已有該代稱的個人分類目錄時，使用 `.agents/skills/<handle>/<handle>-mode/SKILL.md`；否則預設放在專案的 `.agents/skills/<handle>-mode/SKILL.md`。
- **代稱（Handle）**：使用者的名字或自選識別名。
- **Frontmatter `description`**：觸發條件應綁定使用者的名字 + `/<handle>-mode` + 「以他的風格工作」，切勿綁定「寫程式碼」或「審查 PR」等通用關鍵字。
- **Frontmatter 格式**：將 `description` 保持為單一 YAML 純量字串（加引號或使用 `description: >-` 縮排多行）。
- **Frontmatter `disable-model-invocation: true`**：預設啟用。僅在使用者明確希望每一輪對話都自動套用其模式時才移除。

### 5. 迭代精煉文字（Iterate on prose）

對每一行文字套用 **unslop** 技能與精簡寫作準則。

將草稿展示給使用者並收集回饋。預期會有多次迭代。請無情地刪減贅字——模式技能是操作指令，不是長篇手冊。

### 6. 交付落地（Land it）

依專案 Git 規範建立分支或提交變更，確認無誤後再進行 Commit。

## 安全護欄（Guardrails）

- **不要對單次對話過度擬合（Overfit）**：只提過一次且在別處矛盾的偏好屬於雜訊，必須有多次實例佐證才可編入規則。
- **不要賣弄聰明**：重複敘述其他技能的內容、自創比喻，或為代理讀者撰寫「詩意」文字，都是毫無效益的成本。請保持直接、可操作。
- **使用參照，不要內嵌（Reference, don't inline）**：使用者依賴的其他技能應以相對路徑參照呈現，不要貼上整段摘錄；使用者在別處維護的原則文件亦同。
- **保持章節極簡**：唯有當使用者在該領域有具體、非預設的規則時才建立章節。「清楚溝通」不配作為一個章節；「段落簡短。比較選項時用表格。僅在項目真正平行時才用列點。」才是具體規則。
- **指令稱謂保持通用**：在祈使句中使用「使用者（the user）」或「人工（the human）」，不要直接寫出作者的名字。
- **不要強求對稱**：如果使用者沒有值得寫下來的流程規則，請直接跳過「開發流程」章節。

## 評估（Evaluation）

`-mode` 技能屬於主觀產出，不需要跑自動化的基準測試迴圈。直接與使用者進行直覺確認（vibe-check）：讀起來像他本人嗎？有沒有漏掉什麼？確認無誤即可交付。

僅在實務上發現技能觸發準確度有問題時，才針對 `description` 進行最佳化調整。

## 何時不該使用（When not to use）

- 使用者想要的是特定任務技能（而非個人工作慣例）：直接建立一般技能即可，無須探勘對話紀錄。
- 使用者只想捕捉單一狹窄的工作流程（例如「我怎麼寫 Commit 訊息」）：那是一般技能，不是 `-mode` 技能。
