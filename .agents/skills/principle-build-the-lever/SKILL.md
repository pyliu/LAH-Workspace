# 打造槓桿工具（Build the Lever）

當工作並非一眼可完成的小事時，請打造能完成這項工作的工具，而不是靠手工逐一處理。

無論是 codemod、產生器（Generator）還是腳本，每次執行的方式都完全一致，且能零成本重複執行。工具本身就是審查者可以閱讀並重複執行以檢驗成果的產物；相反地，手工修改只能靠「重做一次」來重新驗證。具確定性的腳本能把「相信我」變成「執行這個就能驗證」。

預設請選擇打造槓桿工具。只有當任務極其瑣碎（例如一眼就能看清的兩三處簡單修改）時才跳過。

- 先手工完成第一個單元以摸索出標準作法（Recipe），接著打造工具。在同一個單元上重新執行該工具，並與手工版本進行 `diff` 比對來證明工具無誤。確保該工具可安全地重複執行（具備冪等性）。
- 修改程式碼用 codemod 或腳本、重複性檔案用產生器、分析資料用匯出至 SQLite 的查詢腳本、驗證則用可重複執行的檢查腳本。
- 具確定性的工具勝過平行派遣子代理。如果工具能一次掃描並處理所有單元，請直接自己執行腳本，不要透過 `invoke_subagent` 平行派遣多個子代理去手工套用腳本就能做完的事。
- 當你確實需要透過 `invoke_subagent` 將工作分發給多個子代理（Subagents）時，請將「槓桿」寫成一份所有子代理共同讀取的技能（Skill）：把標準作法、驗證契約（Verification Contract）以及不可觸碰的邊界（Do-not-touch Fences）集中在同一個產物中，並將其放在子代理的寫入範圍之外，避免子代理在過程中悄悄修改了契約。
- 套用本原則必然會產出一個檔案。如果你聲稱引用了本原則，但變更差異（Diff）中卻沒有任何 codemod、腳本、產生器或子代理技能檔，代表你並沒有真正套用它。
- 當這項工作的生命週期超過單次工作階段（Session）時，請將該槓桿工具一併提交（Commit）至版本控制中。

判斷是否打造工具的門檻在於「是否瑣碎」，而非「是否重複」。即使是一次性任務，只要打造工具能讓工作成果變得「可檢驗」，就值得為它打造槓桿。同時請遵循 [惰性準則](../principle-laziness-protocol/SKILL.md)：打造能完成或證明工作的最小腳本即可，切勿過度設計成龐大的框架。

本原則與 [將經驗編碼為結構](../principle-encode-lessons-in-structure/SKILL.md) 不同：後者是將重複出現的指示轉化為持久的防呆護欄；本原則則是為了提升眼前工作的處理吞吐量與可審查性。關於將驗證本身腳本化的作法，請參閱 [證明它能運作](../principle-prove-it-works/SKILL.md)。

> **輸出語言規定**：套用本原則時，所有分析、說明與回覆內容一律使用**台灣繁體中文**。
