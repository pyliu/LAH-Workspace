# Technical Writing（技術寫作與文件規範）

> **輸出語言規範**：所有技術文件、架構說明、README、PR 描述與 Git Commit 訊息，**一律強制使用台灣繁體中文與台灣慣用資訊術語撰寫**（程式碼中的英文命名、API 路徑、指令與設定鍵值則保持原樣，不得為了中文化而任意竄改）。

寫作的最高原則，是讓一位疲憊的工程師**讀第一遍就能完全看懂**。請同時套用以下四個層級的規範。

在進入四個層級之前，有三條凌駕於一切之上的最高準則：

- **刪掉每一個沒有實際作用的字**：如果拿掉一個詞，句子依然完整成立，就把那個詞刪掉。「為了能夠達成 X 的目的」直接寫成「為了 X」；「值得注意的是，我們必須…」直接刪掉，直奔主題。
- **使用簡短、日常的台灣慣用詞彙**：寫「使用」而非「進行一個使用的動作」；寫「協助」而非「賦能／促進」；寫「執行」而非「進行操作」。長詞或專業術語必須以「更高的精確度」來換取它的篇幅。
- **當某條硬性規則讓句子讀起來更生硬時，請換個寫法或保留自然的表達**：一個遵守了所有文法規則、讀起來卻像機器翻譯出來的句子，就是失敗的句子。

**程式碼庫本身就是你的詞彙表。** 請直接寫出真實的符號（Symbol）、檔案路徑、旗標（Flag）或指令名稱，不要用同義詞或模糊的描述去代稱它。

切勿自創行話。請使用開發者日常口頭會說的話：直接說「搬移」、「刪除」、「只減不增的預算上限」，不要故弄玄虛地說「疏散（evacuate）」、「棘輪（ratchet）」或「終局（endgame）」。如果是業界通用的設計模式名稱，只要在首次出現時說明清楚即可。

## LAH-Workspace 台灣繁體中文與 Git Commit 專屬規範（整合自 `AGENTS.md`）

### 1. 台灣慣用資訊術語標準

在撰寫任何技術文件、註解、PR 描述與 Commit 訊息時，請一律使用台灣慣用資訊術語，避免中國大陸用詞或生硬機翻：

| 建議使用（台灣慣用術語） | 避免使用 |
|---|---|
| 專案（Project） | 項目 |
| 伺服器（Server） | 服務器 |
| 資料庫（Database） | 數據庫 |
| 陣列（Array） | 數組 |
| 物件（Object） | 對象 |
| 非同步（Asynchronous） | 異步 |
| 呼叫（Call / Invoke） | 調用 |
| 程式碼（Code） | 代碼 |
| 套件（Package） | 包 |
| 部署（Deploy） | 發版／上線（視脈絡） |
| 元件（Component） | 組件 |
| 記憶體（Memory） | 內存 |
| 快取（Cache） | 緩存 |
| 預設（Default） | 默認 |
| 腳本（Script） | 脚本 |
| 介面（Interface） | 接口 |

### 2. Git Commit 訊息結構規範（`AGENTS.md` 4.3）

撰寫 Commit 訊息時，**一律使用台灣繁體中文**，並嚴格遵循以下三段式結構：

1. **標題行（Summary）**：採用 Conventional Commits 前綴（如 `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`）搭配簡明繁體中文摘要。
2. **詳細說明（Body）**：空一行後，詳列具體修改資訊，包含：
   - **修改目的**：說明背景與要解決的問題。
   - **修改項目**：列出具體修改的檔案與變更內容清單。
   - **相容性說明**：說明跨專案介面（HTTP API / WebSocket / SQLite）相容性或影響範圍。

**標準格式範例**：
```text
feat: 新增使用者登入逾時自動重新整理功能

- 修改目的：避免逾時後未更新 Token 導致 API 回傳 401 錯誤。
- 修改項目：
  - components/lah-login.vue: 加入 15 分鐘計時器並提示倒數通知。
  - store/auth.js: 新增 refreshToken action 與狀態管理。
- 相容性說明：與既有 LAH-API 驗證端點相容，不影響現行登入介面。
```

## 讓節奏富於變化（Vary the Rhythm）

一份文件就算遵守了所有規則，若每句話都切得一樣短、毫無觀點、缺乏具體細節，讀起來依然像機器寫的：

- **刻意交錯句子長度**：短句用來一針見血地下結論；較長的句子用來承載包含前提條件或後果的完整事實。
- **「一句話一個想法」不等於「每句話一樣長」**：把塞了兩個想法的句子拆開；但若一個長句只承載一個連貫想法，請保留它。
- **在允許的模式中展現明確觀點**：在「原理解釋（Explanation）」文件中權衡取捨（Trade-offs）時，請直接說出你的判斷，而不是列出一張冷冰冰的優缺點對照表。反之，「參考手冊（Reference）」則必須保持絕對客觀乾燥。
- **用具體事實取代空泛警告**：不要寫「修改 Schema 可能會導致問題」，請直接寫「重新命名資料表欄位會導致建置失敗（或破壞 `LAH-API` 與 `lah-messenger-server` 的讀寫相容性）」。

## 第一層：先選定文件模式（Diátaxis 框架）

一份文件只採行一種模式。用兩個問題來決定：這份內容是為了引導「行動（Doing）」還是「理解（Thinking）」？是服務於「學習（Learning）」還是「實際工作（Work）」？

- 行動 + 學習：**新手教學（Tutorial）**
- 行動 + 工作：**操作指南（How-to Guide）**
- 理解 + 工作：**參考手冊（Reference）**
- 理解 + 學習：**原理解釋（Explanation）**

無論是整份文件還是單一段落，都請用這個羅盤來定位：

- **新手教學（Tutorial：從做中學）**：讓學習者順利做出成果是你的責任。開頭直接說明讀者將「打造出什麼」，而不是將「學到什麼」。每個步驟都要儘早且頻繁地產出可見的結果。明確告訴讀者應該看到什麼：預期的終端機輸出、畫面變化或日誌行。原理解釋請濃縮成半句話加一個連結。保持具體，以「我們」與直接指令撰寫：「首先，執行 X。接著，設定 Y。」
- **操作指南（How-to：達成目標的步驟）**：解決真實工程師面臨的具體問題，而非單純介紹機器支援哪些功能。假設讀者已具備基本能力，略過基礎教學。**只寫行動步驟**：不要離題、不要講歷史背景、不要為了追求大而全而塞入無關資訊（需要時用連結導出去）。允許分支與情境判斷：「如果你需要 X，請執行 Y。」標題請以任務命名：「如何校正雷達陣列」，而非「雷達陣列校正」。
- **參考手冊（Reference：供查閱的事實）**：只做客觀描述。不寫教學步驟、不說服、不帶個人觀點。保持簡練、完整且篤定。不帶保留語氣地陳述事實、參數選項、限制與錯誤碼。結構應與所描述的程式碼結構完全對應，讓讀者能對照著程式碼與文件一起瀏覽。盡可能從程式碼自動產生。
- **原理解釋（Explanation：理解與原因）**：聚焦單一有邊界的主題，讓讀者即使不打開系統也能讀懂。每個標題前面都應該能自然冠上隱含的「關於…」。錨定在一個真實的「為什麼（Why）」問題上，提供脈絡：設計決策、歷史演進、限制條件與曾考慮過的替代方案。**唯有在這個模式中，才允許表達權衡觀點。**

**嚴禁混用模式**：不要在新手教學裡塞入整張參數參考表；不要在參考手冊裡手把手教基礎步驟；不要在操作指南裡長篇大論爭辯架構優劣。請將它們拆開並用連結互連。

## 第二層：直接對讀者說話（Google 開發者文件風格）

- 直接稱呼讀者為「你」，並以現在式陳述事實。只有真正發生在未來的事才用「將會」。
- **明確寫出「誰」做了「什麼」**（主動語態）：寫「編譯器會檢查型別」，不要寫「型別會被檢查」。唯有當行為主體未知或完全不重要時，才使用被動語態。
- **將操作說明寫成直接祈使句**：「點擊 **送出**。」平實陳述事實，絕不寫「應該要被執行」。
- **將前置條件放在動作指令之前**：「若要刪除文件，請點擊 **刪除**。」（先讓不打算刪除文件的讀者在讀到前半句時就能跳過。）
- **先講最常見的一般情況，例外狀況放在後面。**
- 語氣像一位懂行的同事：不講流行空話、不用浮誇比喻、指令中不需客套加「請務必勞駕」，且**在操作步驟中嚴禁出現「只需簡單地（simply）」、「輕鬆地（easily）」、「快速地（quickly）」**——如果事情真的那麼簡單，讀者就不需要看這份文件了。
- 不要預告尚未實作的功能（「我們未來將會支援…」），且避免連續多個句子都用相同的詞彙開頭。
- **連結文字必須明確說出連結目標**：直接使用目標頁面標題或簡短描述（例如「請參閱 [`AGENTS.md` 跨專案介面契約](file:///c:/Temp/DEV/LAH-Workspace/AGENTS.md)」），**絕不只寫「點擊這裡（click here）」**。若一句話就能在當前頁面把脈絡交代清楚，就不要強迫讀者跳轉連結。
- **標題要點出核心結論或具體動作，而不只是名詞主題**（寫「先選定文件模式」，而非只寫「模式」）。任務標題使用動詞片語（「建立執行個體」）；概念標題使用名詞片語。每頁僅限一個 H1（`#`），且標題層級不可跳階（如 H2 直接跳 H4）。
- 有先後順序的步驟使用**編號清單（Numbered list）**；無順序之分的項目使用**項目符號（Bullet list）**。在進入清單前先用一句完整的話引導，並保持清單各項目句型結構平行一致。
- 程式碼、檔名、指令與變數一律使用反引號（`` `code` ``）；UI 介面元素一律使用**粗體**。避免用「等等（etc.）」含糊帶過，若清單未列舉完畢，請直接在開頭說明「常見項目包含：」。

## 第三層：讓資訊一次載入一個概念（STE 簡化技術語言規則）

- **每句操作指令只包含一個動作**；其他敘述句每句只承載一個核心想法。
- 若操作指令超過約 35 個中文字（或一般句子超過約 45 個字），請考慮拆成兩句。
- **將警告或危險條件放在它所保護的步驟之前**：「未帶 `WHERE` 條件的 `UPDATE` 會覆寫整張資料表。執行 SQL 前請先確認查詢條件。」
- **一詞一義，始終如一**：每個詞彙只賦予一種明確含義。同一種動作從頭到尾只用同一個動詞（例如統一用「啟動」，不要這段寫「啟動」、下一段寫「拉起」、再下一段寫「激發」）。
- 操作程序一律寫成直接指令，絕不寫成旁白敘述或被動語句：寫「安裝相依套件」，不寫「相依套件必須被進行安裝」。

## 第四層：消除任何產生兩種解讀的歧義（無歧義語法規範）

- 將「僅（only）」、「不（not）」等限定詞緊貼在它實際修飾的詞彙旁邊：「僅在數量增加時失敗」與「在數量增加時僅會失敗」意思完全不同。
- **拆解過長的名詞堆疊**：不要寫「即時通伺服器頻道分庫連線逾時重試設定腳本」，請拆開寫成「用於設定 `lah-messenger-server` 頻道資料庫連線逾時與重試機制的腳本」。
- 確保每一個代名詞（「它」、「這」、「該項目」）都明確指向唯一且顯而易見的對象。只要有一絲可能造成混淆，就直接重複寫出該名詞，**絕不用「這（this）」去籠統指代前面整句話**。
- 不要省略關鍵動詞：「第一階段負責搬移轉換器，第二階段負責搬移執行期環境」，不要把第二階段的動詞省掉。
- 使用句號斷句，減少分號與破折號。若想用破折號補充說明，請直接拆成一個新句子。
- 括號內的文字必須是語意完整的單元，或乾脆獨立成句。
- 避免用斜線（`/`）含糊連接（如「A/B」或「及／或」），請明確寫出「A、B 或兩者皆是」。
- **同一個事物在整份文件中只用同一個名稱稱呼**：如果一份文件對同一個機制交替使用「關卡（the gate）」、「棘輪（the ratchet）」與「預算檢查（the budget check）」，讀者會以為有三個不同的東西。

## 語氣與專案儲存庫規範

- 對本技能接觸到的每一份文件套用 **unslop** 技能，徹底清除 AI 罐頭詞彙、無意義轉折、模稜兩可的套話與過度花俏的排版。
- **PR 描述與 Commit 訊息也是技術寫作**：除了 Diátaxis 分類外，上述所有清晰度規範皆完全適用。PR 描述是一份讓審閱者能在 1 分鐘內讀完的簡報，請勿把大段日誌、長串 SHA 清單或巨大表格直接貼進內文，改用檔案連結或摘要呈現。
- 產品 UI 畫面上的提示字串屬於介面文案（UX Copy），請遵循既有前端元件（`LAH-FE` 與 `lah-messenger`）的繁體中文用語習慣。
- 撰寫真實的檔案路徑。任何在文件中提及的數量統計或目錄樹結構，在提交當下都必須是真實準確的，並附上可重新產出該數據的指令。

## 改寫實例（Worked Example）

**修改前（充斥名詞堆疊、被動語態與 AI 贅字）**：
> 關於 proto 匯入棘輪預算腳本參數的配置作業，主要是透過 budget.json 來進行處理的。值得注意的是，我們必須牢記在使用 --write 參數（該參數會更新已提交的預算以反映當前的計數狀態）來進行執行時，應該僅限於在調降預算的情況下才得以為之。一旦超出範圍，CI 將會發生失敗的情況。

**修改後（主動、直白、精準無贅字）**：
> `budget.mjs` 會從 `budget.json` 讀取已提交的預算上限，並統計匯入 proto 的檔案數量。若檔案數量超過預算上限，CI 就會失敗。請僅在調降預算上限時才執行 `budget.mjs --write`。
