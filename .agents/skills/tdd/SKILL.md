# TDD 測試驅動臭蟲修復（TDD Bug Fix）

> **輸出語言規範**：所有問題分析、測試說明、驗證證據與最終回覆，**一律強制使用台灣繁體中文輸出**。

當修復一個具備清晰、低成本測試路徑的臭蟲時，請在修改正式程式碼之前，先讓「壞掉的行為」變成可執行的自動化檢查。目標是寫出一個精準聚焦的迴歸測試（Regression Test）：**在修復前失敗，並在修復後通過**。

當撰寫測試不切實際時，切勿強行硬寫。如果可用的測試需要搭建龐大的測試框架（Harness）、脆弱的 Mock、緩慢的端對端（E2E）基礎設施、僅存在於正式環境的狀態、模糊的重現步驟，或大量無關的測試資料（Fixture）更動，請略過新增測試，改用最接近且實用的驗證方式（注意：在 LAH-Workspace 中測試時，`LAH-API` 必須維持 `MOCK=true`，且 SQLite 測試必須使用專用測試資料庫如 `test.sqlite`，嚴禁覆寫既有開發資料庫）。

## 工作流程（Workflow）

1. **理解臭蟲本質（Understand the bug）**：釐清預期行為、目前錯誤行為、受影響的程式碼路徑，以及最小可觀測的重現方式。
2. **選擇最精準的可執行檢查（Choose the narrowest executable check）**：優先選用該程式碼路徑已經在使用的單元測試、元件測試、整合測試或迴歸測試。如果沒有明顯實用的既有測試路徑，請勿僅為了滿足流程而從零打造一套測試架構。
3. **先寫出會失敗的測試（Write the failing test first）**：新增能抓出這個臭蟲的最小聚焦測試。測試應該編碼「預期的業務行為」，而不是照抄目前的實作細節。
4. **在修復前先執行新測試（Run the new test before fixing）**：確認測試確實因為「預期的錯誤原因」而失敗。如果測試直接通過，或因為無關的原因失敗，請在修改正式程式碼之前先修正測試或重現條件。
5. **修復臭蟲（Fix the bug）**：做出滿足預期行為的最小必要正式程式碼變更，同時保留周邊介面契約相容性。
6. **重新執行迴歸測試（Rerun the regression test）**：確認測試現在順利通過。

## 若撰寫失敗測試不切實際時（If a Failing Test Is Impractical）

請改用最接近的可執行迴歸檢查：針對性的驗證腳本、手動重現指令（如 `php -l`、`node -c`、API 請求測試）、瀏覽器自動化檢查、快照比對、日誌斷言，或聚焦的整合檢查。

**寧可不加新測試，也不要寫出爛測試。** 所謂的「爛測試」是指：大部分在測試 Mock 本身、把當前實作細節寫死、依賴計時（Timing）或無關的全域狀態、為了一個小修復需要昂貴的基礎設施，或是證明修復成功後馬上就得刪掉的測試。

## 安全護欄（Guardrails）

- 絕不僅為了遷就錯誤的實作而修改既有測試。
- 除非預期行為真的改變且理由明確，否則絕不削弱既有的斷言（Assertions）。
- 讓迴歸測試嚴格聚焦於該臭蟲本身，避免大幅更動測試資料（Fixtures）或無謂地擴大測試覆蓋範圍。
- 若臭蟲屬於偶發性（Flaky），請盡可能讓測試具備決定性（Deterministic），並記錄所鎖定的觸發訊號。
- 若該臭蟲揭露了一整類更廣泛的錯誤，請先完成並驗證聚焦的迴歸修復，再考慮補充同類情境的測試覆蓋。

## 最終回覆規範（Final Response）

請回報**具體證據**，而不僅是宣稱結果：

- 點名修復前失敗的測試或可執行檢查，以及它實際產生的失敗輸出。
- 點名修復後通過的測試執行結果，以及任何一併執行的周邊驗證（如語法檢查、Lint 檢查）。
- 若無法展示「修復前失敗」的證據，請明確說明原因，並描述你改用了哪種最接近的迴歸檢查來替代。
