# Show Me Your Work（保留可稽核的決策軌跡）

> **輸出語言規範**：決策紀錄（TSV）中的文字說明（`decision`、`why`、`result`）以及最終向使用者回報的稽核與「需注意（Attention）」摘要，**一律強制使用台灣繁體中文撰寫與輸出**。

維護一份單一且權威的決策紀錄（Canonical Log）。

## 紀錄格式（The Format）

單一 TSV（Tab 分隔）檔案，每個決策佔一列。每個儲存格（Cell）必須維持單行。證據（`evidence`）必須是具體的指標（Pointer），而非長篇大論的文字。

開始一份新紀錄時，請複製 [`references/decision-log-template.tsv`](references/decision-log-template.tsv) 的標題列。各欄位定義如下：

- **`ts`**：ISO 8601 時間戳記（UTC）。
- **`phase`**：所屬階段或工作流名稱。
- **`decision`**：選擇了什麼方案或執行了什麼動作（單行繁體中文）。
- **`why`**：背後的理由（直白的繁體中文）。若是受某項原則驅動，請用白話寫出原因，不要只貼行話標籤。
- **`evidence`**：證明該決策或結果的連結與路徑：Commit SHA、PR 編號、`檔案路徑:行號`，或是產出物、追蹤紀錄、截圖的路徑。**絕不可寫成一段文章。**
- **`result`**：最終結果或檢查條件狀態：例如 `測試全數通過`、`已還原（reverted）`、`pixel-diff 0`、`結果未定（INCONCLUSIVE）`、`待處理（open）`。

以下是一個直白易讀的範例，讓審閱者一眼就能掌握全貌：

```tsv
ts	phase	decision	why	evidence	result
2026-05-24T09:02:00Z	frame	先盤點整體工作量，約 100 個元件、預估耗時約 75 小時	在啟動長時任務前先掌握規模與邊界	commit 3a9f1c2	找出開始前必須先釐清的 5 個問題
2026-05-24T09:40:00Z	harness	在修改任何程式碼前先擷取舊版畫面截圖作為基準	以便比對新舊版本並攔截任何非預期的視覺變化	scripts/snapshot.sh, baseline/	已儲存 120 張基準參考截圖
2026-05-24T11:15:00Z	widget	在不改變外觀的前提下遷移 widget 樣式	保持變更最小化並確保畫面結果完全一致	commit 7c21e0a, pixel-diff 0	外觀完全一致，測試通過
2026-05-24T12:30:00Z	widget	捨棄輔助子代理的修改成果，因為其產出的截圖為空白	親自檢查真實檔案而非盲目相信子代理的口頭摘要	worktree reset	已還原變更，並收緊下一次的子代理指示
```

## 如何寫入一筆紀錄（Logging a Row）

請用「向團隊夥伴清楚交代你剛才做了什麼」的口吻撰寫每一筆紀錄：使用直白的繁體中文、具體的行動描述，嚴禁 AI 官腔或抽象行話（**unslop** 技能同樣適用於決策紀錄文字）。

可使用輔助腳本 `scripts/log.sh <紀錄檔路徑> <phase> <decision> <why> <evidence> <result>`。該腳本會自動打上 `ts` 時間戳記、在首次使用時寫入標題列、清除多餘的 Tab 與換行字元，並在任何以 `=`、`+`、`-` 或 `@` 開頭的儲存格前加上單引號（防止試算表公式注入）。在 Windows PowerShell 環境中，也可直接以對等的檔案附加方式寫入符合相同規範的 TSV 列。

**請記錄「決策點」與「檢查點」，而非每一個細瑣動作**：例如選擇了哪條分岔路徑、完成了某個單元及其驗證結果、發生方向轉換（Pivot）或還原（Revert）及其觸發原因、浮現的阻礙（Blocker）、或是修復了某個檢查關卡。針對循環執行（Loop runs），每輪迭代記錄一列。請略過瑣碎且不言自明的常規操作。

一次「執行（Run）」代表同一個 Agent 對話（包含其後續多輪對話與摘要）。接手任務（Pickup）、替換的新 Agent 或開啟新對話，都視為一個新的 Run。當一個 Run 要往已經有紀錄的檔案中新增內容時，它的第一列必須將 `phase` 設為 `start`；若在同一個對話的後續回合重新回來寫入，請先讀取紀錄檔的最後幾列，確認中間是否有另一個 Run 插入了紀錄——若有，則再次寫入一筆 `phase` 為 `start` 的列。`start` 列的說明應標註其前方不屬於本次 Run 所寫入的 `ts` 時間範圍，並在 `evidence` 中標註本次 Run 的識別資訊（如 `<conversation-id>`）。除此之外，切勿將 `start` 用於其他用途。

## 紀錄檔存放位置（Where It Lives）

預設情況下，決策紀錄是工作過程的暫存產物，不需提交至 Git。請將其存放在工作目錄下的 `decisions.tsv`（若同時有多項任務進行，則存於 `.audit/<task-slug>.tsv`），並排除於版控之外（或存放於 `<appDataDir>\brain\<conversation-id>\` 下的產出物目錄中）。

唯有當這項工作規模龐大、極具挑戰性，且審閱者需要透過決策軌跡才能信任最終成果時，才將其提交至版本控制。

## 鐵則（Rules）

- **僅限附加（Append-only）**：若發現先前的決策錯誤，請新增一列來取代（Supersede）它。**絕不編輯或刪除歷史紀錄列。**
- 優先採用由版控腳本自動產出的驗證證據，勝過手動拼湊的一次性檢查（參見 **encode-lessons-in-structure** 原則技能）。

## 對照對話紀錄稽核決策日誌（Audit the Log Against the Transcript）

在任務結束、交還成果給使用者之前，請檢查決策紀錄是否完全吐實。請讀取本次對話在 `<appDataDir>\brain\<conversation-id>\.system_generated\logs\transcript.jsonl` 中的真實紀錄（切勿跨專案讀取無關的私密對話），將本次 Run 在 TSV 中寫下的每一列與實際發生的過程逐一比對（比對範圍從本次 Run 的 `start` 列或首列開始，直到下一個其他 Run 的 `start` 列為止）：

- 確認每一列都對應到真實發生過的決策或行動。
- 確認每一列的 `evidence` 指標都能實際解析（檔案存在、行號或 SHA 正確），且內容確實證明了該列所宣稱的結果。
- 若有某個分岔選擇、方向轉換或放棄的嘗試實際影響了工作走向，卻未記錄在案，這就是紀錄缺口——請將其補齊。

**請修正紀錄，而不是編造故事。** 稽核過程絕不編輯或刪除既有列（即使是寫錯的列也一樣）。當發現某一列既非真實決策也非真實行動，或者其宣稱的結果與證據有誤時，請在下方**新增一列**來取代它，寫明實際發生的情況並附上真實有效的證據指標。

## 跨視角獨立審查決策軌跡（Independent Review of the Trail）

在交還成果前，請透過 `invoke_subagent`（設定 `TypeName: "research"`）啟動一個獨立的審查子代理來審查這份決策軌跡。自我審查無法取代獨立子代理的檢視。該子代理會同時讀取決策紀錄（TSV）與對話紀錄（Transcript），並標記出使用者應該特別注意的地方——這不是要重做一次工作，而是掃描是否有次佳決策或潛在風險：

- 證據薄弱或缺乏證據支撐的決策列。
- 被跳過、或在對話紀錄中找不到實際證據卻宣稱已完成的驗證步驟。
- 事後看來具風險的選擇（過早優化、範圍蔓延 Scope-creeping、只粉飾表面症狀而未解根因）。
- 使用者若只是快速瀏覽很可能會漏看的盲點或缺口。

每一個產出決策軌跡的任務，其最終回覆的結尾都必須包含一個 **「需注意（Attention）」** 章節：第一行標註審查子代理資訊，接著條列每一項警示並指明對應的 TSV 列或對話步驟。若完全沒有問題，填寫「無警示事項（No flags）」也是有效的值。

## 如何審閱決策軌跡（Reviewing the Trail）

由上往下閱讀，順著 `evidence` 指標抽查實際檔案或輸出。提交至 GitHub 的 `.tsv` 檔案會自動渲染為表格；在終端機中也可透過格式化指令或編輯器直接檢視。

## 與其他技能組合（Composing This Skill）

其他技能在需要保留稽核軌跡時，應直接導向本技能，而非各自發明新的日誌格式。只需直接點名引用 `show-me-your-work` 並遵循本檔案定義的欄位規範即可，不需在其他技能中重複定義欄位。
