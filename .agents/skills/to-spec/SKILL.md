# 規格提煉器 (To Spec)

將現有對話脈絡與對程式庫的理解，直接綜合成一份清晰、完整的**功能規格書（Spec）**。  
此階段**不需重複盤問使用者**，而是直接彙整既有討論成果。

---

## 處理流程

1. **探索程式庫狀態**：
   - 檢查相關程式碼與設定，使用專案專屬詞彙（如 `GLOSSARY.md`）並遵守既有的架構決策紀錄（ADR）。
2. **界定測試接縫（Test Seams）**：
   - 規劃該功能未來的驗證接縫。優先沿用既有最高層級的接縫，接縫數量愈少愈好。
3. **撰寫規格並輸出**：
   - 採用下方標準範本產生規格書（可存於 `specs/<feature>.md` 或輸出至指定任務系統）：

---

### 規格書標準範本

```markdown
# 功能規格書：[功能名稱]

## 1. 問題陳述 (Problem Statement)
從使用者／業務端的視角描述面臨的具體痛點。

## 2. 解決方案 (Solution)
從使用者視角說明此功能如何解決上述問題。

## 3. 使用者故事列表 (User Stories)
極度詳盡且編號的使用者故事清單，格式如下：
1. 作為一個 <角色>，我想要 <功能>，以便於 <效益>。
2. ...

## 4. 實作決策 (Implementation Decisions)
記錄已敲定的具體技術決策：
- 將新增或修改的模組／子專案
- 涉及的 API 契約或路由變更
- 資料庫 Schema 或快取結構變更
- 核心狀態轉換或關鍵互動流程
> ⚠️ 避免在規格書中黏貼過度脆弱的具體程式碼細節，重點在於介面契約與決策。

## 5. 測試與驗證決策 (Testing Decisions)
- 外部行為驗證方式（黑箱／端對端／API 回應契約）
- 涵蓋的主要測試場景與邊界條件
- 既有可參考的測試用例或驗證腳本（如 verify-lah）

## 6. 不在範圍內 (Out of Scope)
明確界定本功能**不處理**的項目與邊界。

## 7. 補充備註 (Further Notes)
其他需要未來實作或 Code Review 時留意的附帶事項。
```
