# Maintain a Verification Skill（維護專案驗證技能與功能地圖）

只要應用程式一改版，驗證功能地圖（feature map）就會開始腐朽過時。本技能是專為 `/create-verification-skill` 所生成的技能（或任何帶有功能地圖的專案本地驗證技能）設計的定期維護迴圈。嚴謹度的基本單位是「功能（feature）」，而非逐字逐句死板核對：從原始碼涵蓋每一個功能檔案，並在實機環境中實際操作每一個功能。

> **強制輸出語言規範**：所有原始碼比對摘要、漂移（drift）分析、實機驗證紀錄與最終維護報告，**一律強制使用台灣繁體中文輸出**。
>
> **LAH 工作區環境與安全特別規範**：在 LAH 工作區執行實機驗證維護時，必須嚴格遵守全域架構契約（`AGENTS.md`）：
> 1. **強制 MOCK 模式**：驅動或驗證 `LAH-API`（PHP 7.3）時，必須確保 `./LAH-API/www/.env` 中 `MOCK=true`，嚴禁對正式或測試環境 Oracle 9i 資料庫執行未授權連線或破壞性操作。
> 2. **SQLite 測試隔離**：驗證 `LAH-API` 或 `lah-messenger-server`（Node.js / `ws`）時，必須使用專用測試資料庫或隔離環境，嚴禁在維護過程中清空或覆寫既有開發資料庫。
> 3. **跨專案拓撲一致性**：檢查功能地圖是否涵蓋 `LAH-FE`（Nuxt 2，含移植之 `components/lah-messenger-*.vue` 元件群）與 `lah-messenger`（Electron 桌面端）對 `LAH-API` 及 `lah-messenger-server`（WebSocket `:8081` / HTTP 附件 `:8082`）的介面變動。

## 判定結果（Outcomes）

最終必須從以下三者中擇一，並明確宣布結果：

- **`clean`（乾淨無漂移）**：每一個功能都完成了原始碼與實機雙重覆蓋，沒有任何需要修正的內容。不建立分支、不發 PR。
- **`changed`（已修正）**：交付一份包含經過實證之文件、測試架（harness）或功能地圖修正的變更。
- **`blocked`（受阻）**：覆蓋檢查無法完成，或已證實的修正無法安全交付。請精確說明是什麼阻礙了流程。

## 編輯範圍限制（Edit scope）

**僅允許編輯驗證技能自身的目錄**（其 `SKILL.md`、`features/` 目錄以及它所擁有的測試架腳本）。在執行維護期間**嚴禁修改產品程式碼**：如果功能地圖描述的某個行為，應用程式現在已經做不到了，那要嘛是「文件漂移（doc drift，請修正功能地圖）」，要嘛是「產品退化 Bug（product regression，請向使用者回報，切勿透過修改驗證文件來粉飾太平）」。

## 維護流程（Pass）

0. **定位目標技能（Locate the target）**：找出要維護的驗證技能——即內文包含 Launch/Drive 章節與功能地圖的專案本地技能（通常位於 `.agents/skills/verify-*/`）。若有數個候選目標，請使用 `ask_question` 詢問使用者要維護哪一個；若完全找不到，請立即停止並引導使用者改用 `/create-verification-skill`，切勿憑空捏造目標。

1. **索引衛生檢查（Index hygiene）**：讀取功能地圖的 `README.md` 並列出同目錄下的所有功能檔案。修正遺漏、多餘、重複或失效的索引項目。保持輕量，不需產生額外的清單檔案。

2. **原始碼平行檢視波（Source wave）**：針對每一個功能檔案，透過 `invoke_subagent`（`TypeName: "research"`，`Model: "inherit"`）平行啟動一個唯讀子代理（Subagent）。每個子代理負責從原始碼解釋「這個面向使用者的功能實際上是如何運作的？」、標記可能的文件漂移（附上原始碼位置引用），並回傳一份簡潔的實機驗證配方（recipe）。**子代理絕不親自驅動應用程式，也絕不編輯任何檔案。** 回傳格式固定為：功能摘要 ／ 原始碼進入點 ／ 疑似漂移或無漂移 ／ 單一驗證配方。

3. **調和與盤點（Reconcile）**：確認每個功能檔案都已收到回傳摘要。將重疊的驗證配方合併為最少數量的應用程式狀態切換。抽查子代理引用的疑似漂移處；對於無漂移的聲明則不需重複查證。掃描近期的 Git 變更紀錄（churn），檢查是否有新加入、面向使用者的操作表面遺漏在功能地圖之外——必須找到具體的原始碼路徑才能判定為遺漏。

4. **實機驗證波（Live pass）**：即使原始碼看起來完全沒變，**也必須執行實機驗證**。由主代理（Coordinator）統一負責所有實機驅動，並遵循該驗證技能自身的 Launch 模型（對於伺服器與 UI 採用單一長駐實例依序驅動；對於短生命週期 CLI 則每次驅動使用全新隔離工作階段——由技能本身的 Launch 章節決定）。每個功能至少實際操作一次，並在整個過程中無論遇到任何失敗，都嚴格維持以下**三大不變量（Invariants）**：
   - **(1) 絕不驅動未經健康檢查的實例**：在第一次驅動前執行 Doctor；若以工作階段為單位則在每個新工作階段前執行 Doctor；在任何一次驅動失敗後再次執行 Doctor。若 Doctor 看不出異常（例如程序存活但 UI 畫面卡死），請重設回已知狀態或重新啟動，切勿抱持僥倖心態繼續跑。
   - **(2) 已擷取的驗證證據必須在每次清理後存活**：在指定路徑實際檢查證據檔案存在，而非主觀假設。
   - **(3) 任何一次驅動所產生的殘留物絕不能活過該次驅動**：無論工作階段是卡住、已退出還是共用實例，失敗迭代留下的殘留狀態都必須清理乾淨（針對共用實例，請清理測試殘留資料，而非砍掉共用實例本身）。
   
   若 Doctor 失敗是由於驗證技能本身過時（skill drift）所導致，請在編輯範圍內修正技能並重試一次（僅重啟被該修正影響的部分），若仍失敗才判定為 `blocked`。若某個功能無法到達，唯有在明確記錄具體前提條件（驗證權限、作業系統、外部狀態）與已嘗試路徑時，才可標記為 `verified-unreachable`（已驗證無法到達）；若功能地圖漏寫了該前提條件，這本身就是文件漂移，請補進地圖中。任何在分類階段修改過的測試架腳本，都必須在交付前重新實機跑通驗證。最終拆除（Final teardown）會在最後一次實機驅動（包含重新驗證）完成後執行，確保沒有任何測試程序殘留（但驗證證據依然保留）。

5. **問題分類處置（Triage）**：
   - 使用者視角描述錯誤或遺漏 → **文件漂移（doc drift）**，修正功能地圖。
   - 產品功能正常運作，但測試架無法驅動 → **測試架缺口（harness gap）**，修正測試架（輔助腳本必須可直接執行，且呼叫方式需記載於技能內文中）。
   - 應用程式本身的行為真的壞掉了 → **產品缺陷（product gap）**，明確記錄下來回報給使用者，切勿混入本次驗證技能維護變更中。

6. **交付或停止（Ship or stop）**：若結果為 `changed`，在提交前先重新閱讀每一個修改過的檔案，確保精確無誤。若為 `clean` 或 `blocked`，則不修改檔案，誠實回報最終判定結果與覆蓋範圍。

請將簡潔的執行筆記（已覆蓋的功能、無法到達的前提條件、已確認的漂移、最終結果）保存在暫存目錄（如 `<appDataDir>/brain/<conversation-id>/scratch/`）中，切勿將暫存筆記 Commit 進儲存庫。
