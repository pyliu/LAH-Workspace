# 設計理由範本（Rationale Template）

與型別草稿一併交付的說明文件。篇幅以一頁為限。使用一般句子大小寫標題，不寫空洞套話。請將斜體說明替換為實際內容，並**一律強制使用台灣繁體中文撰寫**。

## 問題（Problem）

*一段話。說明我們試圖解決什麼問題，以及既有系統或約束條件中有哪些因素讓架構形狀並非顯而易見。若 [階段 A](../SKILL.md) 浮現了設計必須遵守的約束條件（必須互通的既有型別、不能破壞的呼叫端、跨越邊界的不變量），請在此明確列出，讓讀者看見與你相同的約束。*

## 使用方式（呼叫端視角 / Usage - caller's view）

*在撰寫型別草稿之前，請先寫這一段。展示使用者（呼叫端）會閱讀的 README 或快速入門，以及兩到三個在他們自身程式碼中的真實呼叫點（call sites）：他們匯入什麼、呼叫什麼、取得什麼回傳值。[架構形狀](#架構形狀shape) 中的型別草稿是由此推導而來。兩者必須一致；當出現分歧時，請修正草稿以配合使用方式，而非反過來。呼叫端的體驗就是規格，型別是為它服務的。*

## 架構形狀（Shape）

*推薦的架構設計。先說明資料結構，再說明資料如何流經各個簽章。點出關鍵的承重決策（load-bearing decisions）。說明哪些不變量（invariants）已編碼進型別中、驗證邏輯位於何處，以及系統刻意不做哪些事。明確評估介面深度（interface depth）：說明公開表面隱藏了哪些複雜度、對呼叫端暴露了哪些部分，以及為何介面大小恰到好處而無多餘。引用每個決策背後的原則（例如：`依據 boundary-discipline`），不需重複解釋原則內容。*

## 綜合決策（Synthesis decision）

*由 [arena](../../arena/SKILL.md) 填入。記錄哪一個候選方案成為基底（base）及其原因、從其他候選方案採納並改寫了哪些部分，以及淘汰了哪些部分及其原因。*

## 接受的取捨（Tradeoffs accepted）

*所選形狀做出的每項取捨各列一點。格式：「我們接受 X，以換取 Y。」點出任何未來讀者可能誤以為是疏忽的地方，包含看起來像過早最佳化或過度簡化的設計。*

## 考量過的替代方案（Alternatives considered）

*必填。列出至少一個具體的替代架構形狀，並用一句話說明它落敗的原因。請從「介面深度」而非單純「實作難易度」來評估每個替代方案，點出它對呼叫端暴露了什麼複雜度、隱藏了什麼複雜度。當設計空間存在真正的競爭方案時，可列出兩到三個替代方案；當約束條件直接決定了唯一解答時，列一個即可，結論寫為「這是唯一可行的形狀，因為……」。避免列出同一種形狀的不同微調版本。本章節涵蓋所選形狀自身考量並淘汰的設計替代方案，而非其他平行 runner 的候選方案。*

## 待決問題與風險（Open questions and risks）

*在勾勒草稿期間注意到、需要使用者權衡決定的事項，以及在開始實作前值得標記的風險。請以「提問」而非「斷言」的形式撰寫，讓使用者的回答直接成為決議，而非只是一則評論。*

## 下一步實作項目（Next implementation step）

*依據草稿要建構的第一個項目。一句話說明在綜合完成後（或若啟用了檢查點，在簽核通過後）你會立即開始撰寫的內容。*
