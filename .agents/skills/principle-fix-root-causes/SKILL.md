# 修復根本原因（Fix Root Causes）

除錯時，請修復「故障源頭」，而不是修復「故障浮現的位置」。症狀只是錯誤狀態變得可見的地方；根本原因則是系統第一次做出不該做的行為、或是未能處理它本應處理的狀態之處。

**原因：** 治標不治本的症狀修復會掩蓋證據，讓故障有機會改從其他地方冒出來。每增加一個這類修補，系統就會變得更難推論，因為程式碼裡背負了一個沒人說得清源頭的 Bug 繞道作法（Workaround）。

**實踐模式：**
- 先重現問題。
- 在每一步追問「為什麼」，直到答案指向程式碼中的某個錯誤決策，而非前一個錯誤所衍生出的結果。
- 卡關時，加入觀測與日誌（Instrument）。讀取實際的錯誤訊息與實際狀態，不要靠猜測。
- 詰問觸發該症狀的狀態本身是否「合法（Legitimate）」。如果系統在正常運作下確實可能處於該狀態，那麼遇到該狀態而崩潰的程式碼就是根本原因，在此處妥善處理該狀態就是正確修復。如果該狀態根本不應該存在，那麼在崩潰處加上防呆檢查只是在掩蓋 Bug——請找出是什麼產生了這個非法狀態。防呆檢查（Guards）、重試、吞掉錯誤、強制截斷數值（Clamped Values）與丟棄狀態，都是掩蓋 Bug 最常見的手法。
- 當某個問題只有在重啟後才會發生時，請優先懷疑持久化狀態：設定檔、快取、Lock 檔、序列化的狀態。
- 檢查「錯誤模式」，而不只是「單一案例」。找出所有存在相同缺陷的地方並一併修復。
- 如果一個繞道作法（Workaround）需要寫上整段長篇註解才能合理化它的存在，代表程式碼本身寫錯了。請修復程式碼，而不是修潤註解。
- 如果某個關鍵事實需要深入挖掘老半天才能發現，請提出一個低成本且常駐開啟的觀測指標（Signal），讓下次第一眼就能看出問題。

> **輸出語言規定**：套用本原則時，所有分析、說明與回覆內容一律使用**台灣繁體中文**。
