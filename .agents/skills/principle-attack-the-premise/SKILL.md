# 質疑前提（Attack the Premise）

當兩個或以上共用同一前提的修復方案皆未通過同一個驗證關卡時，請懷疑那個「前提」，而不是懷疑修復本身。

**原因：** 每一次失敗的修復，都是反駁其背後假設的證據。若在同一個前提下進行第三次修復，只是把精力浪費在證據已經表明「根本原因不在這裡」的地方。

**實踐模式：**
- **將前提明確寫下來。** 前提就是先前每一個失敗的修復所共同預設的那一句話。
- **在進行下一次修復前，先驗證前提。** 找出一個「如果前提為假，觀察結果就會完全不同」的切入點，並實際執行觀測。不只看失敗的規模有多大，更要看失敗是如何分佈的。並依照 [打造槓桿工具](../principle-build-the-lever/SKILL.md) 原則，讓這項檢查具備可重複執行的能力。
- **順著證據走。** 如果證據與前提相矛盾，代表真正的原因在別處——請找出這些失敗案例之間有哪些「前提未能預測到」的共同點。如果證據證實了前提為真，請依照 [修復根本原因](../principle-fix-root-causes/SKILL.md) 原則繼續追問下一個「為什麼」；先前的修復可能只處理了結果，而非源頭。
- **消除異常產生的條件，而非事後彌補**（遵循 [惰性準則](../principle-laziness-protocol/SKILL.md)）。如果證據顯示某個環節總是落入失敗的一方，請改變「讓它落入該處」的源頭機制。事後清理的補償機制不僅讓根本原因留在原處，還會在每次執行時增加額外負擔。

**停下腳步：** 在把前提寫下來並完成驗證之前，切勿開始撰寫下一個修復方案。

本原則與 [從第一性原理重新設計](../principle-redesign-from-first-principles/SKILL.md) 不同：後者是圍繞新需求重新建構設計；本原則則是質疑現有設計所依賴的事實假設。

> **輸出語言規定**：套用本原則時，所有分析、說明與回覆內容一律使用**台灣繁體中文**。
