# Blast Radius（爆炸半徑與影響範圍分析）

在變更交付之前，找出它會在其他什麼地方造成破壞。適用於「X 的爆炸半徑」、「這可能會弄壞什麼」，或審查一個你還不放心的微小 Diff。

這是 `how` 與 `why` 的搭檔技能：`how` 告訴你程式碼在做什麼，`why` 告訴你為什麼它長這樣，而 **blast-radius** 則告訴你它會弄壞別處的什麼東西。

光把呼叫端（callers）列出來不是這項技能的工作——代理（Agent）用 grep 一秒鐘就能找完。真正的任務是找出**光靠 grep 絕對看不出來的破壞**。

> **強制輸出語言規範**：所有爆炸半徑分析、風險評估、安全事實證明與最終報告，**一律強制使用台灣繁體中文輸出**。
>
> **LAH 工作區跨專案邊界特別提醒**：在 LAH 工作區進行爆炸半徑分析與實機驗證時，請務必遵守全域架構契約（`AGENTS.md`）：
> 1. 執行任何測試或腳本驗證 `LAH-API` 時，必須確認 `./LAH-API/www/.env` 中 `MOCK=true`，嚴禁對正式或測試環境 Oracle 9i 資料庫進行未授權寫入或破壞性操作。
> 2. 跨專案介面檢查必須涵蓋四個子專案的邊界：`LAH-API`（PHP 7.3 REST API 與內部 Legacy HTML）、`LAH-FE`（Nuxt 2 前端與移植之 `components/lah-messenger-*.vue` 元件群）、`lah-messenger-server`（Node.js / `ws` WebSocket 事件、Payload、HTTP 附件路由與 SQLite 頻道分庫）以及 `lah-messenger`（Electron 主程序與 Nuxt 渲染端）。

## 不要相信你自己的紙上分析（Don't trust your own writeup）

一份聽起來頭頭是道的爆炸半徑分析報告本身毫無價值——無論它是真是假，讀起來都很具說服力。因此，不要只交出一份文字報告。請找出整件事之所以安全的**那一兩個關鍵事實（the one or two facts）**，並透過**實際執行程式碼**來證明它們。

### 你有多確定？（How sure are you）

針對變更安全性所依賴的每一個事實，在成本允許的範圍內，盡可能往這份清單的下方推進，並誠實標明你停在第幾步：

1. **你口頭說的**：單憑這點毫無價值。
2. **你指出了程式碼行號**：給出真實的 `file:line`，或所呼叫套件本身的原始碼位置。
3. **你推導出壞情況不可能發生**：你一步步走過失敗路徑，證明程式執行流不會到達那裡。
4. **你實際執行了它**：寫一個小腳本或測試去呼叫真實程式碼，如果你錯了它會大聲報錯失敗。
5. **你在執行中的應用程式裡重現並驗證了它**。

第 4 步通常只是一支小腳本，匯入應用程式實際使用的同一個套件或類別，並直接呼叫你所擔心的那個函式。

## 執行步驟（Steps）

1. **閱讀變更**：檢視 Diff、它新增／修改／刪除的符號（symbols），以及它現在的行為與之前有何不同——特別是 Diff 表面沒有明寫出來的隱含改變。可參考 `why` 技能的步驟 2 來拉取 PR 與 Commit 歷史。
2. **找出「它之所以安全的那一個關鍵事實」**：大多數看起來有風險的變更，之所以安全都取決於單一事實（例如：「這個呼叫只會清除已經過期的快取項目，不會做任何其他事」）。找出那個事實！如果它成立，絕大多數的風險情境就會瞬間解除。請把時間花在這裡，而不是列出一長串「可能會怎樣」的猜測清單。
3. **往 grep 停下來的地方深挖**：閱讀你所呼叫套件的原始碼，檢查鎖定的版本號（pinned version）與任何本地修補檔（patch）。釐清各個動作的執行時機：微任務（microtasks）、元件卸載與清理（unmount and teardown，如 Vue 2 生命週期）、非同步事件順序。追蹤符號搜尋（symbol search）會漏掉的跨邊界細節：API 回傳的 JSON 結構、資料庫欄位（Oracle 9i / SQLite 3）、WebSocket 連線封包格式、另一個語言（如 PHP 寫、Node.js 讀，或後端回傳、前端解析）讀取相同資料結構的行為、功能旗標（feature flag），以及下游三層之外的程式碼。
4. **誠實評估每一項風險**：給出它實際發生的機率，以及一旦發生時的真實代價。保留你已確認存在的風險；將你檢查過並排除的項目另外列在「已排除（Cleared）」中。規則與 `why` 相同：引用真實的 `file:line`，搜尋結果為空也是一個有效答案，絕對不要捏造不存在的呼叫端或 API。
5. **證明那一個關鍵事實**：撰寫腳本或測試來執行真實程式碼，實際跑一次，並將輸出結果貼上來。
6. **大型或廣泛變更請動用 `arena`**：針對影響廣泛的變更，將它作為 **arena** 執行，向多個平行子代理提出相同問題並整合答案，以捕捉不同視角發現的真實問題。

## 交付內容（What to hand back）

- **變更內容（What it does）**：改了什麼，包含不直觀的隱含行為變化。
- **確保安全的那一個關鍵事實（The one fact it's safe because of）**：明確陳述該事實、說明你推進到上述清單的第幾步，並展示證明過程與執行輸出。若無法證明，請明確標記為「未證實（unproven）」。
- **確認的風險（Risks）**：每一項需點出它如何損壞、對應的 `file:line`、發生機率與嚴重程度，以及如何檢查。針對重要風險貼上實際驗證證據。
- **已排除項目（Cleared）**：你檢查了哪些地方，以及為什麼它們沒問題。
- **合併前檢核（Before you merge）**：能抓出真實 Bug 的最低成本測試或重現步驟，包含你所撰寫的驗證腳本。

請透過 **unslop** 精煉文字、引用真實程式碼，並在公開前移除任何敏感私密資訊。

**最終回覆**：上述分析報告，且其中的關鍵安全事實必須附上實證或明確標記為「未證實（unproven）」。
