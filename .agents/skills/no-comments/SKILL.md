# No Comments（消除冗餘註解與權宜死碼）

啟動 Comment Sicko（註解狂魔）子代理，並針對已確認接受的發現採取行動。請尊重 Comment Sicko 全新的嚴格視角。

> **強制輸出語言規範**：所有審查報告、刪除統計、`MUST KILL` 重構建議、約束編碼提案與最終回覆，**一律強制使用台灣繁體中文輸出**。
>
> **LAH 工作區文件完整性護欄（關鍵優先規則）**：
> 依據本工作區與系統規範之「**維護文件完整性（Maintain documentation integrity）**」原則：
> 1. **嚴格保留與本次變更無關的所有既有註解與 Docstrings**：除非使用者明確指示清理特定歷史檔案，否則不得刪除或破壞與當前變更無關的既有註解與文件說明。
> 2. **鎖定變更範圍**：`no-comments` 與 `comment-sicko` 僅針對「**本次變更範圍內新增或修改的冗餘敘事註解、被註解掉的死碼屍體、以及用來掩蓋不良設計的藉口註解**」進行清理與標記 `MUST KILL`。

## 1. 界定範圍（Scope）

優先使用呼叫者指定的檔案或 Diff 範圍；若未指定，則使用當前工作樹相對於基底分支（預設為 `main`）的 Diff 範圍（且僅聚焦於本次變更觸及的區塊，遵守上述文件完整性護欄）。

## 2. 執行步驟（Steps）

1. **啟動 Comment Sicko 子代理**：在 Antigravity 環境中，使用 `invoke_subagent`（`TypeName: "self"`，`Model: "inherit"`）啟動子代理，將 [`references/comment-sicko.md`](references/comment-sicko.md) 的內容作為子代理提示詞，並傳入步驟 1 界定的變更範圍。請依據 **poteto-mode** 技能的 Subagents 章節配置適當的推理層級。切勿在提示詞外重複贅述規則。
2. **檢視報告與 Diff**：嚴格檢查子代理回傳的報告與 Diff：
   - **予以退回（Reject）**：退回任何擅自修改應用程式業務程式碼的行為、超出本次變更範圍的越界刪除（違反文件完整性護欄）、誤刪受保護例外條款的註解、理由陳述錯誤的 `MUST KILL` 標記，以及將刻意保留的合理設計誤判為有罪的標記。
   - **保留可操作的重構標記**：針對我們自身新增程式碼中「不直觀行為（our-code surprises）」所發出的重塑（reshape）標記，屬於可採取行動的有效發現——不要把那些被刪掉的解釋性廢話註解還原回來，而是應該把程式碼本身改到一目了然。
   - **嚴格審核保留條款（Keep）**：唯有具備確鑿證據、證明該註解描述的是「我們無法修改的外部依賴、平台或協定限制」時，才允許保留解釋性註解。
   - **稽核被漏掉的 Lint 與型別壓制註解**：檢查範圍內是否有被漏掉的 `eslint-disable`、`@ts-ignore`、`@ts-expect-error` 等壓制註解。壓制正確性或安全性檢查的註解一律維持為可操作的 `MUST KILL`。
   - **查證模糊的警告註解**：在核准刪除或保留單薄的 `IMPORTANT` 或 `do not remove` 註解之前，先對該符號執行 `/how` 或 `/why` 技能。若刪除理由存疑，不要盲目還原註解，請先查明真相；若保留理由被推翻或依然模稜兩可，則將該冗餘註解刪除。若退回第一份子代理報告，請指名失敗原因、還原後重跑一次；若第二次仍不合格，請將問題公開回報並宣告 `/no-comments` 執行失敗。
3. **處理已接受的 `MUST KILL` 標記**：
   - 對於簡單的標記，直接透過刪除死碼路徑、移除無用參數或改用正確的 API 來修復。
   - 若任何修復需要重新設計結構形狀，請針對已接受的項目集與周邊程式碼執行一次 `/architect`（僅停留在草稿階段：由 `architect` 負責定出形狀，由步驟 4 負責實作）。
4. **實作範圍內最小的根本原因修復**：移除每一個被點名的權宜解法（workaround）。如果根本原因超出本次變更範圍，請先落地範圍內最小的修復，並將其餘部分作為待決事項回報。**fix-root-causes** 與 **redesign-from-first-principles** 原則技能僅用於指導修改意圖，**絕不授權擴大修改圍欄或去修改範圍外的無關程式碼**。切勿再硬釘新的表面症狀防衛判斷（symptom guards）。
5. **將約束型註解轉化為結構防呆（Constraint comments）**：針對寫著 `do not remove`、`請勿修改字眼` 或 `修改前請先找 X` 的約束型註解，若屬於我們無法改變的外部限制則予以保留；若屬於內部規則，請向使用者提議範圍內成本最低的結構化防呆方案（型別約束、執行期斷言、單元測試或 CI Lint 規則），並等待使用者互動核准（若為無人值守或自動評估模式，則需事先取得呼叫者預先授權）。若獲核准，先完成結構化編碼再刪除該註解；若未獲核准，則保留記錄、將該約束列為待決事項，並勾勒出範圍外的後續工作。
6. **最終回報**：清楚列出刪除的冗餘註解數量、因合規或護欄而還原的註解、重跑紀錄、`architect` 草稿、已完成的根本修復、提出的約束編碼方案、已落地的結構編碼、尚未強制執行的約束條件，以及其他開放待決事項。
