# 為領域建立模型（Model the Domain）

將真實的業務領域知識編碼進資料結構中，而不是將它拆散在各處的條件判斷式（Conditionals）裡。契合領域特性的資料結構能讓「非法狀態」從根本上無法被表示（Make Invalid States Unrepresentable），並直接消滅多餘的分支。在撰寫之初就選對結構的成本極低；事後才想補救往往會被視為大型重構而被無限期延後。

請善用下列結構：

- 使用**狀態機（State Machine）**，取代散落各處的布林旗標、階段標記或生命週期檢查。
- 使用**具名型別模型（Typed Model）**，取代鬆散的參數傳遞或重複的資料結構假設。
- 使用**映射表（Map）、註冊表（Registry）、查表（Lookup Table）或具辨識標籤的聯合型別（Discriminated Union）**，取代散佈在多個檔案中的條件分支。
- 使用 **Reducer 或命令／事件模型（Command/Event Model）**，取代隨處可見的臨時狀態修改（Ad hoc State Mutations）。
- 圍繞**單一領域知識體系**來組織模組，而不是按照 `load`、`validate`、`transform`、`save` 這類執行先後順序來切分模組——執行順序不等於領域職責歸屬（Ownership）。
- 建立**精簡的模組邊界**，將重複出現的行為、職責歸屬或不變條件（Invariants）匯聚在一起。
- 當資料存取模式有需要時，選用合適的**佇列（Queue）、快取（Cache）、索引（Index）、圖（Graph）、樹（Tree）或正規化集合（Normalized Collection）**。
- 任何其他契合問題的資料結構。如果現有結構都不適合，請先釐清「程式碼絕對不允許發生什麼情況」以及「資料會如何被讀取」，再設計出能精確表達這些限制的結構。

不要強行套用抽象化。如果目前的結構已經足夠清晰、局部且不太可能繼續膨脹，請優先保留直白無奇的程式碼。如果某個抽象層只增加了間接跳轉，卻沒有減少條件分支、重複規則、非法狀態或生命週期風險，請對它抱持懷疑態度。

如果你發現新功能只是讓既有的 `if/else` 鏈又多長出一個分支，或是新增了第二個必須與第一個保持同步的布林變數，就代表你跳過了本原則。依時間順序切分模組（Temporal Decomposition）則是另一個警訊：以執行階段命名的模組，往往會在各步驟間重複相同的領域規則。
