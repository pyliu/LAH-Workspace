# Create a Verification Skill（建立專案專屬驗證技能）

每一個嚴謹的專案都需要一套腳本化的方式來驅動真實應用程式並證明其行為：啟動它、像真實使用者一樣操作功能，並擷取驗證證據。本技能會針對當前專案儲存庫量身產出一個專案本地技能（`.agents/skills/verify-<app>/`）。請注意，你產出的技能內容是寫給「下一個代理（Agent）」讀的，而非寫給人類看的——它將在任務中途被一個從未見過此應用程式的代理直接冷啟動讀取。

> **強制輸出語言規範**：所有儲存庫盤點分析、生成的驗證技能內容、功能地圖與最終回覆，**一律強制使用台灣繁體中文輸出**（指令、路由與程式碼識別字除外）。
>
> **LAH 工作區環境與安全特別規範**：在 LAH 工作區建立或執行驗證技能時，必須嚴格遵守全域架構契約（`AGENTS.md`）：
> 1. **強制 MOCK 模式**：啟動或驗證 `LAH-API`（PHP 7.3）時，必須確保 `./LAH-API/www/.env` 中設定為 `MOCK=true`，嚴禁對正式或測試環境 Oracle 9i 資料庫執行未授權連線或破壞性操作。
> 2. **SQLite 測試隔離**：驗證 `LAH-API` 或 `lah-messenger-server`（Node.js / `ws`）的 SQLite 行為時，必須使用專用測試資料庫或隔離環境，嚴禁清空或覆寫既有開發資料庫。
> 3. **多端點拓撲識別**：可善用工作區根目錄的 `start_dev.bat` / `stop_dev.bat` 或各子專案獨立啟動指令（`LAH-FE` Nuxt 2 `:8080`、`lah-messenger-server` WebSocket `:8081` / HTTP 附件 `:8082`、`lah-messenger` Electron 桌面端），並在 Doctor 與 Cleanup 階段精準管理 Port 占用與程序生命週期。

## 1. 訪談專案儲存庫，而非詢問使用者（Interview the repo, not the user）

請直接從程式碼庫中找出以下問題的答案，僅在程式碼庫中無法觀察到時才詢問使用者：

- **操作表面（Surface）**：使用者實際觸碰的是什麼？是 Web UI、CLI/TUI、桌面應用程式（如 Electron）、REST/WebSocket API、行動裝置 App 還是函式庫？一個儲存庫可能包含多個表面；請選出最主要的一個，並記錄其餘部分。
- **啟動方式（Run）**：應用程式如何在本機啟動？優先採用儲存庫本身記載的開發指令（`package.json` scripts、批次檔、Makefile、README 快速入門）。記下連接埠（ports）、環境變數、種子資料（seed data）與驗證機制。
- **驅動方式（Drive）**：代理如何以程式化方式與它互動？優先尋找既有的測試架（harnesses）——例如 Playwright/Cypress 規格、Chrome DevTools MCP、expect 腳本、PTY 輔助工具、可 curl 的端點或除錯埠。若無既有工具，才挑選通用配方：Web 與 Electron 使用瀏覽器/CDP（如 `chrome-devtools` 技能），CLI/TUI 使用終端機工作階段，後端服務使用標準 HTTP / WebSocket 客戶端。
- **觀測證據（Observe）**：可以擷取哪些證據？螢幕截圖、ARIA 快照、終端機輸出紀錄、HTTP/WebSocket 回應內容、日誌（logs）、結束代碼（exit codes）、資料庫狀態。
- **隔離性（Isolate）**：能否同時並排執行兩個實例（透過不同的連接埠、資料目錄、設定檔）？如果不行，請在產出的技能中明確寫出來——拒絕雙重驅動同一個共用實例，遠勝過破壞使用者正在使用的工作階段。

如果當前的程式碼檢出（checkout）無法正常建置或原樣啟動，請在產出技能之前先將問題修好（或精確回報阻礙原因）；建立在損壞基底上的驗證技能只會教導錯誤的步驟。當某個無關緊要的缺失資源阻礙了啟動（例如 API 根本不會用到的靜態目錄、或範例設定檔），產出的技能可以建立它（需清楚標記為驗證用鷹架），並在清理（Cleanup）階段將其移除。

## 2. 產出驗證技能（Generate the skill）

撰寫 `.agents/skills/verify-<app>/SKILL.md`，必須包含完整的 YAML frontmatter（`name: verify-<app>` 以及明確點出應用程式名稱、操作表面與何時該調用它的 `description`——沒有 frontmatter 的技能無法被系統註冊）以及下列章節。每個章節都必須基於步驟 1 實際調查到的事實撰寫（嚴禁留下未填寫的佔位符）：

- **啟動（Launch）**：為了驗證而啟動應用程式的確切指令，以及如何判斷它已準備就緒（特定的日誌行、提示字元或健康檢查回應）。Launch 必須能從空的資料目錄達到「真正可用」的狀態（包含任何 Migration 與種子資料）。「就緒」代表功能可用，而不只是程序有回應（例如資料庫健康檢查通過時，初始化腳本可能還在背景執行）。同時包含關閉（teardown）指令。對於短生命週期的 CLI 或 TUI，不需要維持常駐伺服器：Launch 代表先建置執行檔（或安裝依賴）一次，接著在各自隔離的終端機工作階段中執行每一次驅動。
- **健康檢查（Doctor）**：一項唯讀檢查，用來回答「這個實例值得驅動嗎？」——確認程序存活、版本/建置正確、連接埠確實由我們持有、驗證權限有效、且（針對 LAH-API）`MOCK=true` 已啟用。每當情況看起來不對勁時，代理應第一時間執行 Doctor。
- **驅動（Drive）**：使用此儲存庫中真實的選擇器（selectors）或指令的測試架配方，而非抽象範例。優先使用穩定的控制代碼（ARIA 標籤、data 屬性、提示字串、路由路徑），避免依賴螢幕座標或 Tab 鍵順序。
- **證據（Evidence）**：為了證明功能正常需要擷取什麼，以及證據檔案存放在哪裡。明確規定證明標準：必須走真實的使用者路徑，而非呼叫內部 setter 或測試專用端點；必須同時擷取「操作動作」與「結果狀態」，而非只有最後一張畫面；除了視覺畫面外，還要驗證副作用（寫入的檔案、新增的資料列、發送的訊息）；僅在正式環境邊界本來就隔離了外部系統（如 LAH-API 的 Oracle MOCK 模式）時才允許使用 Mock。當安全路徑是 dry-run 或測試模式時，必須透過實際觀測（檔案、網路、Git refs）來驗證它到底跳過了什麼，而不是盲目相信它的名稱（有些 dry-run 仍會連線網路或開啟瀏覽器）。
- **清理（Cleanup）**：如何拆除本次執行所建立的實例。切勿直接用通用程序名稱（如 `killall node`）亂砍；只終止你自己啟動的程序或指定 Port 的服務。Cleanup 只移除實例與暫存狀態，**絕不刪除驗證證據**——證明產物必須在拆除後依然完好保存在技能所指定的位置。
- **輔助腳本（Helpers）**：技能所附帶的任何腳本都必須是可直接執行的，且其呼叫方式必須直接展示在技能內文中。需要讀者反向工程才能看懂怎麼用的輔助腳本，不配稱為輔助腳本。

## 3. 建立初始功能地圖（Seed the feature map）

建立 `.agents/skills/verify-<app>/features/README.md`，並為你識別出的每個面向使用者的功能各建立一個檔案（初期目標先抓最重要的 3 到 5 個核心功能，可從路由、指令、選單或文件中提取）。結構請遵循 [`references/feature-map-example/`](references/feature-map-example/) 中的範例，包含一份 README 索引與每個功能獨立的 Markdown 檔。每個功能檔都必須從「使用者視角」回答：這個功能是什麼、如何到達那裡、如何用測試架驅動它，以及什麼可觀測的最終狀態能證明它正常運作。四個固定的 H2 標題依序為：`Sub-features`（子功能）、`How to get to it (user POV)`（如何進入 - 使用者視角）、`Driving it with <harness>`（使用測試架驅動），以及 `Gotchas`（常見陷阱）。如果種子資料缺少某個使用者旅程所需的前提條件，該旅程應直接回報失敗，並將原因寫入該功能的 `Gotchas` 中——**切勿為了讓測試通過而削弱驗證旅程的標準**。功能地圖是儲存庫持續維護的驗證基準；當地圖中列出了多個進入點時，只挑一個最方便的進入點跑完並不算完整驗證。

## 4. 在交付前親自驗證產出的技能（Prove the generated skill before handing it over）

照著你寫好的技能指令，從頭到尾完整執行一次：啟動（Launch）、健康檢查（Doctor）、驅動**一個**已建立地圖的功能（跑通一個即可，地圖的存在是為了讓後續執行能涵蓋其餘功能）、擷取證據（Evidence）、清理環境（Cleanup）。在執行 Cleanup 之後，確認證據檔案依然存在於指定位置——會把證據一起吃掉的 Cleanup 代表此步驟失敗。修正所有失敗之處，且在每次失敗的迭代後也必須執行 Cleanup，以免失敗的嘗試留下孤兒程序與被占用的連接埠。**一份從未被實際執行過的生成技能只是草稿，不是可交付成果。** 若你是在替代環境（例如用容器代替全新 VM、用本機服務代替遠端環境）中完成驗證，請明確列出替代環境自動幫你完成、但真實目標環境不會自動完成的每一個設定步驟；這些步驟在真實目標環境跑過之前，都應維持標記為「未驗證（unverified）」。

## 5. 提供後續維護迴圈建議（Offer the maintenance loop）

向使用者指出未來可使用 `/maintain-verification-skill` 來隨著應用程式演進保持功能地圖的準確性。僅在使用者主動詢問時，才建議定期執行的頻率。
