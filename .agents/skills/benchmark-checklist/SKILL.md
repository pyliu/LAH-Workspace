# Benchmark Checklist（效能基準測試檢核表）

當你要產出任何效能數據時請使用本檢核表：包括 PR 的前後對比、效能退化（regression）聲明、爬山最佳化（hillclimb）測試架、或是套件與設定的選擇。請用實際執行的證據來回答每一個問題，而非對程式碼進行猜測。

> **強制輸出語言規範**：所有效能檢核分析、數據報告與最終結論，**一律強制使用台灣繁體中文輸出**。

若使用者只是要求一個快速的粗略估計（ballpark），跑一次就夠了，但仍必須檢查問題 4 與問題 7，並明確註明「這只是單次執行結果」。除非該次結果看起來有異，否則可略過其餘問題。**注意：在多個選項之間做選擇時，絕不能只靠粗略估計。**

## 在執行任何測試之前（Before you run anything）

- 先寫下你預期做出的聲明，使用你準備交付的精確字句（例如：「在 6 萬筆資料集上，匯出功能的 p50 速度快了 30%」）。以下所有問題都是為了檢驗這句話。
- 閱讀量測腳本。記下它計時了什麼、計數了什麼，又忽略了什麼。
- 檢查機器當前的負載與核心數（例如在 Linux 使用 `uptime` 與 `nproc`，在 Windows 檢查系統工作管理員或處理器使用率）。如果機器正忙，找出是什麼程序在跑。若無法停止背景程序，請交錯執行對照組（A、B、A、B），讓雙方承受相同的雜訊，並在報告中據實說明。

## 七大檢核問題（The questions）

1. **為什麼沒有快兩倍？（Why not double?）** 點出瓶頸限制器（limiter）。請在「不計入報告」的獨立執行中進行剖析（profile），因為剖析器與追蹤器本身會拖慢執行速度。觀察各程序的 CPU 使用率、執行期剖析器（如 `node --cpu-prof`、`py-spy`、`perf`）、I/O 等待時間與系統呼叫次數，並將熱點（hot spot）對應回原始碼。同時也要監看負載產生器（load generator）：如果它先飽和了，你量測到的其實是負載產生器本身的極限。如果某項修改沒有讓數據變動，瓶頸限制器能解釋原因——在宣稱該修改無用之前，請先把限制器找出來。
2. **雙方都經過調校了嗎？（Was it tuned?）** 請以正式環境（production）的運作方式來執行對照雙方：使用正式發行建置（release builds）、正式環境旗標與環境變數、批次與交易（transaction）設定、連線池、與正式環境一致的冷熱快取狀態，以及相同的版本與資料集。如果其中一方使用預設值執行，你比較的是「設定檔差異」而非「實作差異」。若瓶頸限制器其實是個設定問題（例如每筆資料都單獨 commit、使用 debug 建置、缺少資料庫索引），代表該方根本未經調校。請先將它調校好再重新量測，然後才能選出贏家；若無法調校，切勿根據該次執行選出贏家。當使用者正在決定要採用哪個方案時，把聲明限縮在「以目前的預設設定而言」並不能解決問題，因為使用者採納的是該方案本身，而非今天的暫時設定。
3. **是否突破了物理與數學極限？（Did it break limits?）** 請算一下算術。將每秒位元組數（bytes/s）與磁碟及網路頻寬相比、將每秒操作數乘以單次操作成本與 CPU 核心數相比，並將「省下的時間」與「被修改部分原本佔用的時間」相比。移除一個原本佔整體執行時間 10% 的部分，最多只能讓整體執行速度快約 11%（依據阿姆達爾定律 Amdahl's Law）。任何超越極限的數據，量測到的肯定不是目標工作本身，而是快取命中、空操作（no-op）或程式 Bug。
4. **過程中是否發生錯誤？（Did it error?）** 統計失敗次數與非成功回應，並檢查輸出結果是否**正確**，而不只是「有輸出」。拒絕請求（rejections）通常非常快，而逾時（timeouts）與重試（retries）則非常慢。如果測試腳本沒有統計錯誤次數，請加上錯誤計數。
5. **結果可重現嗎？（Does it reproduce?）** 對照雙方各至少執行 5 次，並採交錯順序執行（A、B、A、B……），使暖機（warmup）、延遲初始化（lazy initialization）、快取與系統漂移不會偏袒任何一方。回報中位數（median）與全距（range）。若雙方的差距小於多次執行間的變異範圍，代表**沒有可量測的顯著差異**。當結果非常接近時，請使用秩和檢定（rank-sum test）或測試架內建的統計工具。
6. **這真的重要嗎？（Does it matter?）** 在呈現任何微基準測試（micro-benchmark）結果的同時，請在真實資料量與並行度下量測使用者實際等待的端到端（end-to-end）路徑，並回報該微觀結果佔整體的比例。一個只佔單次請求 1% 時間的輔助函式，無論被最佳化到多快，最多也只能讓該請求快 1%。
7. **工作真的有執行嗎？（Did it even happen?）** 確認目標工作確實發生在計時區間之內：請求確實抵達伺服器、資料列確實寫入、位元組確實讀取，且程式碼確實使用了該結果。延遲求值程式碼（沒人迭代的 generator、沒人 await 的 Promise、被 JIT 編譯器直接丟棄的無用計算結果）以及逾時中斷，都會為「根本沒發生的工作」產出看似漂亮的數據。

## 報告格式（Report）

- **開門見山給出判定結論**：變快（faster）、變慢（slower）、無可量測差異（no measurable difference），或無法下定論（inconclusive）。
- **附上帶單位的數據、執行次數、全距與瓶頸限制器**：例如：「p50 由 41 ms 降至 33 ms，雙方各執行 7 次之中位數，修改後全距為 32 至 35 ms，瓶頸受限於單核心 JSON 解析。」
- **何時應判定為「無法下定論（inconclusive）」**：當你宣稱有差異卻無法點出瓶頸限制器、當其中一方未經調校就執行、或當你無法確認問題 4 與問題 7 時，請直接判定為無法下定論，並明確點出缺口。
- **保持 PR 內文精簡**：依據 **open-a-pr** 劇本，在 PR 內文中只放一個主要核心數據，將詳細執行紀錄、全距與限制器證據放在連結的產物或筆記檔中。

## 與其他效能劇本的配合（Other perf material）

- 在 **perf-issue** 劇本根據基準線（baseline）擬定計畫之前，先用本檢核表檢驗該基準線，並檢驗後續產出的每一個數據。
- 在 **hillclimb** 劇本凍結測試架（harness）之前，先用本檢核表檢驗該測試架。凍結後的測試架應自動印出錯誤數與實際完成的工作量計數，讓每一次保留或還原（keep-or-revert）都能免費完成問題 4 與問題 7 的檢查。
